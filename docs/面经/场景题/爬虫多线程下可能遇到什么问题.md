## 1. 问题全景图

爬虫的瓶颈通常在 I/O（DNS、TCP 握手、TLS、服务器响应、代理链路），多线程能显著提高吞吐。但它也会把“单线程下不明显的问题”放大成线上事故，典型表现为：数据重复、线程卡死、QPS 失控、被封禁、内存暴涨、目标站点被打挂、自己服务被打挂。

从工程角度看，多线程爬虫需要同时满足三个目标：

- 正确性：不漏抓、不重抓、数据不乱序或可接受乱序。
- 稳定性：可控的并发、可控的资源（连接、线程、队列、内存）。
- 可治理：可观测、可限速、可降级、可停止、可恢复。

## 2. 共享数据结构的线程安全问题

### 2.1 典型症状

- URL 去重失效：同一个 URL 被多次抓取。
- “偶发”异常：`ConcurrentModificationException`、数组越界、HashMap 死循环（不同语言表现不同）。
- 统计指标不准：计数器丢失更新，成功率突然异常。

### 2.2 根因拆解

- 原子性：`check-then-act` 不是原子操作（例如 “如果没抓过就入队”）。
- 可见性：线程 A 更新了去重集合，线程 B 仍读取到旧值（缺少 happens-before 关系）。
- 有序性：编译器和 CPU 可能重排指令，导致观察到的执行顺序与代码顺序不一致（需要通过锁、`volatile`、原子类建立内存语义）。

### 2.3 解决方案（按“成本/效果”分层）

#### 2.3.1 单机：使用线程安全容器与原子语义

- URL frontier（待抓取队列）：优先 `BlockingQueue`（如 Java 的 `LinkedBlockingQueue`）。
- URL 去重集合：
  - Java：`ConcurrentHashMap.newKeySet()`，避免用 `Collections.synchronizedSet(new HashSet<>())` 做高并发热点。
  - 计数：高并发累加用 `LongAdder`，而不是 `AtomicLong`（热点竞争更小）。

```java
import java.util.Set;
import java.util.concurrent.*;

public class UrlFrontier {
  private final BlockingQueue<String> queue = new LinkedBlockingQueue<>(100_000);
  private final Set<String> visited = ConcurrentHashMap.newKeySet();

  public boolean offerIfAbsent(String url) {
    // “去重 + 入队” 必须作为一个原子决策，否则会重复抓取
    if (!visited.add(url)) return false;
    return queue.offer(url);
  }

  public String take() throws InterruptedException {
    return queue.take();
  }
}
```

要点：

- `visited.add(url)` 在并发下是原子的（对同一个 key）。
- 仍需考虑“入队失败”时的补偿：队列满导致 `offer` 失败，会造成“标记已访问但未入队”，从而漏抓。

#### 2.3.2 单机：为“去重 + 入队”补偿与一致性兜底

处理队列满的一般策略：

- 强一致（不漏抓）：`put` 阻塞等待；或者 `offer(url, timeout)` 超时后回滚 `visited`。
- 最终一致（允许漏抓）：记录告警并把 URL 落盘到补偿队列（例如文件或本地 RocksDB）。

```java
public boolean offerIfAbsent(String url, long timeoutMs) throws InterruptedException {
  if (!visited.add(url)) return false;
  boolean ok = queue.offer(url, timeoutMs, TimeUnit.MILLISECONDS);
  if (!ok) {
    visited.remove(url); // 回滚，避免漏抓
  }
  return ok;
}
```

#### 2.3.3 分布式：用“幂等”代替“绝对不重复”

分布式下做到严格全局去重成本很高（网络、存储、锁竞争）。更常见的工程策略是：

- 抓取端允许 at-least-once（可能重复）。
- 解析、落库端做幂等：用唯一约束兜底（例如 `url_hash` 唯一索引），或用内容指纹（`content_hash`）去重。

## 3. 连接与网络资源耗尽

### 3.1 典型症状

- 大量超时：`connect timeout`、`read timeout`。
- 连接池耗尽：等待连接时间飙升。
- 本机端口耗尽：`TIME_WAIT` 堆积导致新连接失败（不同 OS 报错不同）。
- 代理被打满：代理响应慢，线程全部阻塞。

### 3.2 根因

- 线程数与连接数无上限，导致同时建立过多连接。
- HTTP 客户端未复用连接（每次请求都新建）。
- 超时与重试策略不当：无退避重试引发“重试风暴”。
- 代理池没有“按健康度调度”，坏代理拖慢全部线程。

### 3.3 解决方案

- 限制并发的第一优先级不是线程数，而是“对同一目标域名的并发连接数”。
- 使用连接池并配置上限、超时：
  - 连接获取超时（pool/acquire timeout）。
  - 建连超时（connect timeout）。
  - 读超时（read timeout）。
- 将重试做成“有上限 + 指数退避 + 抖动（jitter）”，避免所有线程同一时刻重试。
- 代理池健康检查：
  - 失败计数、熔断（短时间失败过多直接下线）。
  - 分级回收（隔离观察再恢复）。

可以用 `Semaphore` 做每个 host 的并发上限（示例为“核心思路”）：

```java
import java.net.URI;
import java.util.concurrent.*;

public class HostConcurrencyLimiter {
  private final ConcurrentHashMap<String, Semaphore> semaphores = new ConcurrentHashMap<>();
  private final int perHost;

  public HostConcurrencyLimiter(int perHost) {
    this.perHost = perHost;
  }

  public <T> T callWithHostLimit(String url, Callable<T> task) throws Exception {
    String host = URI.create(url).getHost();
    Semaphore sem = semaphores.computeIfAbsent(host, h -> new Semaphore(perHost));
    sem.acquire();
    try {
      return task.call();
    } finally {
      sem.release();
    }
  }
}
```

## 4. 限速问题

### 4.1 典型症状

- 目标站点返回 `429`、`403`、验证码、人机校验。
- 同一 IP 被封；Cookie 被封；账号被封。
- 目标站点响应时间拉长，错误率上升，爬虫进入“重试风暴”。

### 4.2 根因

- 仅做全局限速，未做 per-host、per-path、per-IP 限制。
- 未识别目标的限流信号（`Retry-After`、429 模式、滑块验证等）。
- 业务逻辑把“失败”当成“需要更快重试”，反而加速压垮对方。

### 4.3 解决方案

- 多级限速：
  - 全局限速：保护自己（线程池、连接池、CPU）。
  - host 维度限速：保护目标站点（同域名并发与 QPS）。
  - 账号、Cookie、代理维度限速：保护资源池。
- 识别服务器信号：
  - 收到 `429` 且有 `Retry-After`，应按其建议等待。
  - 某段时间内 403/验证码比例上升，触发降速或切换策略（代理、UA、Cookie）。
- 令牌桶 / 漏桶：
  - 令牌桶适合“平均速率 + 突发”。
  - 漏桶适合“强平滑”输出。

## 5. 重试、超时、失败处理的并发陷阱

### 5.1 典型症状

- 同一个 URL 被无限重试，队列永远清不空。
- 大量线程阻塞在超时上，吞吐反而下降。
- 失败率上升时，系统资源（线程、连接、队列）被重试占满，成功请求无法执行。

### 5.2 解决方案

- 超时必须分层：DNS、connect、read、整体 deadline。
- 重试必须有边界：
  - 最大次数（例如 3 次）。
  - 最大总耗时（例如 30 s）。
  - 指数退避 + 抖动：`base * 2^n + random(0, jitter)`。
- 按错误类型决定是否重试：
  - 可重试：超时、连接被重置、`503`。
  - 不可重试或谨慎：`400`、确定性的 `404`、明确的权限失败。
- 失败队列与死信（DLQ）：
  - 重试耗尽的任务进入死信队列，后续人工分析或低优先级回放。

## 6. 任务分配、队列与背压

### 6.1 典型症状

- 生产速度远大于消费速度：内存暴涨，最终 OOM。
- 解析很快、落库很慢：队列堆积，最终全部阻塞。
- 线程池被阻塞任务占满：新任务进不来（线程饥饿）。

### 6.2 解决方案

- 明确“流水线分层”并在每层做背压：
  - fetch（下载）层：I/O 密集。
  - parse（解析）层：可能 CPU 密集（DOM、正则、压缩解码）。
  - persist（落库）层：I/O 密集，且常是瓶颈。
- 队列必须有界（bounded）：
  - 无界队列会把压力推到内存，属于“把事故延后”。
  - 有界队列能逼迫系统降速，形成自然背压。
- 线程池拆分：
  - 不要用一个线程池同时做下载与落库，否则慢任务会“占坑”。
- 落库做批量化与幂等：
  - 批量 insert/update。
  - 唯一键冲突直接忽略或转为 update，避免重复写放大。

## 7. 死锁、活锁、饥饿与阻塞链路

### 7.1 典型场景

- 多把锁嵌套：抓取时拿了 URL 锁，又拿了统计锁，另一个线程反向获取，形成死锁。
- 活锁：多个线程不断让出资源但都无法推进（常见于错误的自旋与退避策略）。
- 饥饿：高优先级任务长期抢占，低优先级任务永远拿不到线程或锁。

### 7.2 解决方案

- 降低锁粒度：用无锁或低锁的数据结构（`ConcurrentHashMap`、`LongAdder`）。
- 统一锁顺序：多把锁必须按固定顺序获取。
- 避免“锁内 I/O”：在持锁时发网络请求、写 DB，属于高风险设计。
- 使用超时锁：`tryLock(timeout)`，避免永久等待。

## 8. 数据一致性与幂等

### 8.1 典型症状

- 同一页面多次写入，造成重复数据。
- 内容更新导致“新旧版本交错”，最终落库是旧数据。
- 多线程同时更新同一条记录，出现最后写入覆盖（lost update）。

### 8.2 解决方案

- 用数据库约束表达幂等：
  - 以 `url_hash` 或业务主键建唯一索引。
  - 写入使用 upsert（不同数据库语法不同）。
- 版本化更新：
  - 保存 `fetch_time` 或内容版本号。
  - 落库时只允许更“新”的版本覆盖更“旧”的版本（比较时间戳或版本号）。
- 任务幂等：
  - 每个 URL 的抓取任务可以重复执行，但最终数据只有一份且可被更新。

## 9. 优雅停止、断点恢复与可重复运行

### 9.1 典型症状

- 程序退出时任务丢失：队列在内存里，重启后从头开始。
- “正在处理”的任务被中断，产生半写入、脏数据。

### 9.2 解决方案

- 停止语义要明确：
  - stop accepting：不再接收新 URL。
  - drain：处理完队列里的任务再退出。
  - hard stop：立即退出（用于自我保护）。
- 断点恢复：
  - URL frontier 落盘：本地 KV（RocksDB）、消息队列（Kafka/RabbitMQ）、数据库表。
  - visited 去重集可用 Bloom Filter + 增量日志，或直接以“落库唯一键”作为最终去重依据。

## 10. 可观测性与排障

### 10.1 必备指标

- 队列长度与入队/出队速率（frontier depth）。
- 每层耗时分布：DNS、connect、TTFB、download、parse、persist。
- 连接池：活跃连接、等待获取连接的时间。
- 错误码分布：429、403、5xx、超时。
- 每 host 的 QPS 与并发数。

### 10.2 排障抓手

- 线程 dump：定位是否死锁、是否大量阻塞在同一位置（如连接池获取、队列 `take`、锁竞争）。
- 采样日志：对“重试次数高、耗时长”的 URL 打点，避免全量日志淹没信号。
- 故障注入：模拟超时、慢响应、代理故障，验证退避与熔断是否生效。
