## 1. 先澄清需求：你要的 ID 是什么样

“发号器”只是手段，面试时先把需求说清楚更关键：

- **全局唯一**：不同机器、不同进程、不同机房不会冲突。
- **性能与延迟**：是否需要每秒几十万、上百万的生成吞吐。
- **有序性**：是否要求趋势递增（便于分页、索引、分库分表路由）。
- **可用性**：发号器挂了是否允许业务停写，是否允许降级。
- **可追溯性**：是否需要把时间/业务线/机房编码进 ID。

## 2. 数据库自增 ID 的局限性（分布式视角）

数据库自增在单库里很好用，但放到分布式系统里会遇到这些问题：

- **单点与写入串行化**：自增值分配天然需要串行化，写入并发越高，越容易成为瓶颈。
- **分库分表冲突**：多个库各自自增会产生重复 ID，需要额外的全局协调。
- **跨库迁移与合并成本**：数据迁移/合库时容易出现主键冲突，需要额外改造。

工程上能缓解但会复杂：

- 设置不同的起始值与步长（例如 A 库生成奇数、B 库生成偶数），扩容与运维成本高。
- 使用号段表（segment）减少竞争，但需要专门设计（见下文对比）。

## 3. Redis `INCR` 作为发号器的优势

Redis 作为独立的发号器，核心价值是把“全局序列”从数据库里剥离出来：

- **原子自增**：`INCR`/`INCRBY` 是原子操作，单 key 自增不会并发冲突。
- **高吞吐、低延迟**：内存路径短，适合做高频序列服务。
- **天然服务化**：多业务共用一个“序列中心”，避免多库多方案。

## 4. Redis 发号器的关键设计点（说到这里更像“做过”）

### 4.1 Key 设计：按业务维度隔离

常见做法是每个业务一个 key，例如 `seq:order`、`seq:pay`。如果需要分区或按天归档，可以把日期放进 key（例如 `seq:order:20260125`）。

### 4.2 初始化与过期：避免“从 0 开始”的风险

如果 key 会过期（按天），要保证初始化与 `EXPIRE` 的原子性，避免并发下重复初始化。

```lua
-- KEYS[1] = 序列 key
-- ARGV[1] = 初始值（例如 1000000）
-- ARGV[2] = 过期秒数（例如 86400）
local v = redis.call('INCR', KEYS[1])
if v == 1 then
  redis.call('SET', KEYS[1], ARGV[1])
  redis.call('EXPIRE', KEYS[1], ARGV[2])
  return tonumber(ARGV[1])
end
return v
```

### 4.3 可用性与一致性：防止主从切换导致“回退”

Redis 复制是异步的：主节点返回成功不代表从节点已经收到写入。如果主节点故障切主发生“丢写”，计数可能回退，从而产生重复 ID。

常见应对策略（按强度递增）：

- **号段预取**：服务端用 `INCRBY` 一次拿一段号（例如 1 万个），在本地内存递增发放，减少 Redis 调用次数，也降低切主窗口里的重复概率。
- **写入等待复制**：用 `WAIT` 等待写入被 N 个副本确认后再返回（牺牲延迟换一致性）。
- **写入门槛**：配置 `min-replicas-to-write` / `min-replicas-max-lag`，副本落后时拒绝写入，避免“主活着但没有可靠副本”的状态继续发号。

如果业务对“绝不重复”要求极高，通常会选择雪花算法或数据库号段来获得更强的确定性。

## 5. 横向对比：Redis、数据库自增、号段、雪花

| 方案 | 优点 | 代价/风险 | 适用场景 |
| --- | --- | --- | --- |
| 数据库自增 | 最简单，天然递增 | 单点瓶颈、分布式冲突 | 单库或低并发写入 |
| 数据库号段（Segment） | 强一致、吞吐高（批量拿号） | 需要表设计与发号服务 | 中大型系统的通用方案 |
| Redis `INCR` | 实现简单、吞吐高 | 切主回退风险、依赖 Redis 可用性 | 允许工程化权衡的高并发场景 |
| 雪花算法（Snowflake） | 去中心化、高可用、趋势递增 | 时钟回拨处理复杂 | 多机房、高可用优先 |

## 6. 总结

- “为什么不用数据库自增”本质是分布式扩展问题：全局唯一与写入并发会把自增推成瓶颈或冲突源。
- Redis `INCR` 能用很简单，但要讲清楚切主回退与一致性策略（`INCRBY` 号段、`WAIT`、写入门槛）。
- 方案选型看需求：要强一致与可控，号段常是稳妥解；要去中心化高可用，雪花更常见。
