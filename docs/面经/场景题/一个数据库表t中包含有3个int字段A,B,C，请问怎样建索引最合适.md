## 1. 先问清楚：你的查询模式是什么

“A、B、C 三个 int 字段怎么建索引”没有唯一答案，取决于你的高频 SQL 形态。面试时建议先反问并引导：

- 主要查询是 `WHERE` 过滤，还是 `ORDER BY/GROUP BY`？
- 是否有联合条件（`A=? AND B=?`）？
- 是否有范围查询（`A>?` 或 `BETWEEN`）？
- 返回列有哪些，是否需要覆盖索引减少回表？

如果面试官不给更多信息，可以给出“分场景方案 + 验证方法”，体现工程思维。

## 2. 联合索引设计原则（可复述版本）

### 2.1 左前缀原则

联合索引 `(A, B, C)`：

- 可以支持以 `A` 开头的条件组合：`A=?`、`A=? AND B=?`、`A=? AND B=? AND C=?`。
- 通常不支持跳过 A 直接用 `B=?`（除非优化器做其他选择）。

### 2.2 等值在前，范围在后

如果存在范围条件，一般把范围列放在后面，因为范围会“截断”后续列的利用。

### 2.3 兼顾排序与分组

如果有 `ORDER BY`，索引顺序要能满足排序顺序，才能避免 filesort；这往往比“选择性最高的列在前”更重要。

## 3. 典型方案（按常见 SQL 形态给答案）

### 3.1 以 A 作为主过滤条件

高频 SQL：

- `WHERE A = ?`
- `WHERE A = ? AND B = ?`
- `WHERE A = ? AND B = ? AND C = ?`

推荐：联合索引 `(A, B, C)`（或至少 `(A, B)`）。

### 3.2 B/C 也会被单独查询

如果大量查询是：

- `WHERE B = ?`
- `WHERE C = ?`

那么 `(A, B, C)` 无法覆盖这些查询，可能需要补充单列索引 `B` / `C`，或重排联合索引（取决于整体查询占比）。

### 3.3 存在范围查询

例如：

- `WHERE A = ? AND B > ?`

通常建议 `(A, B)`，并把范围列放在后。

## 4. 避免冗余索引：别把写性能拖垮

索引越多：

- 写入越慢（维护更多 B+ 树）
- 占用越多 Buffer Pool 与磁盘

如果已经有 `(A, B, C)`，再建 `(A, B)` 往往是冗余（是否冗余要看是否存在覆盖索引需求与执行计划差异）。

## 5. 用执行计划验证（落地闭环）

最终用 `EXPLAIN` 验证索引是否真的生效，关注：

- `key`：用了哪个索引
- `rows`：预估扫描行数
- `Extra`：是否 `Using index`、`Using filesort`、`Using temporary`

## 6. 总结

- 没有查询模式就没有“最合适索引”，先问清 `WHERE/JOIN/ORDER BY` 的真实形态。
- 常见最优解是联合索引 + 左前缀：把高频等值条件放前，范围条件放后。
- 索引设计必须用 `EXPLAIN` 验证，并控制索引数量避免写入退化。
