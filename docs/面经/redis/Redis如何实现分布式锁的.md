## 1. 实现中的问题与演进方案

基础的 `SETNX` + `EXPIRE` + `DEL` 组合在实际应用中会遇到多个问题，文章详细介绍了这些问题及其解决方案。

### 1.1 SETNX 和 EXPIRE 的非原子性

**问题描述**：如果在执行 `SETNX` 成功后，客户端在执行 `EXPIRE` 之前崩溃，那么这个锁将没有设置超时时间，变成一个永远不会自动释放的“死锁”。

#### 1.1.1 `SETNX` 的底层原理是什么

`SETNX`（SET if Not eXists）从语义上就是“**key 不存在才写入**”。它的底层原理可以从 Redis 的执行模型与数据结构两点理解：

- 执行模型：
  - Redis 在一个线程的事件循环里串行执行命令（同一实例内，同一时刻只处理一条命令的关键路径），因此 `SETNX` 的“判断是否存在 + 写入”在服务端是一个不可被其他命令打断的临界区，天然具备原子性。
- 数据结构：
  - 每个 Redis DB 维护一个主字典（哈希表）保存 `key -> value` 映射。
  - `SETNX key value` 本质是一次“查字典是否有 key；没有则插入；有则返回失败”的操作，平均时间复杂度为 O(1)。

返回值规则：

- 返回 `1`：表示写入成功（之前不存在该 `key`）。
- 返回 `0`：表示写入失败（`key` 已存在）。

为什么 `SETNX` + `EXPIRE` 会有非原子性问题：

- `SETNX` 只负责“是否写入”，并不会顺带设置 TTL。
- `EXPIRE` 是另一条命令，两条命令之间如果客户端崩溃或网络断开，就会出现“锁存在但无过期时间”的死锁风险。

**解决方案**：将加锁和设置过期时间这两个操作合并成一个原子操作。文章中提到了两种方式：

- **Lua 脚本**：通过 `EVAL` 命令执行一段 Lua 脚本，在脚本内依次执行 `setnx` 和 `expire`，保证了两个操作的原子性。

```lua
if (redis.call('setnx', KEYS[1], ARGV[1]) < 1)
then return 0;
end;
redis.call('expire', KEYS[1], tonumber(ARGV[2]));
return 1;
```

- **SET 命令的扩展参数**：更高版本的 Redis 为 `SET` 命令提供了扩展参数，可以直接在设置 key 的同时指定过期时间并且保证仅在 key 不存在时设置，从而原子性地完成加锁操作。

```shell
SET key value NX EX 30
```

这里的 `NX` 相当于 `SETNX`，`EX 30` 表示设置 30 秒的过期时间。

### 1.2 锁被错误解除

**问题描述**：线程 A 获取了锁，设置了 30 秒超时。但线程 A 的业务执行了超过 30 秒，此时锁已自动过期释放。线程 B 趁机获取了这把锁。随后，线程 A 执行完毕，它执行 `DEL` 命令，错误地释放了本应由线程 B 持有的锁。

**解决方案**：在加锁时，将 `value` 设置为一个唯一的标识（如 UUID），代表当前加锁的线程。在解锁时，必须先验证 `key` 对应的 `value` 是否与自己持有的标识一致，只有一致时才能执行删除操作。这个“检查并删除”的过程也必须是原子的，因此需要使用 Lua 脚本。

- **加锁**：`SET key uuid NX EX 30`
- **解锁 (Lua 脚本)**：

```lua
if (redis.call('get', KEYS[1]) == ARGV[1])
    then return redis.call('del', KEYS[1])
else return 0
end
```

### 1.3 因超时解锁导致的并发

**问题描述**：与上一个问题类似，线程 A 持有的锁因执行时间过长而自动过期，导致线程 B 能够获取到锁。此时，线程 A 的业务逻辑还未执行完，就造成了线程 A 和线程 B 并发执行，破坏了锁的互斥性。

**解决方案**：

1.  **设置足够长的过期时间**：评估业务执行所需的最长时间，并设置一个远大于此时间的过期时间。但这只是一种缓解手段，治标不治本。
2.  **增加守护线程（Watchdog）**：为获取锁的线程启动一个守护线程。守护线程会定期检查主线程是否还持有锁，并在锁即将过期但业务尚未完成时，自动延长锁的过期时间。

### 1.4 看门狗续期的目的是什么

看门狗（Watchdog）续期的本质目标是：**同时降低“锁过期导致并发执行”的概率，并把“锁永不释放”的风险控制在可恢复范围内**。

- 没有看门狗时，你只能在两个坏结果中选一个：
  - 过期时间短：业务偶发变慢就会导致锁过期，出现并发执行，破坏互斥性。
  - 过期时间长：业务异常或进程崩溃时，锁要很久才释放，导致长时间阻塞，放大故障影响面。
- 有看门狗时：
  - 初始过期时间可以设置得相对短（例如 30 秒），降低崩溃后的阻塞时间。
  - 只要持锁线程仍存活，守护线程就周期性续期，避免正常慢请求把锁“跑超时”。

#### 1.4.1 续期的正确姿势：只给“自己持有的锁”续期

续期必须满足两个条件，否则会把别人的锁续命，等价于破坏互斥：

- 续期前必须校验 `value`（唯一标识）仍然等于当前持锁者。
- 校验与 `PEXPIRE` 必须是原子操作（通常用 Lua）。

```lua
-- 如果仍是自己持有的锁，则续期（单位毫秒）
if redis.call('get', KEYS[1]) == ARGV[1] then
  return redis.call('pexpire', KEYS[1], tonumber(ARGV[2]))
else
  return 0
end
```

#### 1.4.2 为什么续期不是“无限续下去”

- 续期与“过期时间”是互补关系：看门狗只在**客户端活着且仍持锁**时续期。
- 一旦进程崩溃、GC 停顿过长、网络分区导致续期失败，锁最终会因过期而释放，从而保证系统具备自愈能力。

### 1.4 锁的不可重入

**问题描述**：一个线程在已经持有锁的情况下，再次尝试获取同一个锁，会因为锁已被自己持有而失败。如果业务逻辑中存在递归调用或方法嵌套，就需要锁是“可重入”的。

**解决方案**：让锁能够记录持有者和加锁次数。

1.  **本地计数**：使用 `ThreadLocal` 在当前线程内记录对某个 `key` 的重入次数。每次加锁时，先检查 `ThreadLocal` 中是否已有记录。如果有，则次数加一；如果没有，则向 Redis 请求新锁。解锁时则次数减一，直到计数为 0 时才真正向 Redis 请求删除 `key`。
2.  **Redis Hash 结构**：使用 Redis 的 Hash 数据结构来存储锁信息。Hash 的 `key` 是锁名，`field` 是线程的唯一标识，`value` 是重入的次数。
    - **加锁**：检查 `key` 是否存在。若不存在，则 `HSET` 创建锁，并将重入次数设为 1。若存在，检查 `field` 是否为当前线程标识。如果是，则通过 `HINCRBY` 将重入次数加一，并重置过期时间。
    - **解锁**：将重入次数减一。如果减后大于 0，则只更新 Hash 值；如果减后等于 0，则 `DEL` 删除整个 `key`。

### 1.5 无法等待锁释放

**问题描述**：上述的加锁操作都是“尝试一次立即返回”，如果获取锁失败，不会等待。

**解决方案**：

1.  **客户端轮询**：当获取锁失败后，线程不立即返回，而是等待一小段时间后再次尝试，直到成功获取或达到指定的超时时间。这种方式会消耗较多 CPU 资源。
2.  **Redis 发布/订阅 (Pub/Sub)**：获取锁失败的客户端订阅一个特定的频道。当持有锁的客户端释放锁时，它会向该频道发布一条“锁已释放”的消息。所有订阅者收到消息后，再次尝试获取锁。

### 1.6 如果分布式锁不设置过期时间，会有什么问题

不设置过期时间（即锁 key 永不过期）最大的问题不是“偶尔死锁”这么简单，而是会把一个局部故障放大成系统级雪崩：**锁无法自愈，等待会无限增长**。

#### 1.6.1 直接后果：永久死锁与业务永久阻塞

- 典型触发链路：
  - 线程 A 获取锁成功。
  - A 在释放锁之前发生进程崩溃、机器宕机、容器被杀、网络隔离、代码异常导致未执行解锁逻辑。
  - 由于没有过期时间，这把锁将一直存在，后续所有竞争者永久拿不到锁。
- 业务表现：
  - 某条关键链路永远卡住（例如同一订单、同一用户、同一库存项的更新）。
  - 即使重启应用也无济于事，因为锁留在 Redis 里，需要人工介入删除。

#### 1.6.2 为什么会导致“服务器崩溃”等严重后果

锁永不过期会把“卡住”转化成资源耗尽，常见放大路径如下：

- 应用侧线程池/连接池耗尽：
  - 获取锁失败的请求不断重试或排队，占满业务线程池。
  - 下游调用占用连接，连接池被占满，导致更多请求堆积。
  - 最终表现为接口超时、雪崩、进程 OOM 或被容器/系统杀死。
- 应用侧 CPU 被打满：
  - 如果采用自旋重试（busy-wait）且没有退避（backoff），会导致 CPU 飙升，进一步放大超时与重试风暴。
- Redis 侧内存被吃光（典型于“锁 key 高基数”场景）：
  - 例如锁 key 按“订单号/请求 ID”生成且永不过期，随着业务增长，锁 key 会无限累计。
  - Redis 内存持续上涨，触发 `maxmemory` 淘汰、写入失败（`OOM command not allowed`）或直接被 OOM killer 干掉。
  - 一旦 Redis 抖动，业务重试会进一步加压，形成恶性循环。
- 运维侧故障处置困难：
  - “锁永不过期”意味着故障恢复依赖人工定位并删除 key，恢复时间不可控。

#### 1.6.3 结论：过期时间不是优化项，是安全阀

- **必须设置过期时间**，否则分布式锁在任何异常场景下都无法保证可恢复。
- 看门狗续期解决的是“业务变慢导致锁过期”的问题；过期时间解决的是“持锁方消失后锁能自愈”的问题，两者缺一不可。

## 2. 集群环境下的挑战

在 Redis 集群（主从、哨兵、Cluster）模式下，分布式锁会面临更严峻的挑战。

1.  **主备切换**：客户端 A 在 Master 节点成功加锁，但这条写命令还未异步同步到 Slave 节点时，Master 节点宕机。哨兵或集群机制将一个 Slave 提升为新的 Master。此时，客户端 B 向新的 Master 请求加锁，由于新 Master 上没有锁的数据，B 也能成功加锁，导致两个客户端同时持有同一把锁。
2.  **集群脑裂**：由于网络分区，原 Master 与其他节点失联，但它仍在独立运行。哨兵集群在另一个网络分区中选举出一个新的 Master。这导致集群中同时存在两个 Master 节点，不同的客户端连接到不同的 Master，都能成功获取同一把锁。
