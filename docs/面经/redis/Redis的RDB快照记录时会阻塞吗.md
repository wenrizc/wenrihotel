## 1. `SAVE` 命令 (阻塞)

`SAVE` 命令会**完全阻塞** Redis 服务器进程。

- **同步执行**：当执行 `SAVE` 命令时，Redis 主线程会同步地将所有数据写入 RDB 文件到磁盘。
- **停止服务**：在这个过程中，Redis 服务器无法处理任何其他命令请求，包括来自客户端的读写请求。
- **生产环境不建议使用**：数据量较大时会导致服务不可用，生产环境通常不会手动执行 `SAVE`。

## 2. `BGSAVE` 命令 (主体后台，但 `fork` 阶段有短暂阻塞)

`BGSAVE` (Background Save) 命令是 Redis 默认和推荐的 RDB 快照方式，它旨在避免阻塞 Redis 主线程。

- **创建子进程**：当执行 `BGSAVE` 命令时，Redis 主进程会调用 `fork()` 系统调用，创建一个子进程。这个子进程专门负责将数据写入 RDB 文件，而父进程（Redis 主进程）则可以继续处理客户端的请求。
- **`fork()` 阶段的短暂阻塞**：虽然 `BGSAVE` 命令本身是后台执行的，但 `fork()` 操作会**短暂地阻塞** Redis 主进程。
    - `fork()` 操作会复制父进程的页表，这需要一定的时间和内存。
    - 阻塞时间与实例内存规模、系统负载、内核与内存管理策略等相关，需要用指标观测。可以通过 `INFO stats` 里的 `latest_fork_usec` 查看最近一次 `fork` 的耗时（微秒）。
- **写时复制 (Copy-on-Write, COW)**：`fork()` 创建子进程后，父子进程会共享相同的内存页面。 只有当父进程（主 Redis 实例）或子进程（RDB 持久化进程）修改共享内存中的某个页面时，操作系统才会复制该页面，从而使得父子进程拥有各自独立的副本。
    - 这意味着子进程在保存 RDB 文件期间，父进程可以继续接收并处理写命令，而不会影响子进程正在快照的数据一致性。
    - COW 机制有效地减少了 `fork` 期间的内存开销，避免了完全复制整个数据集。
- **内存开销**：尽管有 COW 机制，但在 `BGSAVE` 期间，由于主进程的写操作会导致页面复制，Redis 的实际内存使用量可能会暂时增加，最高可能达到原有内存的 2 倍（极端情况下）。 如果系统可用内存不足，`fork` 操作可能会失败。

## 3. `BGSAVE` 的两个影响面（为什么会“感觉卡”）

### 3.1 `fork`：一次性复制页表带来的短暂停顿

`fork` 发生在主线程调用路径上，暂停时长往往是毫秒级，但在大内存、系统抖动或内存紧张时可能更明显。生产上经常把这段停顿当作“RDB 卡顿”的主要来源。

### 3.2 COW：写入越多，额外内存与抖动越大

`fork` 之后父子进程共享内存页，主线程写入越频繁，被修改的页越多，触发的 COW 拷贝就越多：

- 内存会阶段性上涨（取决于写入压力与数据分布）。
- 若触发 swap 或内存回收，延迟会显著恶化。
- 子进程写 RDB 需要磁盘带宽，I/O 紧张时也可能间接影响整体延迟（竞争页缓存、I/O 调度等）。

## 4. 如何判断“是否阻塞”和“阻塞多久”

建议把判断拆成两类：Redis 自身指标与操作系统指标。

### 4.1 Redis 侧观测（面试可直接说命令）

```bash
# RDB 过程与结果
redis-cli INFO persistence

# fork 耗时（微秒）
redis-cli INFO stats | grep latest_fork_usec

# 事件循环延迟与慢命令
redis-cli LATENCY DOCTOR
redis-cli SLOWLOG GET 10
```

常用字段（不同版本字段略有差异，以实际输出为准）：

- `rdb_bgsave_in_progress`：是否正在后台生成 RDB。
- `rdb_last_bgsave_status` / `rdb_last_bgsave_time_sec`：上次结果与耗时。
- `latest_fork_usec`：最近一次 `fork` 的耗时。

### 4.2 OS 侧观测（决定 fork 与 COW 的“体感”）

- 内存水位是否逼近上限、是否发生 swap。
- 磁盘 I/O 是否持续打满（子进程写 RDB）。
- page fault 与内存回收是否明显增加。

## 5. 工程建议（怎么做才不影响线上）

- 大实例避免在高峰期触发 RDB（手动 `BGSAVE` 或配置 `save` 规则都要错峰）。
- 预留足够内存 headroom，避免 COW 叠加导致 OOM 或触发 swap。
- 复制场景注意全量同步：主从全量复制会用到 RDB，容量规划要把这段开销算进去；必要时评估 `repl-diskless-sync` 等能力（仍会 `fork`）。
- 需要低延迟优先时，持久化策略要与业务 SLO 对齐：RDB、AOF、`BGREWRITEAOF` 都可能引入 `fork` 相关抖动。

## 6. 总结

- `SAVE` 会阻塞主线程，生产环境一般不使用。
- `BGSAVE` 主体在子进程完成，但 `fork` 阶段会产生短暂停顿，且写入压力越大 COW 放大越明显。
- 大实例做 RDB 要用指标闭环：`latest_fork_usec`、`INFO persistence`、延迟与系统内存/I/O 水位。
