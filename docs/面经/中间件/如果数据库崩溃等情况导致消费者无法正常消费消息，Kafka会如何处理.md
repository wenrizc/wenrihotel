## 1. 问题拆解：Kafka 会“如何处理”取决于 offset

Kafka 没有 RabbitMQ 的 `ack/nack` 协议回执，Kafka 的“确认语义”主要体现在 **offset 是否提交** 上：

- 提交 offset：语义上表示“我已经确认处理到这个位置”。
- 不提交 offset：故障恢复或 Rebalance 后仍可能从旧 offset 重读，形成至少一次语义。

因此“数据库崩溃导致消费者无法消费”并不是 Kafka Broker 自动替你处理，而是你在消费端需要明确两件事：

1. 失败时要不要推进 offset。
2. 失败消息要走哪条旁路（重试、DLT、落库）。

## 2. 消费者崩溃：Rebalance 与重复消费

### 2.1 崩溃后的分区迁移

当消费者进程崩溃或被判定失活：

1. 消费组触发 Rebalance。
2. 该实例持有的分区被重新分配给组内其他健康实例。
3. 新实例从“已提交 offset”继续消费。

推论：

- 崩溃前尚未提交最新 offset：会从旧 offset 重读，出现 **重复消费**。
- 崩溃前已提交 offset，但业务写库尚未真正成功：会出现 **业务层丢失**。

### 2.2 两个容易踩的超时参数

数据库崩溃往往导致“处理阻塞”，进而影响 poll 与心跳：

- `max.poll.interval.ms`：业务处理过久导致 poll 不及时，可能被踢出组触发 Rebalance。
- `session.timeout.ms`、`heartbeat.interval.ms`：心跳超时也会触发 Rebalance。

面试表达建议：

- Kafka 的稳定性不仅取决于 Broker，也取决于消费者的 poll 循环是否健康。

## 3. 数据库崩溃但消费者仍存活：你有哪些选择

数据库不可用时，消费端常见有三类策略。选哪一种取决于“是否允许阻塞主分区推进”与“是否允许旁路治理”。

### 3.1 策略 A：不提交 offset，让消息重读（保守但会阻塞）

做法：

- 写库失败直接抛异常或返回失败，不提交 offset。

优点：

- 语义直观，消息不会被你主动“跳过”。

缺点：

- 如果数据库长时间不可用，同一条消息会反复失败，导致该分区卡住，后续消息无法推进。
- 处理阻塞还可能触发 Rebalance，导致重复消费范围扩大。

### 3.2 策略 B：提交 offset，把失败消息转移到重试 Topic 或 DLT（主链路不阻塞）

做法：

- 当前消息处理失败，但你选择推进主链路 offset。
- 同时把消息投递到重试 Topic（可恢复错误）或 DLT（不可恢复错误）。

优点：

- 主消费链路继续推进，系统整体吞吐更稳定。

缺点：

- 你必须保证“旁路写入可靠”。否则会出现“offset 已提交，但失败消息也没被可靠保存”的风险。

### 3.3 策略 C：暂停分区消费（Backpressure），等待依赖恢复

做法：

- 检测到数据库不可用后，主动暂停部分或全部分区消费（pause）。
- 以指数退避方式探测数据库是否恢复，恢复后再继续（resume）。

优点：

- 避免无意义的失败风暴，保护下游。
- 不会把失败消息无限重试刷爆日志。

缺点：

- 会产生 lag 增长，需要结合 retention 与容量评估。

## 4. 为什么最终都绕不开“幂等”

Kafka 在工程上更常见的交付语义是 **至少一次**，因此重复消费是常态而不是异常。

会导致重复的典型路径：

- 写库成功，但 offset 提交失败或提交延迟：重启后会重读。
- Rebalance 发生在处理过程中：可能出现同一条消息被不同实例重复处理。

因此消费者侧必须具备幂等或去重能力：

- 数据库唯一约束（业务主键）。
- 幂等表（记录已处理的事件 id）。
- 业务状态机校验（只允许合法迁移）。

## 5. 推荐的工程落地（按可维护性排序）

### 5.1 快速重试 + 延迟重试 + DLT

建议把失败闭环做成三层：

1. 快速重试：应对瞬时错误，次数要小，避免阻塞。
2. 延迟重试：通过重试 Topic 实现退避，避免原地 sleep。
3. DLT：最终失败隔离与治理通道。

### 5.2 写库一致性：Outbox 与去重表

“消费消息 -> 写数据库”的一致性要点是：数据库成功与 offset 提交不在同一个本地事务里。

常见落地方式：

- 去重表：先用事件 id 插入一条“处理标记”（唯一约束），成功则继续执行业务，重复则直接跳过。
- Outbox：把要对外发布的事件写入本地 outbox 表，由异步任务可靠投递，避免分布式事务。

## 6. 一个最小伪代码：失败时 pause + 旁路重试（示意）

```java
// 伪代码，表达控制流：依赖不可用时先 pause，避免失败风暴；必要时旁路到 retry/DLT。
while (true) {
    var records = consumer.poll(Duration.ofMillis(100));
    for (var r : records) {
        try {
            writeToDb(r); // 可能因为数据库崩溃而失败
            consumer.commitSync(); // 处理成功后提交 offset
        } catch (DbDownException e) {
            consumer.pause(consumer.assignment());
            // sleep/backoff + health check
            // 数据库恢复后 consumer.resume(...)
            // 或者把 r 投递到 retry topic，然后提交 offset 推进主链路
        } catch (Exception e) {
            // 不可恢复错误：投递到 DLT，告警，并决定是否提交 offset
        }
    }
}
```
