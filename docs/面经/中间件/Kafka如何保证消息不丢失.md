## 1. 先定义“丢失”是什么

讨论“Kafka 如何保证消息不丢失”前，先把“丢失”拆成三类，否则很容易鸡同鸭讲：

1. **生产端认为成功，但 Broker 实际没可靠保存**：例如 `Leader` 确认后立刻崩溃，副本还没同步。
2. **Broker 保存了，但消费者侧丢了处理语义**：例如 offset 提交与业务处理不一致。
3. **消息被你主动丢弃**：例如 retention 过短导致还没消费到就过期被清理。

Kafka 能保证的是“在合理配置与正确使用下，消息可以持久化、可复制、可回放”。端到端不丢失必须同时约束生产、存储、消费三段。

## 2. 生产阶段：保证“写入成功”足够可靠

### 2.1 `acks`：写入成功的确认门槛

- `acks=0`：不等确认，吞吐高但风险最高。
- `acks=1`：只等 `Leader` 确认，`Leader` 崩溃且未复制时存在丢失窗口。
- `acks=all`：等待 ISR 确认，可靠性更高（延迟与吞吐会受影响）。

工程上如果你在意“写入不丢”，通常会优先考虑 `acks=all`。

### 2.2 ISR 与 `min.insync.replicas`：让“副本不足”变成失败

如果 ISR 数量不足仍然返回成功，会把风险隐藏起来。常见组合：

- Topic 配置足够的副本数（例如 `replication.factor >= 3`）。
- 配置 `min.insync.replicas`。
- Producer 使用 `acks=all`。

这样当 ISR 不足时，写入会失败，促使你降级或告警，而不是悄悄把“弱副本写入”当作成功。

### 2.3 幂等与重试：避免“重试带来的副作用”

网络抖动、超时会触发 Producer 重试。重试带来两个风险：

- 你以为没写入成功，但其实写入成功了，重试会导致重复写入。
- 你以为写入成功了，但其实请求没到达 Broker。

常见做法：

- 开启幂等生产者（`enable.idempotence=true`），降低重试导致的重复。
- 合理配置超时与重试窗口（例如 `delivery.timeout.ms`），确保失败可感知且可控制。

### 2.4 生产端常用“高可靠”基线配置（示意）

```shell
acks=all
enable.idempotence=true
retries=2147483647
delivery.timeout.ms=120000
request.timeout.ms=30000
```

说明：

- 这不是通用模板，实际还要结合吞吐、延迟与集群能力调整。
- “无限重试”必须搭配可观测与熔断策略，否则会在故障时放大压力。

## 3. 存储阶段：保证 Broker 故障不丢

### 3.1 多副本复制是核心

Kafka 的分区日志会落盘，并复制到多个副本。抗单机故障的关键是：

- 副本数足够。
- ISR 策略合理。
- 选主策略不让“落后副本”当 `Leader` 造成缺口。

### 3.2 unclean 选举：可用性与不丢失的矛盾点

当 `Leader` 挂了，如果允许“非 ISR 的落后副本”成为新 `Leader`，集群可用性可能更好，但会引入数据缺口风险。

工程结论：

- **追求不丢失时，要谨慎对待允许落后副本成为 `Leader` 的策略**。

### 3.3 retention：消息“被清理”也等价于丢失

Kafka 不会“消费即删除”，清理由 retention 决定：

- 消费 lag 超过 retention 窗口，会出现“还没消费到就被清理”，这在业务上等价于丢失。

因此“保证不丢”必须包含容量与保留策略治理，而不仅是 `acks`。

## 4. 消费阶段：保证“处理语义不丢”

### 4.1 自动提交 offset 的典型风险

如果开启自动提交 offset，可能出现：

- offset 已提交，但业务写库失败或尚未完成。
- 进程崩溃后不会再重读该消息，造成业务语义丢失。

### 4.2 手动提交：至少一次 + 幂等

更常见的模式是：

1. 拉取消息。
2. 执行业务处理（写库、调用下游）。
3. 处理成功后提交 offset。

这通常实现“至少一次”，会带来重复消费，因此必须配套幂等：

- 数据库唯一约束（业务主键）。
- 去重表（处理过的事件 id）。
- 状态机校验（只允许一次性迁移）。

### 4.3 处理失败：重试 Topic 与 DLT

为了避免毒丸消息卡住分区，建议建立失败闭环：

- 可恢复错误：走延迟重试（重试 Topic）。
- 不可恢复错误：进入 DLT，告警并支持回放。

## 5. 更强一致语义：什么时候需要事务

如果你的链路是“消费 Kafka -> 写 Kafka”，可以考虑用事务把：

- 下游写入。
- offset 提交。

绑定成原子单元，从而获得更强语义（代价是复杂度与性能）。

如果是“消费 Kafka -> 写数据库”，通常仍要靠幂等与 Outbox，而不是指望 Kafka 事务替你覆盖数据库写入。

## 6. 端到端总结（按链路拆解）

| 环节 | 典型风险 | 关键手段 |
| :--- | :--- | :--- |
| Producer -> Broker | `Leader` 确认后故障、重试不确定性 | `acks=all` + `min.insync.replicas` + 幂等 + 可观测重试 |
| Broker 存储与复制 | 副本不足、错误选主、磁盘与网络故障 | 多副本 + ISR 策略 + 谨慎 unclean 选举 |
| Broker -> Consumer | offset 提交与业务处理脱钩 | 手动提交 + 先处理后提交 + 幂等 |
| retention 与容量 | lag 超过保留窗口被清理 | 容量规划 + retention 治理 + 堆积告警 |
| 失败治理 | 毒丸消息、无限重试 | 重试 Topic + DLT + 回放闭环 |
