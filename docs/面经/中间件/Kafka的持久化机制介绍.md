## 1. Kafka 持久化的核心：分区日志（Log）

Kafka 的持久化本质是：把消息按分区追加写入日志文件，并通过多副本复制把日志复制到其他 Broker。

理解持久化机制时，先记住三句话：

1. **一个分区就是一条追加写日志**。
2. **Kafka 不会因为“被消费”就删除消息**，删除由保留策略决定。
3. **可靠性更多依赖副本复制与确认策略**，而不是“每条消息都 fsync”。

## 2. 磁盘上长什么样：Segment 与索引

### 2.1 Segment（段文件）：为什么要分段

如果一个分区只用一个超大文件，会导致：

- 删除与清理成本高。
- 需要频繁维护超大索引。

因此 Kafka 会把分区日志拆成多个段文件（segment），段文件按滚动策略产生。一个段文件通常对应：

- 日志数据文件（存储消息批次）。
- 索引文件（把 offset 映射到文件位置）。

### 2.2 Index：为什么查 offset 不需要全量扫描

Kafka 用索引把“逻辑 offset”映射到“段文件中的物理位置”，读取时通常是：

1. 根据目标 offset 找到所属 segment。
2. 用索引定位到接近的位置。
3. 从该位置顺序扫描直到目标 offset。

工程结论：

- 顺序追加写 + 索引定位读，是 Kafka 吞吐与读性能的基础。

## 3. 写入落盘：页缓存、刷盘与可见性

### 3.1 写入路径（简化）

1. Producer 发送消息到分区 `Leader`。
2. `Leader` 把消息追加到日志（通常先进入 OS 页缓存）。
3. `Follower` 拉取数据并写入本地日志。
4. 达到确认条件后，`Leader` 返回写入成功（受 `acks` 与 ISR 影响）。

注意：

- “写入成功”通常意味着满足复制与确认条件，并不等价于“数据已刷到物理介质”。
- Kafka 更偏向依赖复制来降低单机故障窗口，而不是对每条消息强制刷盘。

### 3.2 为什么追加写通常很快

- 追加写接近顺序 I/O。
- 页缓存能把随机写变成批量刷盘。
- Producer 的批量与压缩进一步减少系统调用与 I/O 次数。

## 4. 删除与保留：Kafka 怎么“清理历史数据”

Kafka 的清理不是按消费，而是按保留策略（retention）：

### 4.1 基于时间/大小的删除（Retention）

常见含义：

- 超过保留时间的 segment 会被删除。
- 超过保留大小阈值也会触发删除。

工程风险：

- 消费 lag 如果超过 retention 窗口，会出现“还没消费到就过期被删除”，业务上等价于丢失。

### 4.2 日志压缩（Log Compaction）：保留每个 key 的最新值

如果 Topic 设为 compaction，Kafka 会在后台清理旧版本记录，保留：

- 同一 `key` 的较新记录（不是实时更新）。
- tombstone（删除标记）在保留窗口后也可能被清理。

典型用途：

- 保存“某个 key 的最新状态快照”（例如用户最新画像、配置快照）。
- 做变更日志（changelog）底座。

工程注意：

- compaction 不是数据库的强一致更新语义，它更像“最终整理”。

## 5. 多副本复制：持久化可靠性的真正关键

单机落盘只能抗进程崩溃，无法抗机器故障。Kafka 的可靠性主要来自：

- 副本数（`replication.factor`）。
- ISR 与 `min.insync.replicas`。
- 生产端 `acks`。

工程结论：

- 想要“尽量不丢”，优先把副本与 ISR 策略配齐，再谈刷盘参数。

## 6. 常见配置项速查（方向性理解）

下面列的是“你需要知道它控制什么”，不建议面试背默认值：

| 配置项 | 作用 |
| --- | --- |
| `log.segment.bytes` | 段文件滚动大小 |
| `log.segment.ms` | 段文件滚动时间 |
| `log.retention.hours` / `log.retention.ms` | 基于时间的保留窗口 |
| `log.retention.bytes` | 基于大小的保留阈值 |
| `log.cleanup.policy` | 清理策略（`delete`、`compact` 或组合） |
| `min.insync.replicas` | 最小同步副本数门槛 |

## 7. 面试总结

1. Kafka 的持久化是“分区追加写日志 + 段文件 + 索引”。

2. Kafka 的删除由 retention/compaction 决定，不是“消费即删除”。

3. Kafka 的可靠性更多依赖“多副本复制 + ISR + `acks`”，而不是每条消息都强制刷盘。
