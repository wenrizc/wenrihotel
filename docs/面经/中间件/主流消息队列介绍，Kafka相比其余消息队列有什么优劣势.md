## 1. Kafka 的优势

1. **吞吐量与水平扩展强**：Kafka 的核心是 `Topic` 分区追加写日志，分区可以分布到不同 Broker，上限更多取决于分区数、磁盘与网络，天然适合水平扩展。

2. **持久化与回放能力强**：Kafka 的数据默认落盘，并按保留策略（retention）保存一段时间。消费者用 offset 控制读取位置，因此可以回放历史数据，适合日志采集、事件溯源、数据管道、流式计算。

3. **多订阅（多消费组）成本低**：同一个 `Topic` 可以被多个消费组独立消费，互不影响。新增下游通常只需要新增消费组，不需要在 Broker 侧配置复杂路由。

4. **分区内顺序可控**：只要把同一业务主键作为 `key`，就可以把同一主键的事件固定到同一分区，从而获得“主键维度”的顺序性。

5. **生态完善**：连接器（数据源接入）、流处理、Schema、监控等生态成熟，更适合作为“数据平台底座”。

## 2. Kafka 的劣势

1. **Broker 侧路由能力弱**：Kafka 没有 Exchange 这类 broker 侧路由抽象，更多是“按 Topic/分区”组织消息。复杂路由通常要在应用侧拆 Topic、改 key 规则，或引入流处理组件做二次分发。

2. **顺序性有边界**：Kafka 的顺序保证通常是“分区内有序”，跨分区不保证全局有序。想要全局顺序往往意味着单分区，吞吐会受限。

3. **端到端一致性需要设计**：Kafka 常见交付语义是至少一次，重复消费需要业务幂等。要实现更强语义，需要事务、Outbox、幂等键、去重表等配套机制。

4. **运维与参数治理更复杂**：分区规划、复制、Rebalance、磁盘、保留策略、热点 key、配额限流等需要系统治理。对小团队或简单业务可能偏“重”。

5. **延迟/定时不是原生强项**：Kafka 本身不提供“按消息 TTL 自动延迟投递”的交换机能力，延迟重试通常靠重试 Topic 与调度逻辑实现。

## 3. 对比分析：Kafka、RabbitMQ、RocketMQ 怎么选

### 3.1 选型维度速查表

| 维度   | Kafka                 | RabbitMQ       | RocketMQ         |
| ---- | --------------------- | -------------- | ---------------- |
| 核心定位 | 事件流平台                 | 消息代理           | 面向业务消息的队列        |
| 典型吞吐 | 高                     | 中              | 高（通常介于二者之间）      |
| 消费模型 | Pull + offset         | Push + ack     | Pull 为主（随实现）     |
| 路由能力 | Topic/分区为主            | Exchange 路由强   | 业务语义与标签能力较强      |
| 回放能力 | 强（offset + retention） | 弱（通常消费即删除）     | 具备回溯能力（随实现）      |
| 顺序性  | 分区内有序                 | 队列内有序（并发消费会弱化） | 支持顺序消息（随实现）      |
| 延迟消息 | 通常靠方案实现               | 可用 TTL / 插件等   | 通常支持更直接          |
| 适用场景 | 数据管道、日志、事件溯源、多下游订阅    | 业务解耦、任务队列、复杂路由 | 交易、电商、需要更强业务消息能力 |

### 3.2 Kafka vs. RabbitMQ：

Kafka 更像“流水账本”，强调：

- 数据落盘与保留窗口。
- 多下游订阅与回放。
- 分区带来的并行与扩展。

RabbitMQ 更像“邮局”，强调：

- 灵活路由（Exchange + Routing Key）。
- push 模型下的消费控制与确认协议。
- 业务集成与企业协议生态。

### 3.3 Kafka vs. RocketMQ：为什么很多业务队列会选 RocketMQ

RocketMQ 往往更贴近业务消息中常见诉求：

- 更直接的延迟/定时能力（依赖具体版本与实现）。
- 顺序、事务等能力更“业务化”。

而 Kafka 在“数据流与平台化”方面更强，尤其是“多下游订阅 + 回放 + 数据管道”。

## 4. 按需求反推选型

1. **需要海量写入、要回放、多个下游订阅**：优先 Kafka。

2. **需要复杂路由、吞吐不是瓶颈、希望开箱即用**：优先 RabbitMQ。

3. **更偏交易类业务消息，强依赖顺序、延迟、事务等业务语义**：优先 RocketMQ。

4. **任何选型都绕不开三件事**：

- 交付语义（至少一次、至多一次、是否追求 EOS）。
- 幂等与去重方案。
- 监控与故障治理闭环（积压、重试、DLT、回放）。
