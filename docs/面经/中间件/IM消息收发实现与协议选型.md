# IM消息收发实现与协议选型

## 1. 端到端收发流程
典型 IM 架构分为接入层（长连接网关）、业务层、存储与消息队列。客户端登录后建立长连接，完成鉴权与心跳，网关维护 `userId -> channel` 的会话映射。发送消息时，客户端先把消息投递到网关，业务层生成全局消息 ID、落库或写入消息日志，并根据路由找到接收方所在网关。接收方在线则通过网关推送到客户端，不在线则写入离线库并在上线时补发。

## 2. 收发可靠性设计
可靠性一般从“至少一次投递、去重展示与可补偿”三个方向设计。

- 发送前生成 `msgId` 与 `seq`，服务端落库成功后再 ACK，保证至少一次投递。
- 客户端按 `msgId` 去重，避免重试导致重复展示，同时维护已读、送达等状态表。
- 离线消息设置 TTL 与拉取窗口，结合补偿任务处理超时与失败重投。

## 3. 高并发与流量激增处理
当消息量突然上升时，接入层先水平扩展承载连接，再通过路由表或一致性哈希把用户连接分片到不同节点。业务层通常引入消息队列进行削峰与异步分发，避免同步推送把网关压垮。对单用户或单群的突发流量可使用令牌桶限流、发送频控、降级策略（丢弃低优先级、合并通知）。针对大群或大 V 的扇出场景，可按群成员分区、分批推送，并结合缓存与读写分离降低热键压力。

## 4. 协议选型与取舍
IM 通常采用长连接协议以降低延迟与握手成本，常见选择如下。

| 协议 | 优点 | 适用场景 |
| --- | --- | --- |
| TCP 自定义二进制 | 开销低、可控性强 | 移动端、桌面端长连接 |
| WebSocket | 浏览器兼容、易穿透代理 | Web 端与小程序 |
| MQTT | 轻量、支持 QoS | 物联网与弱网场景 |

实际工程里经常同时支持 TCP 与 WebSocket，移动端走 TCP，自研二进制协议保证性能，Web 端走 WebSocket 方便接入。无论哪种协议，都需要心跳、重连、断线续传与压缩策略来保证弱网可用性。

## 5. 常见追问/易错点
常见追问与易错点如下。

- 追问：如何保证消息不丢、不重、不乱序？
  - 答：不丢靠服务端落库与 ACK，重试靠 `msgId` 去重，乱序靠会话 `seq` 与客户端有序展示。
- 易错点：只关注推送路径忽略离线与补偿。
  - 答：离线消息、失败重投与状态一致性同样是收发链路的一部分，必须设计补偿与清理策略。
