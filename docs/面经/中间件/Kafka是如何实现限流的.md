## 1. Kafka 的“限流”在限制什么

Kafka 的限流（throttling / quota / backpressure）通常不是一个单点开关，而是三层共同作用：

1. **消费端限流**：控制拉取与处理节奏，保护消费者和下游（数据库、RPC、缓存）。
2. **生产端限流**：控制写入速率，保护 Broker 与网络，同时避免下游被洪峰冲垮。
3. **Broker 端配额**：集群级安全阀，用配额限制某个 client 或用户的带宽/请求占比，实现多租户隔离。

## 2. 消费端限流（保护消费者与下游）

Kafka 是 pull 模型，消费端限流的本质是“你决定拉多少、多久拉一次、拉到后怎么处理”。

### 2.1 限流的三个控制面

1. **控制单次拉取规模**：限制一次 poll 的记录数与字节数，降低内存峰值与单次处理时间。

2. **控制处理并发**：线程池、队列长度、批处理策略决定了消费者实际吞吐。

3. **控制分区推进节奏**：通过 `pause/resume` 形成反压，避免依赖崩溃时失败风暴。

### 2.2 常见消费端参数（抓住“别把 poll 卡死”）

| 参数 | 作用 | 典型风险 |
| --- | --- | --- |
| `max.poll.records` | 单次 poll 返回的最大记录数 | 太大导致单次处理过久，触发 Rebalance |
| `max.poll.interval.ms` | 允许两次 poll 的最大间隔 | 业务线程阻塞会被踢出组 |
| `fetch.max.bytes` | 单次拉取的总字节上限 | 太大导致内存峰值与 GC 抖动 |
| `max.partition.fetch.bytes` | 单分区拉取字节上限 | 热分区会顶满内存或拖慢 |
| `fetch.min.bytes`、`fetch.max.wait.ms` | 批量拉取与等待 | 影响吞吐与延迟的权衡 |

### 2.3 `pause/resume`：最实用的消费反压手段

当下游（例如数据库）不可用时，常见处理是：

- 检测到失败后对分区执行 `pause`，避免继续拉取新消息。
- 以退避策略探测下游恢复，恢复后 `resume`。

工程注意点：

- 暂停分区会导致 lag 增长，需要结合 retention 评估“最坏恢复窗口”。
- 如果业务线程阻塞导致 poll 不及时，可能触发 Rebalance，因此“处理线程与 poll 线程解耦”很重要。

## 3. 生产端限流（保护 Broker 与网络）

生产端限流的目标通常是两件事：

1. 不让写入速率超过 Broker 的磁盘与复制能力。
2. 不让消息洪峰把下游消费系统打爆（削峰填谷）。

### 3.1 Producer 端的“反压点”

Producer 常见的节流点来自客户端自身：

- **批量发送**：通过 `linger.ms`、`batch.size` 聚合消息提升吞吐，同时降低网络包数。
- **缓冲区**：`buffer.memory` 决定客户端缓冲上限，满了之后 `send()` 会阻塞或失败（受 `max.block.ms` 控制）。
- **超时与重试**：`delivery.timeout.ms`、`request.timeout.ms` 等决定失败可感知的窗口，过载时要能快速失败或降速。

### 3.2 常见生产端参数（抓住“别无限堆积”）

| 参数 | 作用 | 典型风险 |
| --- | --- | --- |
| `buffer.memory`、`max.block.ms` | 缓冲与阻塞 | 缓冲满导致线程卡死或请求风暴 |
| `linger.ms`、`batch.size` | 批量聚合 | 批量越大吞吐越高，延迟可能升高 |
| `compression.type` | 压缩策略 | CPU 与带宽的权衡 |
| `acks`、`retries` | 可靠性与重试 | 过度重试可能放大过载 |

## 4. Broker 端限流（配额与节流）

Kafka Broker 常见提供配额（quota），以限制某个 client 或用户的吞吐与请求占比，避免单个业务抢占集群资源。

### 4.1 Broker 端限流的典型目标

- 多租户隔离：不同业务线互不影响。
- 故障隔离：异常客户端无法拖垮整个集群。
- 资源保护：避免磁盘、网络、请求线程池被打满。

### 4.2 你需要记住的工程结论

- **限流不是为了“更快”，而是为了“可控”**。
- 限流策略必须与告警联动，否则只会把问题从“崩溃”变成“悄悄变慢”。

## 5. 常见策略组合（建议落地顺序）

1. **先做消费端反压**：最终压力往往落在数据库与 RPC 下游。

2. **再做生产端削峰**：入口处的限流比末端止血更有效。

3. **最后用 Broker 配额兜底**：作为集群级安全阀，防止异常 client 抢占资源。
