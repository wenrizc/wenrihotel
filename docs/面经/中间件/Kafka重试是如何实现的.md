## 1. Kafka “重试”的本质：重试的是处理，不是 Broker 投递

Kafka 没有 RabbitMQ 那种 broker 侧 `nack + requeue + TTL + DLX` 的标准重试链路。Kafka 的重试通常是消费端语义，本质上只有两类动作：

1. **控制 offset 是否推进**：不提交意味着“我还没确认”，故障或 Rebalance 后会重读。
2. **把消息转移到另一个 Topic**：用重试 Topic 或 DLT 承载失败消息的后续治理。

因此“Kafka 重试怎么实现”的核心是：你要选择“阻塞主分区推进”还是“旁路重试并继续推进”。

## 2. 先做分类：哪些错误应该重试

### 2.1 可恢复错误（适合重试）

- 下游超时、网络抖动、连接池短暂耗尽。
- 依赖服务短暂不可用。

### 2.2 不可恢复错误（不应无限重试）

- 反序列化失败、schema 不兼容。
- 参数缺失、业务校验失败、状态机非法迁移。
- 明确的数据问题，重试不会改变输入。

工程结论：

- **把不可恢复错误尽快进入 DLT**，否则会造成分区阻塞与堆积。

## 3. 常见重试方式（从简单到可治理）

### 3.1 消费者端本地重试（同步重试）

做法：

- 同一次消费回调里捕获异常，做有限次数重试与退避，超过次数后进入 DLT 或落库。

优点：

- 实现简单，不需要额外 Topic。

缺点：

- 重试会阻塞该分区的消费线程，容易放大积压。
- 应用重启会丢失重试状态。

适用：

- 退避很短、错误很“瞬时”的场景。

### 3.2 Seek 重试（回退 offset 重试同一条消息）

做法：

- 处理失败后，通过 `seek` 把分区 offset 回退到当前消息，再次尝试处理。

优点：

- 不需要额外 Topic，语义直观。

缺点：

- 本质仍是“原地重试”，会阻塞分区推进。
- 如果是毒丸消息，会无限卡住。

工程建议：

- Seek 重试一般只用于“短暂瞬时错误”的有限次快速重试，最终仍应进入 DLT。

### 3.3 不提交 offset，让消息自然重读（原地重读）

做法：

- 失败时不提交 offset，重启或 Rebalance 后从旧 offset 再读。

优点：

- 简单且可靠，消息不会被你主动跳过。

缺点：

- 失败风暴时会放大 Rebalance 与重复范围。
- 毒丸消息会卡住分区。

### 3.4 重试 Topic（推荐）：主 Topic + 多级重试 Topic + DLT

这是更常见、更可治理的工程方案。

基本思路：

1. 主 `Topic` 消费失败时，不在主分区阻塞。
2. 把消息投递到重试 `Topic`，并携带 `x-retry-count`、`x-next-at` 等 headers。
3. 重试 `Topic` 的消费者在“到期”后再转发回主 `Topic` 或更长延迟的重试 `Topic`。
4. 超过最大重试次数后进入 DLT。

关键设计点：

- 不要在分区里 sleep 等待重试。
- 重试必须是有限次，否则必然把系统拖入堆积。
- 需要在 DLT 中保留原始 `topic/partition/offset` 与异常摘要，便于排查与回放。

## 4. 延迟重试的两种常见建模

### 4.1 多级固定延迟 Topic

示例：

- `pay.retry.5s`
- `pay.retry.1m`
- `pay.retry.10m`

优点：

- 规则清晰，易观测。

缺点：

- Topic 数量增加，需要规范化命名与治理。

### 4.2 指数退避（基于 headers 的下一次执行时间）

做法：

- 每次失败计算下一次时间，写入 header `x-next-at`。
- 重试消费者读取后，如果未到期则转存到“更长延迟”的 Topic 或落入调度系统。

工程注意：

- Kafka 本身不是定时器，最终仍要有“调度/到期判断”的组件。

## 5. 重试与顺序性的关系（分区视角）

Kafka 的顺序保证是“分区内有序”，因此重试需要考虑两个问题：

1. 是否允许后续消息先于失败消息被处理。
2. 是否允许同一业务主键并行处理。

常见权衡：

- 若要求严格顺序，失败消息往往要阻塞同分区推进（代价是吞吐下降）。
- 若允许乱序，可把失败消息旁路到重试 Topic，让主链路继续推进（代价是业务需要能处理乱序）。

## 6. 与“可靠性”绑定的底线：DLT 与回放闭环

重试不是可靠性的终点。一个可交付系统需要：

- DLT：最终失败隔离。
- 监控：重试速率、DLT 写入量、消费 lag。
- 回放：人工修复后可把消息重新投递回主 Topic。
- 幂等：保证重复消费不会产生副作用。

## 7. 方案对比表

| 方案 | 是否阻塞分区 | 复杂度 | 可靠性闭环 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| 本地同步重试 | 是 | 低 | 弱 | 瞬时错误、退避很短 |
| Seek 重试 | 是 | 中 | 弱 | 少量快速重试 |
| 不提交 offset 重读 | 是 | 低 | 中 | 失败率低、可快速修复 |
| 重试 Topic + DLT | 否（主链路） | 高 | 强 | 中大型系统标准解法 |
