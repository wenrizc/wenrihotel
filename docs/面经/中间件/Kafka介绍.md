## 1. Kafka 是什么：一句话抓住定位

Kafka（Apache Kafka）常被描述为“消息队列”，但它更贴近 **事件流平台（event streaming platform）**：把消息当成可持久化的追加写日志（commit log），支持高吞吐写入、多下游订阅、按 offset 回放历史。

- Kafka 的核心抽象是 `Topic` 的 `Partition`（分区日志）。
- Kafka 的核心能力是“持久化 + 可回放 + 多订阅”，而不是“复杂路由”。

## 2. 数据模型与基本语义

### 2.1 Record（消息）与字段

一条消息常见要素：

- `key`：决定分区选择的重要输入，也是“同一业务主键尽量落同一分区”的基础。
- `value`：业务负载。
- `timestamp`：用于时间语义与保留策略等（具体由生产端与 Broker 配置共同决定）。
- `headers`：承载重试次数、追踪信息、错误原因等元数据。

### 2.2 Topic 与 Partition：Kafka 的“队列语义”从哪里来

- `Topic` 是逻辑分类。
- `Partition` 是物理切分，且每个分区是一条 **追加写（append-only）的有序日志**。

Kafka 的“队列语义”通常通过 `Topic` + `Consumer Group` 表达：

- 同一消费组内，一个分区同一时刻只分配给一个消费者实例，达到“队列式负载均衡”。
- 不同消费组互不影响，达到“发布订阅式多下游订阅”。

### 2.3 顺序性：只在分区内成立

Kafka 的顺序保证通常是：

- **同一分区内有序**。
- **跨分区不保证全局有序**。

工程上想要“同一业务主键严格有序”，常用做法是：

- 以业务主键作为 `key`，保证同一 `key` 落到同一分区。

### 2.4 Offset：Kafka 的“确认语义”

Kafka 没有 RabbitMQ 那种协议级 `ack/nack`，Kafka 的“确认语义”主要体现在 **提交 offset**：

- 提交 offset：语义上表示“我确认已经处理到这里”。
- 未提交 offset：崩溃后可能从旧 offset 重读，形成 **重复消费（至少一次）**。

## 3. 集群与副本：为什么 Kafka 能抗单机故障

### 3.1 Broker、Leader、Follower

- `Broker`：Kafka 服务端节点。
- 对每个分区：
  - `Leader` 负责处理该分区的读写请求。
  - `Follower` 从 `Leader` 复制数据并保持一致。

### 3.2 ISR（In-Sync Replicas）：写入成功的“门槛”

`ISR` 是与 `Leader` 保持同步的一组副本集合。生产端使用 `acks=all` 时，通常意味着：

- 写入只有在满足 ISR 确认条件时才返回成功。

配合 `min.insync.replicas`，可以把“副本不足”变成可感知失败，避免“只剩一个副本仍返回成功”导致的隐性丢失风险。

### 3.3 控制面：谁来做选举与元数据管理

Kafka 需要一个控制面来管理：

- 分区副本分配与 `Leader` 选举。
- 集群元数据（topic、分区、副本、ACL 等）。

历史上常见是 ZooKeeper 方案；新版本逐步演进到 KRaft（Kafka 自己的元数据一致性机制）。

## 4. 写入链路：Producer 做了哪些事

### 4.1 分区选择：Partitioner

Producer 写入时要先决定目标分区：

- 指定 `key`：通常基于 `key` 的哈希选择分区，保证同一 `key` 的顺序性。
- 未指定 `key`：常见是轮询或粘性分区（具体策略随客户端实现变化）。

### 4.2 批量、压缩与吞吐

Kafka 的高吞吐通常来自“批量化”：

- Producer 会把多条消息聚合成批次再发送。
- 支持压缩（例如 `lz4`、`zstd` 等）以用 CPU 换网络与磁盘。

工程权衡：

- 批量与压缩会提升吞吐，但可能增加端到端延迟。

### 4.3 `acks`、幂等与事务：可靠性三件套

1. `acks` 决定“写入成功”的确认门槛：

- `acks=0`：不等确认，风险最高。
- `acks=1`：只等 `Leader` 确认，`Leader` 故障窗口可能丢。
- `acks=all`：等待 ISR 确认，可靠性更高。

2. 幂等生产者（`enable.idempotence=true`）用于降低重试导致的重复写入风险。

3. 事务用于把“多次写入”绑定成一个原子单元，并与消费端配合实现更强语义（代价是复杂度与吞吐下降）。

### 4.4 常用生产端参数

| 参数 | 影响 | 典型取舍 |
| --- | --- | --- |
| `acks` | 可靠性与延迟 | `all` 更可靠但更慢 |
| `retries`、`delivery.timeout.ms` | 重试窗口 | 太小容易误判失败，太大可能堆积 |
| `linger.ms`、`batch.size` | 批量与吞吐 | 批量越大吞吐越高，延迟可能增加 |
| `compression.type` | 网络与磁盘 | 压缩省带宽但耗 CPU |
| `max.in.flight.requests.per.connection` | 并发与有序 | 幂等场景通常更谨慎配置 |

## 5. 读取链路：Consumer 做了哪些事

### 5.1 Pull 模型：poll 循环

Consumer 通常以“poll 循环”拉取数据：

1. 向 Broker 拉取分区数据（fetch）。
2. 本地反序列化并交给业务处理。
3. 在合适时机提交 offset。

### 5.2 Consumer Group 与 Rebalance

消费组机制提供两类能力：

- 负载均衡：分区在组内成员之间分配。
- 故障转移：成员退出或崩溃后触发 Rebalance，分区转移给其他成员。

Rebalance 的工程含义：

- 业务处理太慢导致 poll 不及时，可能触发“被认为失活”，从而 Rebalance。
- Rebalance 期间分区会短暂停止推进，延迟会上升。

### 5.3 offset 提交与交付语义

交付语义由“处理与提交顺序”决定：

- 先提交、后处理：更接近“至多一次”，可能丢。
- 先处理、后提交：更接近“至少一次”，可能重复。

因此 Kafka 侧的可靠性通常以“至少一次 + 业务幂等”落地。

### 5.4 常用消费端参数

| 参数 | 影响 | 常见坑 |
| --- | --- | --- |
| `enable.auto.commit` | 是否自动提交 offset | 自动提交容易与业务处理脱钩 |
| `max.poll.records` | 单次 poll 数量 | 太大导致单次处理过久 |
| `max.poll.interval.ms` | 处理超时阈值 | 业务处理阻塞会触发 Rebalance |
| `session.timeout.ms`、`heartbeat.interval.ms` | 心跳与失活判定 | 配置不当导致频繁 Rebalance |

## 6. 交付语义：至少一次、至多一次、精确一次

### 6.1 至少一次（最常见）

- 处理成功后提交 offset。
- 允许重复，靠业务幂等兜底。

### 6.2 至多一次（少见）

- 先提交 offset，再处理。
- 更少重复，但容忍丢失。

### 6.3 精确一次（Exactly Once Semantics，EOS）

Kafka 的“精确一次”通常指在特定前提下实现更强语义，例如：

- 幂等生产者降低重复写入。
- 事务把“消费位移提交 + 下游写入（通常是写 Kafka）”绑定成一个原子单元。

工程上要先把问题说清楚：

- 你要保证的“精确一次”是“写 Kafka 精确一次”，还是“写数据库精确一次”。
- 写数据库通常仍需要幂等键、去重表、Outbox 等方案配合。

## 7. 适用场景与不适用场景

### 7.1 适用场景

- 日志采集、埋点、指标流：高吞吐写入与回放。
- 事件驱动架构：多下游订阅、可重放、可追溯。
- 数据管道与流处理：与连接器、流计算生态配合。

### 7.2 不适用场景

- 需要 broker 侧复杂路由（交换机、路由键）且希望开箱即用的场景。
- 需要严格全局顺序但又要求高吞吐的场景。
- 业务无法接受重复且又不愿做幂等治理的场景。
