## 1. 传统分页（LIMIT/OFFSET）的问题

最常见的分页写法是：

```sql
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10 OFFSET 1000;
```

它的问题主要集中在两类：性能与一致性。

### 1.1 深分页性能退化

`OFFSET` 越大，数据库需要“跳过”的行越多，即使最终只返回 10 行，也可能扫描/排序大量数据，导致：

- 扫描行数随页码线性增长。
- 排序成本增大（尤其是需要 filesort 时）。
- 延迟抖动明显，缓存命中率下降。

### 1.2 数据漂移（分页不稳定）

分页过程中如果有插入/删除/更新，后续页可能出现：

- 重复数据（上一页末尾的数据又出现在下一页）。
- 漏数据（某些数据被“挤走”）。

## 2. 改进一：基于游标的分页（Keyset / Cursor Pagination）

为了解决深分页的性能问题，基于游标的分页（也叫键集分页）会用一个“锚点”来定位下一页起点，而不是用页码与偏移量。

游标通常是**有序且能唯一定位的列**：自增 ID、时间戳 + ID 组合等。

### 2.1 实现原理：把 `OFFSET` 变成 `WHERE`

假设按 `created_at` 降序排列，每页 10 条：

- 第一页：正常查询，记录最后一条的 `created_at`（作为游标）。
- 下一页：用游标作为边界条件。

```sql
SELECT * FROM orders
WHERE created_at < '2025-09-01 10:00:00'
ORDER BY created_at DESC
LIMIT 10;
```

### 2.2 处理游标非唯一：用复合游标

如果 `created_at` 可能重复，必须加上唯一列（如 `id`）保证分页稳定：

```sql
SELECT * FROM orders
WHERE (created_at, id) < ('2025-09-01 10:00:00', 12345)
ORDER BY created_at DESC, id DESC
LIMIT 10;
```

### 2.3 优势与局限

- 优势：性能稳定（不随页码增长），且分页更稳定。
- 局限：无法直接跳到任意页（只能顺序翻页），实现需要传递游标。

## 3. 改进二：延迟关联（Deferred Join）与覆盖索引

当查询列很多、回表成本高时，可以先在索引上拿到一页的主键，再回表取全量字段：

```sql
SELECT o.*
FROM orders o
JOIN (
    SELECT id
    FROM orders
    WHERE created_at < '2025-09-01 10:00:00'
    ORDER BY created_at DESC, id DESC
    LIMIT 10
) t ON o.id = t.id
ORDER BY o.created_at DESC, o.id DESC;
```

这类写法的关键是：子查询尽量走覆盖索引，把“排序 + 分页”的成本压到索引层完成。

## 4. 选型建议

- 页码小、业务允许轻微漂移：`LIMIT/OFFSET` 够用，但要配索引与限制最大页码。
- 无限滚动、深分页、稳定分页：优先 Keyset/Cursor Pagination。
- 查询字段多、回表贵：用延迟关联或覆盖索引做二段查询。
