## 1. 索引是什么：目标与代价

索引（Index）是数据库在“表数据”之外维护的一份辅助结构，用来把 `key` 映射到数据行（或数据页、元组）的定位信息，从而让查询少扫数据、少做比较。

索引的核心价值是：**用空间和写入成本换查询性能**。因此“建不建索引、用不用索引”永远是一个成本问题，而不是一个语法问题。

- 加速的典型操作：`WHERE` 过滤、`JOIN` 连接、`ORDER BY` 排序、`GROUP BY` 分组、`DISTINCT` 去重。
- 付出的典型代价：额外存储、`INSERT/UPDATE/DELETE` 写放大、维护统计信息、构建/重建索引的 DDL 成本、可能更复杂的锁竞争。

### 1.1 为什么索引不是“越多越好”

每增加一个索引，意味着每次写入都要额外维护一棵（或多棵）索引结构；同时，索引会占用更多内存缓存与磁盘空间，降低缓存命中率。

更重要的是，索引会影响执行计划：索引越多，优化器需要评估的候选路径越多，且统计信息不准确时更容易选错索引，导致“加了索引反而变慢”。

## 2. 一条索引记录到底存了什么

从抽象上看，索引条目（Index Entry）通常由两部分组成：**索引键（Key）** 与 **行定位（Row Locator）**。不同数据库、不同存储引擎的差异，主要体现在“定位”到底是什么。

### 2.1 索引键（Key）

索引键可以是单列或多列（联合索引）。在联合索引中，键的比较顺序按列顺序逐列比较，这直接决定了“最左前缀”与能否利用索引完成排序。

- 单列索引：按一个列值排序或散列。
- 联合索引：按 `(c1, c2, c3, ...)` 的字典序排序（或按该组合做散列）。

### 2.2 行定位（Row Locator）

行定位用于把“命中的索引键”映射到“真正的数据”。常见形态如下（概念层面）：

- **聚簇组织（Clustered）**：索引叶子节点直接存放整行数据（或行数据的主要部分），索引与数据同组织。
- **堆表（Heap）**：索引叶子节点存放一个行标识（如 `RID/TID`）或物理指针，需再去堆里取行。
- **二级索引回表（以 MySQL InnoDB 为例）**：二级索引叶子节点存放主键值（而非物理地址），再用主键去聚簇索引取整行，这个过程称为“回表”。

### 2.3 有序性、页（Page）与 I/O

对磁盘型数据库来说，真正昂贵的通常不是一次比较，而是一次随机 I/O。主流 OLTP 引擎会把索引节点设计成“页”（Page），一次 I/O 读入一个页，在页内再做二分或目录查找。

这也是为什么“有序索引”（如 B+ 树）能同时擅长等值、范围与排序：它能把随机 I/O 次数压到很低，并把叶子页串成顺序扫描友好的结构。

## 3. 按底层数据结构：索引的物理形态

不同索引结构并不是“谁更高级”，而是针对不同访问模式（等值、范围、多维、全文、聚合）做的工程取舍。

| 结构 | 是否有序 | 擅长 | 不擅长 | 常见场景 |
| --- | --- | --- | --- | --- |
| B-Tree / B+Tree | 有序 | 等值、范围、排序、前缀匹配 | 写入随机性强时页分裂成本高 | OLTP 通用索引 |
| Hash | 无序 | 等值查询（`=`、`IN`） | 范围、排序、前缀 | 纯 KV、内存引擎 |
| Bitmap | 位集合 | 多条件组合过滤（AND/OR） | 高频更新、OLTP 写入 | 数仓、低基数维度 |
| 倒排索引（Inverted） | term 有序 | 全文检索、成员包含 | 范围/排序（按数值意义） | 搜索、日志、文本 |
| 空间索引（R-Tree 等） | 空间层次 | 多维范围、邻近查询 | 单维全序排序 | GIS、地理位置 |
| LSM-Tree 体系 | 有序（SSTable） | 高写入吞吐、顺序写 | Compaction 成本、读放大 | NoSQL、写密集 |
| 列式 / Columnstore | 列内编码 | 扫描聚合、数据跳过 | 点查、频繁更新 | OLAP、分析型负载 |

### 3.1 B-Tree / B+Tree 索引

在数据库语境里，“B-Tree 索引”往往实际指的就是 B+ 树实现：非叶子节点存放分隔键与子指针，叶子节点存放（有序的）键与行定位，并且叶子节点通常有链式指针用于范围扫描。

#### 3.1.1 为什么 B+ 树适合磁盘

B+ 树是多路平衡搜索树，关键在于“扇出（fan-out）”很大：一个索引页能容纳很多键和指针，因此树高通常很低。

- 树高低：一次查询需要的页访问次数少，随机 I/O 被控制在很小范围。
- 叶子有序：天然支持 `BETWEEN`、`>=`、`ORDER BY`、`MIN/MAX` 等操作。
- 叶子链表：范围扫描更接近顺序 I/O，吞吐更稳定。

#### 3.1.2 聚簇索引与二级索引（以 MySQL InnoDB 为例）

InnoDB 的聚簇索引（Clustered Index）以主键为组织方式，**叶子节点存放整行数据**；二级索引（Secondary Index）的叶子节点存放二级键 + 主键值。

因此通过二级索引取非索引列时会发生“回表”：先命中二级索引，再按主键去聚簇索引取整行。工程上最重要的推论是：

- **主键越长，所有二级索引都会变大**（因为二级索引叶子要存主键）。
- 能覆盖就覆盖：让查询需要的列尽量落在同一个二级索引记录里，减少回表随机 I/O。

### 3.2 Hash 索引

Hash 索引通过 `hash(key)` 把键映射到桶（bucket），平均情况下等值查询接近 O(1)。但它不保序，因此天然不支持范围与排序。

- 适用：`=`、`IN` 这类等值点查，且数据常驻内存或热点明显。
- 局限：`ORDER BY`、`BETWEEN`、按前缀匹配（如 `LIKE 'abc%'`）无法直接受益。

补充：部分引擎会在 B+ 树之上对热点页构建“自适应 Hash 索引”（如 InnoDB 的 Adaptive Hash Index），但这通常是内部优化手段，并非用户显式创建的索引类型。

### 3.3 Bitmap 索引

Bitmap 索引用位图表示“某个取值对应哪些行”。当列的基数（Cardinality）很低时，位图非常紧凑，并且可以用位运算高效组合多个条件。

- 适用：读多写少的分析型负载、低基数字段（如 `gender`、`status`）的多条件组合过滤。
- 局限：频繁更新会导致大量位图块被改写，且容易产生写入竞争，因此不适合作为高并发 OLTP 的常规索引。

### 3.4 倒排索引（Inverted Index，全文检索）

倒排索引从“行 -> 词”反过来组织为“词 -> 行列表”。典型结构是：词典（term dictionary）+ 倒排表（posting list）。

- 适用：全文检索（关键词、短语、相关性评分）、数组/JSON 成员包含检索（不同数据库实现不同）。
- 局限：对数值意义的范围与排序支持有限，且需要分词、停用词、归一化等文本处理策略。

工程上，如果需求是复杂搜索（相关性、分词、多字段权重），往往会采用专用搜索引擎（如基于 Lucene 的体系）而不是只靠关系型数据库的全文索引。

### 3.5 空间索引（R-Tree 等）

空间索引用于多维数据（经纬度、几何对象）。R-Tree 通过层次化的最小外接矩形（MBR）组织空间对象，擅长处理“相交、包含、邻近”等空间谓词。

- 适用：`ST_Within`、`ST_Intersects`、最近邻（KNN）等空间查询。
- 局限：空间对象并不存在天然的一维全序，因此无法像 B+ 树那样直接支持通用排序。

### 3.6 LSM-Tree 体系（写优化索引/存储）

LSM-Tree（Log-Structured Merge Tree）用“顺序写 + 后台合并”换取高写入吞吐：写入先落内存结构（memtable）与日志（WAL），再刷盘为有序的 SSTable，后台 compaction 合并多个 SSTable。

- 适用：写入密集、可接受后台合并开销的场景（常见于 RocksDB、LevelDB、HBase、Cassandra 等）。
- 局限：读路径可能需要查询多个层级并做合并，存在读放大；compaction 会带来写放大与资源抖动，需要工程治理。

### 3.7 列式索引 / Columnstore（分析型）

列式存储按列组织数据，天然适合扫描与聚合（`SUM/COUNT/GROUP BY`），并且更容易做高压缩与向量化执行。很多系统会维护“分段元数据”（如 min/max、字典）用于数据跳过（data skipping）。

- 适用：大宽表扫描、聚合统计、典型 OLAP 工作负载。
- 局限：点查与频繁更新成本高，通常不适合高并发小事务 OLTP。

### 3.8 可扩展索引族（以 PostgreSQL 为例）

部分数据库提供“可扩展索引框架”，允许针对不同数据类型与操作符选择不同索引实现。

- `GIN`：类似倒排索引，适合数组、`jsonb`、全文等“一个值对应多个键”的场景。
- `GiST`：通用搜索树框架，常用于几何、范围类型与近邻查询。
- `BRIN`：按块范围做摘要（如每段块的 min/max），极小索引体积，适合与物理顺序高度相关的超大表（如按时间插入）。

## 4. 按逻辑语义：你在 DDL 里创建的索引类型

“逻辑类型”回答的是：这个索引在业务/约束上扮演什么角色；它最终可以由不同的物理结构实现（最常见仍是 B+ 树）。

### 4.1 主键索引、唯一索引、普通索引

- 主键索引：用于唯一标识一行，通常伴随 `NOT NULL` 语义（不同数据库对实现细节略有差异）。
- 唯一索引：保证索引键不重复（不同数据库对 `NULL` 的唯一性规则可能不同）。
- 普通索引：只提供加速，不提供唯一性约束。

### 4.2 聚簇索引与二级索引（Clustered / Secondary）

聚簇索引决定了“数据行按什么顺序物理组织”。一个表通常只能有一个聚簇组织方式：

- 聚簇索引优点：按聚簇键范围查询更顺序、更少回表；局部性更好。
- 聚簇索引代价：聚簇键变更会引发大规模移动；聚簇键设计不当（过长、随机）会放大页分裂与二级索引体积。

以 InnoDB 为例，主键就是聚簇索引的组织键；因此主键的工程选择非常关键，常见建议是：**短、稳定、尽量单调递增**。

### 4.3 联合索引与最左前缀

联合索引 `idx(a, b, c)` 的本质是按 `(a, b, c)` 的字典序排序，因此它天然支持：

- `a = ?`、`a = ? AND b = ?`、`a = ? AND b = ? AND c = ?`。
- `a` 的范围扫描（如 `a BETWEEN ...`），以及在满足前缀条件下的排序（如 `ORDER BY a, b`）。

一条常用工程口诀是：**等值列放前面，范围列放后面；排序/分组需求要匹配索引顺序**。一旦在中间列出现范围条件，后续列通常无法继续缩小扫描范围（但可能仍可用于过滤，视优化器与引擎能力而定）。

```sql
-- 典型查询：按用户查最近订单
-- WHERE user_id = ? ORDER BY created_at DESC LIMIT 20
CREATE INDEX idx_orders_user_created_at ON t_orders(user_id, created_at);
```

### 4.4 覆盖索引与回表

覆盖索引（Covering Index）指查询所需的列（`SELECT` + 过滤条件 + 排序/分组列）都能从同一个索引记录中取得，从而避免回表。

- 好处：少一次随机 I/O（甚至多次），延迟和吞吐往往都有明显收益。
- 代价：索引变“宽”，写入与存储成本上升，需要权衡。

```sql
-- 覆盖索引示例：让查询只读索引页
CREATE INDEX idx_orders_user_created_status ON t_orders(user_id, created_at, status);

SELECT status
FROM t_orders
WHERE user_id = 1 AND created_at >= '2026-01-01'
ORDER BY created_at
LIMIT 20;
```

### 4.5 前缀索引、包含列（INCLUDE）与“宽索引”

长字符串字段（如 `email`、`url`）直接建全长索引会导致索引巨大。常见优化手段：

- 前缀索引：只索引字符串前 N 个字符（MySQL 支持），用更小的索引换取部分选择性。
- 包含列（`INCLUDE`）：部分数据库允许把“非排序键列”作为 payload 放入索引叶子，用于覆盖查询而不影响索引排序键（如 PostgreSQL、SQL Server）。

前缀索引需要特别注意：N 过小会导致选择性差、扫描行数暴涨；N 过大又接近全长索引，收益有限。

```sql
-- MySQL 前缀索引示例：只索引 email 前 10 个字符
CREATE INDEX idx_user_email_prefix ON t_user(email(10));
```

### 4.6 函数 / 表达式索引、生成列索引

当查询条件对列做了计算（如 `lower(email)`、`date(created_at)`），普通索引往往无法直接利用。解决方式是让“被查询的表达式”本身可被索引。

- 表达式索引：直接对表达式建索引（部分数据库支持）。
- 生成列索引：通过生成列把表达式结果落到表里，再对生成列建索引（MySQL 常用做法）。

```sql
-- MySQL 生成列索引：把 lower(email) 物化后再建索引
ALTER TABLE t_user
  ADD COLUMN email_lc varchar(255) GENERATED ALWAYS AS (lower(email)) STORED,
  ADD INDEX idx_user_email_lc(email_lc);
```

### 4.7 部分索引 / 过滤索引（Partial / Filtered）

如果某类查询只关心表的一小部分行（如“未删除”“状态为 ACTIVE”），对全表建索引会浪费空间且增加写入负担。部分索引通过谓词只覆盖满足条件的行，显著缩小索引体积。

```sql
-- PostgreSQL/SQL Server 等支持“带谓词的索引”（语法示意）
-- CREATE INDEX idx_user_active ON t_user(id) WHERE status = 'ACTIVE';
```

## 5. 优化器如何使用索引

索引能不能用上，取决于优化器是否能把你的查询转成“某种访问路径”，并且该路径在代价模型下更便宜。

### 5.1 常见访问路径（Access Path）

- 点查（Index Seek）：通过等值条件快速定位到少量行。
- 范围扫描（Range Scan）：通过范围条件扫描索引的一个连续区间。
- 索引全扫（Index Full Scan）：扫描整棵索引（有时比扫表更便宜，例如索引更窄）。
- 仅索引扫描（Index Only / Covering）：无需回表，直接从索引返回结果。

部分数据库还会使用索引合并（Index Merge）、跳跃扫描（Skip Scan）等策略，但它们往往是“补救”方案，是否生效依赖数据分布与优化器能力。

### 5.2 什么条件“可索引”（Sargable）

可索引化（Sargable）指谓词能够直接形成“对索引有序键的约束”，从而把扫描范围收敛到很小。典型反例是对列做函数/计算，导致索引失去可用的有序边界。

```sql
-- 反例：对列做函数，往往无法使用 created_at 上的普通索引
SELECT * FROM t_orders WHERE date(created_at) = '2026-01-25';

-- 改写：用范围表达同一含义，让 B+ 树能做范围裁剪
SELECT * FROM t_orders
WHERE created_at >= '2026-01-25' AND created_at < '2026-01-26';
```

### 5.3 排序与分组：什么时候能避免额外排序

如果 `ORDER BY` / `GROUP BY` 的列序与方向和索引一致，并且过滤条件不会破坏索引顺序（例如在中间列做了不匹配的范围裁剪），数据库就可能利用索引的天然有序性避免额外排序。

在 MySQL 中，这类问题通常会体现在 `EXPLAIN` 的 `Extra` 字段里是否出现 `Using filesort`；更详细的排查可结合本目录的 `explain介绍.md`。

### 5.4 Join 与索引：谁是“内表”

最常见的 Join 执行方式之一是 Nested Loop：外表逐行驱动内表，通过内表的连接键索引做点查/范围查。

工程经验是：**为高选择性的连接键建索引**（如外键列、关联字段），并尽量让“内表访问”变成点查或小范围扫描。

## 6. 建索引的工程原则

### 6.1 从查询出发，而不是从字段出发

先看“线上最贵的 SQL”在做什么，再决定索引怎么建。一个能落地的流程通常是：

1. 从慢查询日志/监控找到 Top N 查询与其过滤、排序、Join 列。
2. 设计候选索引（含联合顺序、是否覆盖）。
3. 用 `EXPLAIN` 验证访问路径与扫描行数，评估回表成本。
4. 评估写入代价与索引体积，上线后持续观察。

### 6.2 联合索引列顺序的通用准则

- 等值过滤列优先（能最大幅度收敛扫描范围）。
- 范围列靠后（避免过早“范围截断”）。
- 排序/分组列要与索引顺序一致，才能更可能用索引消除排序。

### 6.3 控制数量：避免写放大与维护成本失控

- 每个索引都会增加写入路径的 I/O 与日志量，尤其在写密集场景里影响非常明显。
- 重复索引（例如 `idx(a)` 与 `idx(a, b)` 同时存在）通常应清理掉前者，除非有明确收益。

### 6.4 利用“不可见索引”做灰度验证（如果数据库支持）

部分数据库支持“不可见索引”（Invisible Index）：优化器默认不使用该索引，但索引仍会被维护。它适合在不影响线上执行计划的前提下验证“删索引是否安全”或“新索引是否值得启用”。

## 7. 常见坑与排查清单

- 只讲 B+ 树而忽略访问模式：等值点查、全文、多维、分析型负载对索引结构的要求完全不同。
- 主键设计不当：主键过长会放大二级索引体积；主键随机性强会增加页分裂与缓存失效率。
- 联合索引顺序错误：把低选择性列放最左，会让扫描范围过大；范围条件放太靠前会导致后续列无法裁剪范围。
- 谓词不可索引化：对列做函数/计算、隐式类型转换、`LIKE '%xxx'` 等会让索引失去边界。
- 只看“是否命中索引”不看“扫描行数”：命中索引但回表太多、过滤率太低，仍然可能比全表扫描慢。
- 统计信息过期：数据分布变化后未更新统计信息，优化器可能选错索引与 Join 顺序。
