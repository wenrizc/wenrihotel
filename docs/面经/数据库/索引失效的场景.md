## 1. 什么叫“索引失效”

工程里常说“索引失效”，通常指两种情况：

1. 优化器最终选择 **全表扫描** 或扫描量很大，看起来“没走索引”。
2. 走了索引但效果差：只用到了索引前导列、发生大量回表、`rows` 仍然很大。

判断是否真的失效，应以执行计划与实际扫描行数为准，而不是只看有没有 `key`。

## 2. 常见失效场景（按原因分类）

### 2.1 对索引列做函数/表达式计算

```sql
-- 可能无法利用 B+ 树索引的有序性
WHERE DATE(created_at) = '2026-01-01'
```

思路：把计算移到常量侧，或使用生成列/函数索引（视数据库能力而定）。

### 2.2 前缀模糊匹配

```sql
WHERE name LIKE '%abc'
```

因为 B+ 树按前缀有序，`%` 在前会破坏有序性；可考虑倒排、全文索引或改成前缀匹配。

### 2.3 隐式类型转换

```sql
-- user_id 是 varchar，但用数字比较可能触发隐式转换
WHERE user_id = 123
```

隐式转换可能导致索引无法有效使用。建议让两侧类型一致，并统一字符集/排序规则（collation）。

### 2.4 联合索引未遵循左前缀，或被范围条件截断

例如索引 `(a, b, c)`：

- 能用：`a=?`、`a=? AND b=?`、`a=? AND b>?`
- 易踩坑：`b=?`（跳过 a）、`a>? AND b=?`（范围在前会截断 b 的利用）

### 2.5 `OR`、`NOT` 条件带来的代价

- `OR` 两侧只有一侧可用索引时，优化器可能倾向全表扫描。
- `!=`、`NOT IN`、`NOT LIKE` 等条件往往选择性差，可能导致扫描行数过大。

### 2.6 回表成本太高导致放弃索引

即使条件能用索引，如果需要回表读取很多行，优化器可能认为“走索引不划算”，转而选择全表扫描。此时可以考虑覆盖索引或调整查询返回列。

## 3. 如何定位：执行计划与实际行数

建议形成固定流程：

1. `EXPLAIN` 看 `type/key/rows/Extra`。
2. 对关键 SQL 使用 `EXPLAIN ANALYZE`（若支持）看真实执行耗时与实际扫描行数。
3. 结合慢日志与统计信息，确认是否统计信息过旧导致选错计划。

## 4. 常用改写与优化手段

- 把“对列计算”改成“对常量计算”，让条件可走索引。
- 需要函数条件时，用生成列（落地结果）再建索引。
- 调整联合索引顺序：等值列优先，范围列靠后，兼顾 `ORDER BY`。
- 通过覆盖索引减少回表：只查必要列。
