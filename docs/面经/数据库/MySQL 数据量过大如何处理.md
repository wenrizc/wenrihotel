## 1. 问题拆解：什么叫“数据量过大”

“数据量过大”在 MySQL 里通常不是单一问题，而是以下瓶颈之一或组合：

- **容量瓶颈**：单表行数过大、单行过宽（大量 `TEXT` / `BLOB`）、索引膨胀、表空间增长不可控。
- **性能瓶颈**：查询走不了索引、排序与临时表爆炸、随机 I/O 过多、热点行锁竞争。
- **运维瓶颈**：备份恢复时间过长（RTO 变差）、DDL 变更风险高、归档清理困难。

因此处理策略也必须分层：先优化“单机单库”，再考虑“数据生命周期治理”，最后才是“水平扩展（分库分表）”。

## 2. 先把单表与查询压到合理区间（最低成本）

### 2.1 Schema 与索引：让数据更“薄”

常见工程做法：

- 用更小的数据类型：例如把 `BIGINT` 能降到 `INT` 就降，能用 `DATETIME(0)` 就别用更高精度。
- 避免大字段参与主链路：把 `TEXT` / `JSON` 等大字段拆到扩展表（主表保留必要列），降低二级索引回表成本。
- 索引遵循“最左前缀”和“覆盖优先”：高频查询优先做覆盖索引，避免回表。

### 2.2 SQL 治理：把慢查询变成可预测

落地流程（建议常态化）：

1. 开启并收敛慢查询：基于 `slow_query_log` 或 performance schema 采样。
2. 用 `EXPLAIN` 验证是否走到预期索引，关注 `type`、`rows`、`filtered`、`Extra`（是否 `Using filesort` / `Using temporary`）。
3. 对高频查询做“固定形态”：避免动态拼接导致的索引失效（隐式类型转换、函数包裹列等）。

示例：避免对列做函数导致索引失效。

```sql
-- 不推荐：对列做函数，可能无法使用索引
SELECT * FROM t_order WHERE DATE(create_time) = '2026-01-26';

-- 推荐：改为范围查询，可用 (create_time) 索引
SELECT * FROM t_order
WHERE create_time >= '2026-01-26 00:00:00'
  AND create_time <  '2026-01-27 00:00:00';
```

### 2.3 InnoDB 关键参数：把热数据尽量留在内存

大表场景下，最核心的是让热点页命中 `buffer pool`，减少随机 I/O。

| 目标 | 参数 / 机制 | 经验要点 |
| --- | --- | --- |
| 缓存热点页 | `innodb_buffer_pool_size` | 通常给到物理内存的 60%～75%（同机还跑别的服务要下调） |
| 提升刷盘稳定性 | `innodb_flush_method` | Linux 常见为 `O_DIRECT`（避免 double cache） |
| 控制刷盘节奏 | `innodb_io_capacity` | 与磁盘能力匹配，避免 checkpoint 积压 |

## 3. 数据生命周期治理：分区、归档、冷热分离

### 3.1 分区表：让“按时间裁剪”变成 O(1)

分区（partitioning）适合典型的时序数据：订单、日志、流水。关键收益是：

- 查询带分区键条件时可以 **partition pruning**，减少扫描范围。
- 清理历史数据可以 `DROP PARTITION`，近似瞬时完成，避免巨量 `DELETE` 带来的回滚段膨胀与锁等待。

实践要点：

- 分区键必须出现在关键查询条件里，否则分区收益有限。
- 分区不是分库：分区表仍在同一实例，热点与 I/O 上限依然受单机约束。

### 3.2 归档：把“历史”从 OLTP 里搬走

当业务存在明显的“近期热、历史冷”特征，推荐做归档：

- 线上库只保留近 N 天 / N 月热数据。
- 历史数据进入归档库（MySQL / ClickHouse / Hive / 对象存储），通过异步链路查询或离线报表获取。

清理策略对比：

| 方式 | 优点 | 风险 / 代价 | 适用场景 |
| --- | --- | --- | --- |
| `DROP PARTITION` | 快、对线上影响小 | 需要分区设计 | 按时间分区的历史清理 |
| 分批 `DELETE` | 灵活 | 产生大量 `undo`、锁时间长 | 小规模清理或无分区表 |
| 归档后 `TRUNCATE` / 重建表 | 彻底回收空间 | 需要停写或切换 | 大表重整、历史全迁移 |

## 4. 水平扩展：分库分表与读写分离（成本最高但上限最高）

### 4.1 读写分离：先扩读能力

在写压力可控、读压力先成为瓶颈时，优先考虑主从复制：

- 主库承接写与强一致读（必要时）。
- 从库扩展读 QPS。

注意点：

- 从库存在复制延迟：**读己之写**（read-your-writes）需求要么走主库，要么通过业务侧一致性策略（例如写后读路由主库一段时间）。

### 4.2 分库分表：解决容量与写上限

分库分表的目标是把单点容量与写入上限打散，典型做法：

- 按业务主键哈希分片：例如 `user_id`、`tenant_id`。
- 按时间分片：例如按月分库，配合归档策略。

工程关键点：

- 路由规则必须稳定：避免后续迁移成本失控。
- 全局唯一 ID：避免自增主键跨分片冲突（常用 Snowflake 类方案）。
- 跨分片查询与事务：要么避免，要么引入汇总表、异步聚合，谨慎使用分布式事务。

## 5. 大数据量下的运维能力：备份、恢复、DDL、空间治理

### 5.1 备份策略：逻辑备份 vs 物理备份

| 方式 | 工具形态 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 逻辑备份 | `mysqldump` | 可跨版本、可选择库表 | 大库很慢、恢复慢 | 中小规模、结构迁移 |
| 物理备份 | 物理拷贝 / 热备工具 | 快、恢复快 | 环境依赖强 | 大库、强 RTO 需求 |

实践建议：

- 大库优先“物理全量 + binlog 增量（PITR）”，把 RPO 与 RTO 可控化。
- 定期演练恢复：不要把“能备份”当成“能恢复”。

### 5.2 在线 DDL：避免长时间锁表

大表修改列、加索引属于高风险操作。原则：

- 优先使用 InnoDB 原生 Online DDL 能力（不同版本支持程度不同）。
- 需要更强控制时，使用在线变更工具（例如 `pt-online-schema-change`、`gh-ost` 的思路是影子表 + 增量同步 + 切换）。

### 5.3 空间回收：为什么 `DELETE` 后磁盘不降

InnoDB 的空间回收常见现象：

- `DELETE` 只标记记录删除，页内会出现空洞，但 `.ibd` 文件未必立刻缩小。
- 想显著回收空间，通常需要重建表（`OPTIMIZE TABLE` 或等价的表重建过程），或者通过分区裁剪来“瞬时回收”历史分区空间。

## 6. 选型建议：一张表已经很大了，先做什么

可以按“收益 / 成本”排序执行：

1. 治理慢 SQL 与索引（立竿见影，成本低）。
2. 拆大字段、控索引、控长事务（降低写放大与恢复成本）。
3. 做分区 + `DROP PARTITION` 清历史（最适合时序类数据）。
4. 建归档链路与冷热分离（把 OLTP 变轻）。
5. 读写分离扩读能力（主从复制）。
6. 分库分表扩容量与写上限（最高复杂度，最后选）。
