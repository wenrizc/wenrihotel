## 1. 幻读是什么？和不可重复读有什么区别

**幻读（Phantom Read）**指：在同一个事务内，**按同一个条件范围查询**两次，第二次出现了第一次“范围内不存在”的新行（或少了行），导致“像出现了幻影”。

它和 **不可重复读（Non-repeatable Read）**的核心区别：

- 不可重复读：针对**同一行**，两次读到的内容不一致（`UPDATE` 导致）。
- 幻读：针对**一段范围**，两次读到的行集合不一致（`INSERT` / `DELETE` 导致）。

一个典型的幻读场景（范围查询 + 插入）：

```sql
-- 事务 A（RR）
BEGIN;
SELECT * FROM orders WHERE user_id = 100 AND status = 0; -- 第一次：返回 0 行

-- 事务 B
BEGIN;
INSERT INTO orders(user_id, status) VALUES (100, 0);
COMMIT;

-- 回到事务 A
SELECT * FROM orders WHERE user_id = 100 AND status = 0; -- 第二次：可能出现“多了一行”
COMMIT;
```

> 注意：面试里很多人会说“MySQL RR 彻底解决幻读”。更严谨的说法是：**InnoDB 在 RR 下通过“MVCC + Next-Key Lock”让常见幻读场景可控，但是否“彻底解决”取决于读的类型（快照读/当前读）与语句形态。**

## 2. MySQL（InnoDB）解决幻读的总体思路：MVCC + Next-Key Lock

在 InnoDB 中讨论幻读，必须先区分两类读取：

- **快照读（Snapshot Read）**：普通 `SELECT`，基于 `ReadView` 读一致性快照。
- **当前读（Current Read）**：读最新版本并加锁，典型是 `SELECT ... FOR UPDATE`、`SELECT ... LOCK IN SHARE MODE`，以及 `UPDATE` / `DELETE`（隐式当前读）。

InnoDB 的策略可以概括为：

- 对**快照读**：主要依靠 **MVCC**，保证事务内读到的是同一份一致性视图，避免“读视角”发生变化。
- 对**当前读**：主要依靠 **Next-Key Lock（临键锁）**，把“范围”锁住，阻止别的事务在该范围插入，从而避免范围内出现“新行”。

## 3. 关键前提：RR 下的“快照读”与“当前读”语义不同

### 3.1 快照读：读到的是历史版本

普通 `SELECT` 不加锁，走 MVCC：同一事务中多次执行相同查询，通常会复用同一个 `ReadView`，因此结果保持一致。

这让很多人误以为“幻读不存在了”，但它只说明：**快照读的结果稳定**，并不代表你的后续写操作不会遇到“幻觉”。

### 3.2 当前读：读最新版本 + 加锁，才是真正“阻止插入”的手段

当业务需要“查出来就要保证没人能在范围内插入/修改”，就必须用当前读（例如先查再改）：

```sql
BEGIN;
SELECT * FROM orders WHERE user_id = 100 AND status = 0 FOR UPDATE; -- 当前读 + 加锁
-- 业务逻辑：基于查询结果做决策
UPDATE orders SET status = 1 WHERE user_id = 100 AND status = 0;
COMMIT;
```

这里避免幻读的关键不是 MVCC，而是 InnoDB 对范围条件加的锁（Next-Key Lock）。

## 4. Next-Key Lock（临键锁）到底锁了什么

### 4.1 三类锁的关系

- **Record Lock（记录锁）**：锁住某条索引记录本身。
- **Gap Lock（间隙锁）**：锁住索引记录之间的“间隙”，阻止在间隙中插入新记录。
- **Next-Key Lock（临键锁）**：`Record Lock + Gap Lock` 的组合，锁住“某条记录 + 其前面的间隙”（可理解为锁住一个范围片段）。

### 4.2 为什么 Next-Key Lock 能防幻读

幻读的本质是“范围内出现新行”。要阻止新行出现，必须阻止别的事务在该范围内插入。

在 RR 隔离级别下，InnoDB 对很多“范围型当前读”会加 Next-Key Lock，从而把范围的间隙也锁住，其他事务就无法 `INSERT` 进入这个范围。

### 4.3 锁能锁多大，取决于索引是否命中

这是工程上最重要的一点：**锁的粒度主要由索引决定**。

- 命中合适索引：锁定的是索引上的局部范围（更小）。
- 未命中索引：可能退化为更大范围的锁，甚至接近全表范围（更大），引发严重锁等待。

因此，“为范围查询建立合适索引”不仅是性能问题，也是并发正确性与可用性问题。

## 5. RR 与 RC 下对幻读的处理差异（务必会讲）

### 5.1 RR（Repeatable Read，可重复读）

- 快照读：依靠 MVCC，事务内视图稳定。
- 当前读：大量场景会使用 Next-Key Lock，**更倾向于阻止范围插入**，因此更能避免“范围内出现新行”的现象。

### 5.2 RC（Read Committed，读已提交）

在 RC 下，InnoDB 更倾向于减少 Gap Lock 的使用（并发更高），因此：

- 快照读：每次语句生成新 `ReadView`，范围查询更容易“看到新插入的行”。
- 当前读：通常也更少对间隙加锁（具体与语句形态、约束检查有关），因此更可能出现“范围内出现新行”的现象。

结论要点（面试回答建议）：

- **想减少幻读带来的业务不确定性**：RR + 当前读（`... FOR UPDATE`）是更常见组合。
- **想要更高并发、接受读视角变化**：RC 更常见，但要配合业务幂等、重试、唯一约束兜底。

## 6. 工程实践：如何在项目里“正确处理幻读”

### 6.1 用“唯一约束”把幻读变成可控冲突

很多业务的“幻读风险”其实是“并发插入重复业务键”。给业务键加 **UNIQUE**，让并发冲突显式化，然后通过重试/返回错误处理，是非常常见的方案。

```sql
ALTER TABLE orders ADD UNIQUE KEY uk_user_status(user_id, status);
```

### 6.2 需要强一致决策时，显式使用当前读

典型场景：库存扣减、抢单、状态机流转等“先查再改”逻辑。

- 用 `SELECT ... FOR UPDATE` 把关键范围锁住（前提是能命中索引）。
- 把事务做短：只包住必要逻辑，减少锁持有时间。

### 6.3 避免“范围过大”的当前读

范围过大意味着：

- 锁住的间隙范围大；
- 并发插入被阻塞；
- 死锁概率上升。

优化方向：

- 更精确的条件 + 更合适的联合索引；
- 拆分为更小批次；
- 用“队列化/分片”降低同一范围竞争。

### 6.4 排查手段（线上常用）

- 查看死锁：`SHOW ENGINE INNODB STATUS;`
- 观察锁等待：关注 `performance_schema` 的锁/事务相关视图（按你的 MySQL 版本启用）。
- 调整等待超时：`innodb_lock_wait_timeout`（仅作为兜底，不是解决方案）。

## 7. 总结（高频回答模板）

- 幻读是“范围集合变化”，不可重复读是“同一行内容变化”。
- InnoDB 处理幻读的关键是 **区分快照读与当前读**：
  - 快照读主要靠 **MVCC** 让读视图稳定；
  - 当前读主要靠 **Next-Key Lock（Record + Gap）** 锁住范围，阻止插入。
- 工程上最关键的是：**索引决定锁粒度**；并发插入类问题优先用 **唯一约束 + 重试/幂等** 把问题显式化。
