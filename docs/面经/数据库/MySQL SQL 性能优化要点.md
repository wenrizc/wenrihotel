## 1. 优化 SQL 的正确姿势：先明确目标与证据

SQL 优化不是“凭感觉改语句”，而是一个闭环：

1. 明确目标：是降低 P99 延迟、提升 QPS，还是降低 CPU / I/O？
2. 拿到证据：慢查询日志、监控指标、执行计划（`EXPLAIN`）、真实数据量。
3. 小步改动：一次只改一件事（索引、SQL、参数），便于归因。
4. 回归验证：对比执行计划与线上指标，确认收益与副作用。

## 2. 先看执行计划：EXPLAIN 要关注哪些字段

`EXPLAIN` / `EXPLAIN ANALYZE`（不同版本能力不同）是定位问题的起点，重点关注：

- `type`：访问类型（从好到坏大致是 `const`、`ref`、`range`、`index`、`ALL`）。
- `key` / `possible_keys`：是否用上了预期索引。
- `rows`：预估扫描行数（越小越好，但要结合 `filtered`）。
- `Extra`：常见信号：
  - `Using index`：覆盖索引（通常是好事）。
  - `Using temporary`：可能用了临时表（`GROUP BY` / `ORDER BY` 常见）。
  - `Using filesort`：需要额外排序（不一定坏，但要警惕大数据量）。

## 3. 索引是第一生产力：设计与使用的关键点

### 3.1 联合索引的“最左前缀”与顺序

联合索引 `(a, b, c)`：

- 能支持 `a`、`a,b`、`a,b,c` 前缀条件。
- 索引列顺序要服务于**高频查询**：通常把选择性更高、过滤更强的列放前面（但也要兼顾 `ORDER BY`、`GROUP BY`）。

### 3.2 让条件“可走索引”（Sargable）

以下写法容易导致索引失效或效果变差：

- 在索引列上做函数/表达式：`WHERE DATE(create_time) = ...`
- 隐式类型转换：数字列用字符串比较、字符集/排序规则不一致。
- 以 `%` 开头的模糊匹配：`LIKE '%abc'`

改写方向：

- 把函数挪到常量侧，或增加冗余列/生成列以便索引。
- 保证参数类型与列类型一致。
- 用前缀匹配 `LIKE 'abc%'` 或引入全文索引/搜索引擎。

### 3.3 覆盖索引：用更少 I/O 换更快查询

如果查询的列都在二级索引里，MySQL 可以只扫索引而不回表（减少随机 I/O）。典型优化：

- 把高频查询需要返回的少量字段纳入联合索引尾部（注意索引膨胀）。
- 避免无意义 `SELECT *`。

## 4. SQL 写法层面的高频优化点

### 4.1 JOIN：让驱动表更小、被驱动表有索引

经验规则：

- 驱动表（先读的表）越小越好。
- 被驱动表的关联列要有索引，否则容易变成“嵌套循环 + 全表扫”。

### 4.2 分页：避免大 OFFSET

`LIMIT offset, size` 在 offset 很大时会扫描大量无用行。常见替代是“基于游标/主键”的 Keyset Pagination：

```sql
-- 记住上一页最后一条的 id
SELECT id, col1, col2
FROM t
WHERE id > ?
ORDER BY id
LIMIT 20;
```

### 4.3 IN / OR / 子查询：优先保证可走索引与可控扫描

- `OR` 条件很容易破坏索引使用，能拆就拆（`UNION ALL` 可能更清晰可控）。
- `IN` 列表过大可能导致计划不稳定，必要时落临时表再 JOIN。
- 子查询不是原罪，关键是执行计划是否合理；复杂场景可用派生表/CTE（版本相关）让语义更清晰。

## 5. 事务与锁：性能问题经常不是“慢”，而是“等”

常见现象：

- SQL 本身不慢，但在等锁（行锁、间隙锁、MDL）。
- 大事务导致锁持有时间长，拖垮并发。

优化方向：

- 缩短事务：只包住必要读写，避免在事务里做远程调用与长时间计算。
- 避免大范围 `UPDATE/DELETE`：分批、命中索引、减少锁范围。
- 对热点行做“削峰”：队列化、分片计数、乐观锁（版本号）等。

## 6. 配置与系统层面：别忽视“基础盘”

常见会直接影响 SQL 性能的点：

- **Buffer Pool**（InnoDB 缓冲池）是否足够，命中率是否正常。
- 临时表、排序、连接缓冲是否频繁落盘（磁盘 I/O 抖动）。
- 连接数过大导致上下文切换与内存压力（连接池与限流）。

> 参数调优必须结合实例规格与负载特征；不要靠“抄配置”。

## 7. 一份可落地的优化清单（面试与实战通用）

1. 先用慢查询日志/监控定位 Top SQL（按时间与调用次数排序）。
2. `EXPLAIN` 看是否走对索引、扫描行数是否合理、是否 `Using temporary/filesort`。
3. 对照查询模式补索引（联合索引顺序、覆盖索引、避免冗余索引）。
4. 改写 SQL：让条件可走索引、避免大 OFFSET、拆大事务与大批量写。
5. 关注锁等待与死锁（不要只盯 CPU）。
6. 回归验证：数据量放大、参数一致、观察 P95/P99 与资源使用。
