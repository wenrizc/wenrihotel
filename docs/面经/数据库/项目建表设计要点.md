## 1. 建表前先想清楚：数据模型与访问模式

建表不是“把字段写进去”这么简单，优先明确 4 类问题：

- **实体与关系**：有哪些核心实体？一对多/多对多怎么表达？
- **访问模式**：最常见的查询条件是什么？按什么维度分页、排序、聚合？
- **写入模式**：写多读多？是否有高并发热点行（计数、库存、余额）？
- **生命周期**：数据保留多久？是否按时间归档、冷热分层、分区？

这些答案会直接决定：主键策略、索引设计、是否分库分表、是否需要冗余字段。

## 2. 主键设计：选择稳定、短、递增（但要避免热点）

### 2.1 主键的基本要求

- **稳定**：不会业务上“改 ID”。
- **短**：越短索引越小，缓存命中更高。
- **递增（或局部递增）**：减少 B+Tree 频繁分裂，写入更友好。

### 2.2 ID 生成策略选择

常见选择：

- 自增 `BIGINT`：简单高效；缺点是跨库不唯一、可被推测、主从切换需要谨慎。
- 雪花 ID：全局唯一、离线生成；缺点是更长、索引更大、需要时钟治理。
- UUID：全局唯一；缺点是随机性强导致索引写入差（除非使用有序 UUID）。

工程建议：

- 单库单表：自增通常足够好。
- 多库多表：优先考虑雪花类全局 ID 或分段号段。

## 3. 字段类型与编码：选对类型就是性能与正确性的基础

### 3.1 数值与金额

- 计数/ID：优先 `BIGINT`（必要时 `UNSIGNED`）。
- 金额：用 `DECIMAL(p, s)`，不要用 `FLOAT/DOUBLE`（避免精度问题）。

### 3.2 字符串与长度

- `VARCHAR` 需要结合最大长度与字符集估算行大小，避免行溢出与频繁页分裂。
- 业务枚举：优先用小整数（`TINYINT/SMALLINT`）+ 枚举映射表，而不是大字符串。

### 3.3 时间字段

- 推荐使用 `DATETIME` 或 `TIMESTAMP`（按时区要求选择），并统一约定时区策略（例如全部用 UTC）。
- 常见组合：`create_time`、`update_time`、`deleted_at`（软删除）。

### 3.4 字符集与排序规则

工程上一般推荐：

- 字符集：`utf8mb4`
- 排序规则：按业务选择（注意大小写、重音、emoji 的比较规则差异）

> 字符集与排序规则不一致会引发隐式转换，导致索引失效与性能问题。

## 4. NULL、默认值与约束：把数据质量前置

### 4.1 NULL 的取舍

- `NOT NULL` + 合理默认值通常更利于索引与查询判断。
- 需要表达“三态”（未知/无/有）时才考虑 `NULL`，否则容易制造歧义。

### 4.2 唯一约束与业务一致性

能用唯一约束解决的问题，不要只靠代码判断：

- 并发插入去重（订单号、幂等号、业务唯一键）
- 状态机的合法迁移（可结合唯一键/条件更新）

```sql
ALTER TABLE t ADD UNIQUE KEY uk_biz(biz_key);
```

### 4.3 外键要不要用

外键优点：

- 数据一致性强，约束由数据库兜底。

外键代价：

- 写入/删除受约束影响，可能放大锁范围与延迟；
- 分库分表后很难使用。

工程上很多团队选择“不用外键”，但要用**应用层约束 + 异步对账**补齐一致性。

## 5. 索引设计：围绕查询而不是围绕字段

### 5.1 索引设计三原则

- 覆盖最常见查询（`WHERE`、`JOIN`、`ORDER BY`、`GROUP BY`）。
- 尽量让条件可走索引（避免在索引列上做函数/隐式转换）。
- 控制索引数量与宽度（索引越多写越慢，索引越宽占用越大）。

### 5.2 联合索引怎么排顺序

常见经验：

- 把选择性高、过滤强的列放前面；
- 若有固定的排序需求，把 `ORDER BY` 列放在联合索引中（并注意顺序）；
- 结合“最左前缀”规则做覆盖。

## 6. 热点与并发：避免“同一行被所有人抢”

高并发热点行常见于：

- 库存、余额、计数器；
- 同一用户/同一商户的单行聚合信息。

常见治理手段：

- 拆分热点（分片计数、分桶行、按时间窗口拆）。
- 乐观锁：增加 `version` 字段做条件更新。
- 异步化：把强一致写入变成队列串行消费。

## 7. 大表治理：分区、归档与历史表

当数据按时间不断增长时，提前规划：

- 是否需要按时间分区（便于清理与范围查询）。
- 是否需要历史表（热数据与冷数据分离）。
- 是否需要归档到对象存储/数仓。

不要等到表上亿再补救，迁移成本会指数级上升。

## 8. DDL 与上线：建表要考虑“演进”

上线后表结构一定会变，建表时就要考虑可演进性：

- 新增字段尽量可空或有默认值，避免强依赖；
- 避免频繁修改大字段类型与主键；
- 大表变更要评估 Online DDL 能力与锁影响，必要时用变更工具与灰度流程。

## 9. 一份建表 Checklist（直接背）

1. 表的访问模式与核心查询是什么？
2. 主键怎么选？是否需要全局唯一？
3. 字段类型是否准确（金额用 `DECIMAL`，时间统一时区）？
4. 是否需要唯一约束保证幂等/去重？
5. 索引是否覆盖 `WHERE/JOIN/ORDER BY` 的高频路径？是否有冗余索引？
6. 是否存在热点行与大事务风险？如何削峰？
7. 数据生命周期与归档策略是什么？
8. 表结构未来怎么演进，DDL 风险怎么控制？
