## 1. 本质

**同步 / 异步**：关注“**I/O 完成**如何通知应用（调用返回即完成，还是先返回、后通知）”。

**阻塞 / 非阻塞**：关注“**本次系统调用**是否可能让当前线程睡眠等待（等不到就立刻返回，还是等到条件满足才返回）”。

二者是**两条正交维度**：一个描述“完成语义”，一个描述“等待方式”。因此可以组合出 4 类行为，但工程上最常见的是：**同步阻塞**、**同步 + I/O 多路复用**、**异步非阻塞**。

## 2. 概念定义与判定标准

### 2.1 同步 I/O（Synchronous I/O）

同步 I/O 的核心特征是：**I/O 是否完成，由发起调用的线程在系统调用返回时拿到结果**（例如 `read()` 返回已读字节数，或返回错误码）。若数据尚未就绪，内核可能让线程睡眠等待（阻塞），也可能立即返回 `EAGAIN`（非阻塞），但“完成通知”仍然体现为“本次调用的返回值”。

可以把同步 I/O 理解为：应用线程与内核在一次（或多次）系统调用往返中，把“等就绪 + 拷贝数据 + 返回结果”这件事做完。

### 2.2 异步 I/O（Asynchronous I/O）

异步 I/O 的核心特征是：**发起 I/O 的系统调用先返回**（只表示“请求已提交/已排队”），而真正的完成（完成多少、是否出错）**通过后续通知机制**交付给应用，例如：

- 信号（POSIX `aio` 可配置）。
- 回调（很多语言运行时会封装成 callback）。
- 事件队列 / 完成队列（Linux `io_uring` 的 CQ，Windows IOCP 的 Completion Port）。
- 轮询获取完成事件（例如 `io_getevents()` 或 `io_uring` 的 `cqe` 拉取）。

异步 I/O 的关键是“**完成分离**”：提交与完成是两步，应用线程不必在提交时等待数据准备与拷贝完成。

### 2.3 阻塞 I/O（Blocking）

阻塞描述的是：**系统调用在条件不满足时，是否会让当前线程进入睡眠等待**。典型表现：

- `read()` 在 socket 无数据可读时阻塞。
- `accept()` 在无新连接时阻塞。
- `connect()` 在三次握手未完成时阻塞（视实现与超时）。

阻塞的“等待”发生在内核调度层：线程从 Running 进入 Sleep，等待被唤醒。

### 2.4 非阻塞 I/O（Non-blocking）

非阻塞描述的是：**系统调用不会因为条件不满足而睡眠**，而是立即返回，告诉你“现在做不了”。POSIX 常见返回：

- `EAGAIN` / `EWOULDBLOCK`：资源暂不可用。

在 Unix / Linux 上，非阻塞通常通过 `fcntl()` 设置文件描述符标志 `O_NONBLOCK`。

```c
// 设置 fd 为非阻塞
int flags = fcntl(fd, F_GETFL, 0);
fcntl(fd, F_SETFL, flags | O_NONBLOCK);
```

## 3. 两条维度如何“正交”

### 3.1 用三个问题判断分类

1. **提交时**：调用是否立刻返回？
2. **等待发生在谁**：等待是由调用线程在内核里睡眠（阻塞），还是调用直接返回（非阻塞）？
3. **完成如何交付**：完成信息是通过“本次调用返回值”交付（同步），还是通过“后续通知/完成队列”交付（异步）？

### 3.2 2×2 组合表

| 组合 | 语义 | 典型接口/场景 | 关键点 |
| --- | --- | --- | --- |
| 同步 + 阻塞 | 调用不返回，直到可完成并拷贝后返回 | `read()`（默认阻塞 fd） | 简单但线程占用高 |
| 同步 + 非阻塞 | 调用立即返回，没就绪则 `EAGAIN` | `O_NONBLOCK + read()` | 需要轮询或配合复用 |
| 异步 + 非阻塞 | 提交立即返回，完成后通过事件/回调交付 | Linux `io_uring`，Windows IOCP | 线程利用率高，工程复杂度高 |
| 异步 +（可等待） | 提交后你也可以主动等待完成事件 | `io_uring_wait_cqe()`，`aio_suspend()` | “异步接口 + 同步等待”很常见 |

注意最后一格：严格说“阻塞/非阻塞”定义在**具体等待点**上。异步 I/O 也可能在“等完成事件”时阻塞，这并不改变其“异步提交、异步完成交付”的本质。

## 4. 典型路径：从用户态到内核态发生了什么

### 4.1 同步阻塞 `read()` 的典型流程（以 socket 为例）

1. 应用线程调用 `read()` 进入内核。
2. 若接收缓冲区为空：线程被挂起（Sleep），等待网卡中断、协议栈处理、数据进入 socket buffer。
3. 条件满足后被唤醒：内核把数据从 socket buffer 拷贝到用户缓冲区（`copy_to_user`）。
4. `read()` 返回：返回值就是“完成通知”。

这里“阻塞”体现在第 2 步，“同步”体现在第 4 步（返回即完成）。

### 4.2 同步非阻塞 `read()` 的典型流程

1. fd 设置为 `O_NONBLOCK`。
2. 应用线程调用 `read()`：
   - 若无数据：立刻返回 `-1`，`errno = EAGAIN`。
   - 若有数据：拷贝后返回字节数。

非阻塞并不等于“不会等待任何事情”，它的含义是：**不会因为“无数据/无连接”等条件不满足而睡眠**。

### 4.3 异步 I/O 的典型流程（以 `io_uring` 为例）

1. 应用把请求写入 SQ（Submission Queue），通过 `io_uring_enter()` 提交。
2. 内核异步执行 I/O：可能在内核线程、驱动、DMA、块层中推进。
3. 完成后写入 CQ（Completion Queue）。
4. 应用从 CQ 取出 `cqe` 得到结果（完成通知）。

这里“异步”的关键是：**提交与完成解耦**，完成通过 CQ 交付，而不是靠最初提交调用的返回值。

## 5. I/O 多路复用

### 5.1 `select` / `poll` / `epoll` 的本质：就绪通知（Readiness）

I/O 多路复用解决的是：**一个线程等待多个 fd 变为可读/可写**。它提供的是“就绪事件”（readable/writable），而不是“完成事件”（读了多少字节、是否发生错误）。

典型 epoll 模型（仍然是同步 I/O）：

```c
// 1) 等就绪：可能阻塞在 epoll_wait
int n = epoll_wait(epfd, events, max, timeout);
for (int i = 0; i < n; i++) {
  int fd = events[i].data.fd;
  // 2) 真正读数据：read 仍然是同步拷贝到用户态
  for (;;) {
    ssize_t m = read(fd, buf, sizeof(buf));
    if (m > 0) { /* 处理数据 */ }
    else if (m == 0) { /* 对端关闭 */ break; }
    else if (errno == EAGAIN) { break; } // 非阻塞读完了
    else { /* 错误处理 */ break; }
  }
}
```

结论：`epoll_wait()` 返回的是“现在读不会阻塞”的概率很高，但真正的“完成”仍由 `read()` 的返回值给出，因此它仍是**同步**模型。

### 5.2 `epoll` 常见模式：阻塞点从 `read()` 转移到 `epoll_wait()`

- 传统同步阻塞：每个连接一个线程，阻塞在 `read()`。
- 同步 + 复用：少量线程阻塞在 `epoll_wait()`，被唤醒后对就绪 fd 做非阻塞 `read()`。

这就是高并发服务器常见的 Reactor 模型：**用“就绪通知”减少线程数量**，而不是把 I/O 变成“异步完成”。

### 5.3 LT / ET 的关键差异

- LT（Level Triggered，水平触发）：只要还有数据没读完，就持续通知可读。
- ET（Edge Triggered，边沿触发）：从不可读到可读的“变化”才通知一次。

ET 必须配合 `O_NONBLOCK`，并在回调里把数据读到 `EAGAIN` 为止，否则会“丢事件”（实际上是你没把缓冲区读空，后续不会再触发）。

## 6. 真正的异步 I/O：Linux 与 Windows 的主流实现

### 6.1 POSIX AIO（`aio_read`）与 Linux AIO（libaio）

POSIX AIO 以 `aio_read()` / `aio_write()` 为代表，语义是“提交后返回，完成后通知”。但在很多系统实现中，尤其是对普通文件的异步，可能会通过线程池模拟（本质仍是同步 I/O + 线程），面试中要能指出：**是否“内核真异步”取决于实现与设备支持**。

Linux 早期“内核异步块 I/O”更多指 Linux AIO（libaio，`io_submit()` / `io_getevents()`），主要面向块设备与 `O_DIRECT` 场景。

### 6.2 Linux `io_uring`：统一的异步接口

`io_uring` 通过共享环形队列（SQ/CQ）把“提交”和“完成”做成低开销通道，支持网络与文件等更多类型的 I/O。它提供的结果是“完成事件”，因此在语义上属于**异步 I/O**。

面试可追问到两点：

- **为什么更快**：减少系统调用次数、减少拷贝与上下文切换（取决于具体特性如 `SQPOLL`、`IORING_OP_*`）。
- **为什么更复杂**：需要管理请求生命周期、并发完成、缓冲区复用与回收。

### 6.3 Windows Overlapped I/O + IOCP

Windows 的 Overlapped I/O 允许异步提交，完成通过 IO Completion Port（IOCP）取回。IOCP 是典型的“完成队列”模型，语义非常明确：**提交返回不代表完成，完成事件从队列获取**。

## 7. 容易混淆的点（务必能反驳）

### 7.1 “非阻塞就是异步”是错的

非阻塞只是“不睡眠等待”，你仍然需要自己反复调用 `read()` 或配合 `select/epoll` 等待就绪；完成仍由 `read()` 返回值给出，因此它是**同步非阻塞**。

### 7.2 “`epoll` 是异步 I/O”是错的

`epoll` 提供的是“就绪通知”，不负责把数据异步搬到用户缓冲区；你仍然要调用 `read()` 完成拷贝与取结果，所以它是**同步 I/O（复用/事件驱动）**。

### 7.3 “异步 I/O 就完全不阻塞线程”不严谨

异步 I/O 的提交阶段不阻塞，但你仍可能在：

- 等待完成事件（例如 `io_uring_wait_cqe()`）。
- 等待业务资源（队列、锁、线程池、GC 等）。

所以更准确的表述是：**异步 I/O 把等待从 I/O 系统调用中解耦出来，并允许用事件驱动方式管理等待**。

### 7.4 “可读事件 = 读完了”是错的

“可读”只表示“读不会阻塞”或“有数据/有 EOF”，一次 `read()` 可能只读到部分数据（TCP 流式），也可能因为缓冲区大小或拥塞而分段到达。

## 8. 工程实践：怎么选，怎么用

### 8.1 选择建议（按场景）

- 连接数不高、逻辑简单：同步阻塞 + 线程池最省心（但要控制线程数与栈内存）。
- 高连接数网络服务：同步 + `epoll`（Reactor）是主流方案，配合非阻塞 socket 与合理的事件循环。
- 需要极致吞吐/低延迟、或大量磁盘 I/O：评估 `io_uring`（以及语言/框架支持成熟度）。

### 8.2 非阻塞读写的必备套路

- 处理 `EAGAIN` / `EWOULDBLOCK`：把 fd 重新注册可读/可写事件，等待下次就绪。
- 处理“部分读/部分写”：维护应用层缓冲区，直到协议帧完整或把待发送数据写完。
- 避免 busy loop：不要在用户态 `while(read()==EAGAIN){}` 空转，占用 CPU。

### 8.3 `epoll` 的三个常见坑

1. ET 未读到 `EAGAIN`：导致后续不再触发，表现为“连接卡死”。
2. 忽略 `EPOLLHUP` / `EPOLLERR`：没及时清理 fd，出现 fd 泄漏或假活连接。
3. 回调里做重活：事件循环被阻塞，表现为尾延迟飙升；重活应扔到工作线程池。

### 8.4 与磁盘 I/O 相关的两个现实

- 普通文件读写往往经过 page cache，很多“读”在内存命中时非常快，瓶颈可能不在磁盘而在拷贝与调度。
- 真正的磁盘异步收益依赖设备与路径：SSD、NVMe、`O_DIRECT`、队列深度等都会影响“异步是否更快”。

### 8.5 与 Java BIO / NIO / AIO 的对应（面试常考）

- BIO（Blocking I/O）：典型是“同步 + 阻塞”，一个连接常配一个线程，阻塞在 `read()`。
- NIO（Non-blocking I/O）：典型是“同步 + 非阻塞 + 多路复用”，用 `Selector` 等待就绪，真正数据读取仍由 `read()` 返回值给出。
- AIO（Asynchronous I/O）：API 语义是“异步”，完成通过 `CompletionHandler` / `Future` 交付；但在不同平台与不同 I/O 类型下，底层可能是内核异步能力，也可能是线程池模拟，因此要区分“**接口语义异步**”与“**内核路径异步**”。
