## 1. 先对齐接口契约与语义

第三方 API 的“坑”经常不是技术实现，而是语义不清：

- 幂等语义：同一个请求重试会不会重复扣款/重复下单？
- 一致性语义：是至少一次、至多一次，还是尽力而为？
- 错误码语义：HTTP 状态码与业务错误码是否一致，哪些错误可重试？
- 分页语义：页码/游标、排序规则变化、是否稳定分页？

建议把这些写进契约（OpenAPI/IDL/对接文档），否则线上只能靠“对账 + 补偿”兜底。

## 2. 鉴权与安全

常见鉴权方式：

- API Key：简单，但要注意泄漏与权限边界。
- OAuth 2.0：有授权与 token 生命周期，需要处理刷新与过期。
- 请求签名：要关注 nonce、时间戳窗口、重放攻击与时钟偏差。
- mTLS：双向证书校验，运维成本更高，但安全性更强。

工程注意点：

- 明确请求签名是否包含 body，是否需要 canonical 化。
- 时钟要统一（NTP），避免因时钟漂移导致签名失败。

## 3. 网络可靠性治理：超时、重试、限流、熔断

第三方调用要默认“不稳定”，必须做防护：

- 超时：区分连接超时、读超时，避免无上限等待。
- 重试：只对幂等请求重试，使用指数退避 + 抖动，避免重试风暴。
- 限流：客户端自限流，避免把自己的流量打穿对方或被对方封禁。
- 熔断与降级：对方故障时快速失败，走兜底策略（缓存、降级返回、异步补偿）。

## 4. SDK 调用

SDK 通常封装了鉴权、重试与序列化，使用成本低，但会引入依赖冲突与版本锁定。常见坑：

- 隐藏重试导致雪崩（你以为一次请求，实际上多次重试）。
- 线程池/连接池不可控，默认配置不适合线上。
- 升级后接口或字段变更不兼容。

使用前应审查默认超时与重试策略，并隔离依赖版本。

## 5. RPC 调用

RPC（如 gRPC、Dubbo）性能好、类型安全，但需要服务发现、负载均衡与协议兼容。坑点集中在：

- IDL 变更不兼容（字段删除、枚举新增等）。
- 超时与重试语义不一致（调用方与服务端不一致会放大故障）。
- 长连接被中间设备重置（空闲超时、NAT 设备回收）。

## 6. HTTP/REST 调用

HTTP 兼容性强、接入简单，但容易被网络抖动与代理影响。常见问题：

- 状态码语义不一致（200 里包业务错误码）。
- 请求幂等未定义（重试导致重复执行）。
- 编码/时区不一致（特别是时间字段）。

对外部 API 必须设置连接与读写超时，并区分幂等与非幂等请求的重试策略。

## 7. 典型失败模式与应对

| 失败模式 | 典型表现 | 常见应对 |
| --- | --- | --- |
| 超时 | 客户端超时但服务端可能已执行 | 幂等键 + 可查询对账接口 + 合理超时 |
| 重试放大 | 故障时 QPS 翻倍导致雪崩 | 指数退避 + 抖动 + 熔断 + 限流 |
| 限流/配额 | 429/403 或业务错误码 | 客户端自限流 + 降级 + 缓存 |
| 签名/时钟偏差 | 鉴权失败、偶发 | 统一时钟（NTP）+ 容忍窗口 + nonce |
| 兼容性变更 | 字段改名/枚举新增导致解析失败 | 兼容性策略 + 灰度 + 回滚 |
