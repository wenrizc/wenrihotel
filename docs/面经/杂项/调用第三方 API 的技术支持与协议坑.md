# 调用第三方 API 的技术支持与协议坑

## 1. 基础技术支持
调用第三方 API 需要接口契约、鉴权、网络与可用性保障。常见的契约形式是 OpenAPI 或 IDL，鉴权可能是 API Key、OAuth 2.0 或签名。网络侧需要 TLS 或 mTLS、超时、重试、限流与熔断，业务侧需要幂等键、补偿机制与版本兼容策略。可观测性上要打点日志、指标与链路追踪，确保问题可定位。

## 2. SDK 调用
SDK 通常封装了鉴权、重试与序列化，使用成本低，但会引入依赖冲突与版本锁定。常见坑包括隐藏重试导致雪崩、线程池或连接池配置不可控、升级后接口变更不兼容。使用前应审查默认超时与重试策略，并隔离依赖版本。

## 3. RPC 调用
RPC（如 gRPC、Dubbo）性能好、类型安全，但需要服务发现、负载均衡与协议兼容。坑点集中在 IDL 变更不兼容、超时与重试不一致、长连接被中间设备重置。跨语言场景还需关注序列化字段的兼容策略与大包限制。

## 4. HTTP/REST 调用
HTTP 兼容性强、接入简单，但容易被网络抖动与代理影响。常见问题包括状态码语义不一致、请求幂等未定义、分页与排序规则变化、编码与时区不一致。对外部 API 必须设置连接与读写超时，并对可重试请求区分幂等与非幂等。

## 5. 通用防坑清单
落地时可以按如下清单逐项确认。

- 明确 SLA 与限流规则，必要时做客户端自限流与缓存。
- 关键接口加幂等键与重试隔离，避免放大故障。
- 建立灰度与回滚策略，升级 SDK 或协议前先做兼容性验证。
- 记录请求参数、响应摘要与错误码，便于对账与追责。
