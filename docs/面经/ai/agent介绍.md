## 1. AI Agent

### 1.1 什么是 AI Agent

AI Agent 不是“更会聊天的 LLM”，而是一个**带状态（State）、能闭环执行（Loop）、可调用外部能力（Tools）的任务执行系统**。常见抽象是：

- 输入：用户目标、约束、上下文、可用工具集合。
- 过程：LLM 产出计划与动作；执行器调用工具；把观测结果回填到上下文；循环迭代。
- 输出：可验证的结果（文件、工单、代码变更、查询结果等），以及可追溯的执行记录。

本质上，Agent = LLM + 控制器（Controller）+ 运行时状态机（State Machine）+ 工具运行时（Tool Runtime）+ 记忆系统（Memory）。

## 2. 核心组件：大脑、规划、记忆、工具

### 2.1 大脑：LLM 负责“决策与生成”

LLM 在 Agent 中通常承担三类输出：

- 任务理解：把用户目标转成可执行约束与验收标准（Definition of Done）。
- 动作选择：决定下一步是“继续思考”还是“调用工具 A”，以及传什么参数。
- 结构化产物：生成代码、SQL、配置、报告等。

工程上你需要明确：LLM 并不天然“可靠”。可靠性来自外围系统的约束与校验，例如：结构化输出、工具白名单、重试、幂等、回滚、评估与监控。

### 2.2 规划：把目标拆成可执行步骤

规划（Planning）解决两个问题：

- 分解：把“写一个需求方案”拆成若干子任务（调研、对比、落库、写文档）。
- 迭代：根据执行反馈动态调整（比如检索不到资料就换检索词，接口报错就补参数）。

常见方法对比：

| 方法 | 核心思想 | 适用场景 | 主要缺点 |
| --- | --- | --- | --- |
| CoT（Chain-of-Thought） | 把推理过程展开成多步 | 逻辑题、分步计算 | 无法天然接入外部环境反馈 |
| ReAct（Reason + Act） | 推理与行动交错，依赖 Observation 纠偏 | 需要查资料、调用工具、与环境交互 | 需要设计好工具与日志，否则易发散 |
| ToT（Tree of Thoughts） | 每步探索多条思路分支并评估 | 需要搜索空间探索（方案设计、推理） | 成本高，分支控制困难 |

落地时更常见的工程模式是 Plan-and-Execute：

1. 先生成一个高层计划（可中途重写）。
2. 再逐步执行每一步，并在失败时回到“重规划”节点。

### 2.3 记忆：让 Agent 具备“跨步骤、跨会话”的信息保持能力

记忆不是一个概念词，而是一组存储策略 + 读写策略：

- 短期记忆（Working Memory）：放在上下文窗口里，适合保存当前任务关键约束、最近工具结果。
- 长期记忆（Long-Term Memory）：放在外部存储里，适合保存知识库、历史任务摘要、用户偏好。

长期记忆常见拆分：

- 语义记忆（Semantic）：面向“是什么”（知识、文档、FAQ）。
- 情景记忆（Episodic）：面向“发生了什么”（一次执行的轨迹、结论、踩坑）。

注意点：

- **不是所有信息都该写入长期记忆**。要有写入门槛（例如：被引用次数、明确结论、可复用性）。
- 记忆检索要可解释、可溯源，否则会把噪声引入推理链路。

### 2.4 工具使用：把语言变成“可执行动作”

工具使用（Tool Use）通常通过“结构化调用”实现：让 LLM 输出符合约束的参数对象，由执行器进行校验与调用。

典型工具定义（JSON Schema 风格）：

```json
{
  "name": "search_docs",
  "description": "检索内部文档库，返回最相关的段落。",
  "parameters": {
    "type": "object",
    "properties": {
      "query": { "type": "string", "minLength": 1 },
      "top_k": { "type": "integer", "minimum": 1, "maximum": 10 }
    },
    "required": ["query"]
  }
}
```

执行器在真正调用工具前，应做最少但关键的防线：

- 参数校验：类型、范围、必填字段、长度。
- 权限校验：该 Agent 是否允许访问此工具、此资源、此租户。
- 幂等与重试：对有副作用的工具要有 `idempotency_key` 或“先 dry-run 再 commit”的两阶段策略。
- 输出规整：把工具返回转换为可供 LLM 消化的 Observation（摘要 + 关键字段）。

## 3. 运行时闭环：从推理到执行的状态机

### 3.1 ReAct 风格的最小闭环

下面是一个“最小可复现”的 Agent Loop 伪代码，核心是：**每次只做一件事**，并把结果写回状态。

```python
def agent_loop(llm, tools, state, budget):
    while budget.ok():
        prompt = render_prompt(state)  # 只包含必要约束与最近观测
        decision = llm(prompt)         # 产出：final 或 tool_call

        if decision.type == "final":
            return decision.output

        tool = tools[decision.tool_name]
        args = validate(decision.args, tool.schema)  # 参数与权限校验
        result = tool.call(args)                     # 可能失败：超时、限流、业务错误

        state.append_observation(decision, result)   # 结构化记录，便于追踪与复盘
        budget.consume(decision, result)

    raise TimeoutError("exceeded budget")
```

要点：

- `state` 不能只堆对话文本，至少要结构化存：计划、步骤、工具调用、关键产物、验收标准。
- `budget` 必须存在：步数上限、时间上限、token 上限，否则闭环容易发散。

### 3.2 运行时数据结构建议

最少包含三类日志，方便定位问题：

- Decision Log：LLM 的输出（工具选择、参数、最终回答）。
- Tool Trace：工具输入、输出、耗时、错误码、重试次数。
- Artifact：代码 diff、生成文件、SQL 变更、外部系统写入记录等。

工程经验：**不要依赖“把所有东西原样塞回上下文”**。要做摘要与裁剪，否则上下文膨胀会导致成本飙升与注意力稀释。

### 3.3 终止条件与验收标准

终止条件要可编程，而不是“感觉差不多了”：

- 达成 DoD（比如：单元测试通过、文档生成、接口返回 200 且断言通过）。
- 达到预算上限（步数、时间、成本）。
- 检测到不可恢复错误（权限不足、资源不存在、工具长期失败）。

## 4. 记忆与 RAG：把外部知识接入决策链路

### 4.1 RAG 的位置：解决“知识缺口”，不解决“推理缺口”

RAG（Retrieval-Augmented Generation）更像是 Agent 的一个工具：当 LLM 需要外部知识时，先检索再生成。

- 知识缺口：模型不知道某个内部规范或最新业务规则。
- 推理缺口：模型不知道如何把已知信息组合成正确结论。

RAG 主要补的是前者。把 RAG 当成“防幻觉银弹”会失败，因为检索也可能返回噪声或不相关段落。

### 4.2 一个可落地的 RAG 调用链

1. Query Rewrite：把用户问题改写成适合检索的查询（可选）。
2. Retrieval：向量检索 Top-K（可混合关键词检索）。
3. Rerank：用交叉编码器或规则重排，提升相关性。
4. Grounding：把引用段落附带来源，喂给 LLM 生成回答。

面试追问常见点：如何降低“检索到但没用上”的情况。

- 控制上下文：只放最相关的少量段落，并对每段写 1 句摘要。
- 强化约束：要求回答必须基于引用内容，必要时输出“无法从资料得出”。

## 5. 架构模式：单 Agent 与多 Agent

### 5.1 单 Agent：简单直接，但容易“又想又做”

单 Agent 的优点是链路短、成本低。缺点是容易出现：

- 计划与执行混杂，导致中途偏航。
- 工具调用缺乏边界，出现越权或副作用。

常见改进：把“规划”与“执行”拆成两个阶段，或拆成两个角色（Planner / Executor）。

### 5.2 多 Agent：角色分工与协作协议

多 Agent 常见组织方式：

- 角色分工：研究员（检索）、方案设计（规划）、执行器（工具）、审阅者（评审）。
- 分层控制：上层 Manager 负责拆任务与分发，下层 Worker 执行并回报。
- 争辩与投票：多个 Agent 给出候选，再由 Judge 选择或融合。

多 Agent 的核心不在“多”，而在**协作协议**：

- 输入输出格式（结构化而非纯自然语言）。
- 共享记忆的读写规范（谁能写、写什么、何时写）。
- 冲突解决策略（优先级、投票、回滚重试）。

### 5.3 多 Agent 的常见坑

- 交流开销：Agent 越多，上下文与成本越高。
- 责任不清：问题发生后难以定位是哪个角色引入错误。
- 循环争论：没有硬终止条件会导致“讨论不收敛”。

## 6. 工程化落地要点：让 Agent 可控、可用、可运维

### 6.1 输出约束：结构化优先于长文本

能结构化就不要自然语言，尤其是：

- 工具参数：用 JSON 严格约束字段。
- 计划：用列表或 `steps[]` 结构，标出 `status` 与 `acceptance_criteria`。
- 最终答案：按模板输出，避免“想到哪写到哪”。

### 6.2 可靠性：重试、幂等、回滚

工具失败是常态，不是异常：

- 超时：设置超时 + 指数退避重试；必要时降级（换数据源、降低 Top-K）。
- 业务错误：把错误码与错误信息写入 Observation，触发重规划，而不是继续硬跑。
- 副作用：写操作必须考虑幂等；必要时用两阶段提交（dry-run / commit）或补偿事务。

### 6.3 安全：提示注入与最小权限

Agent 安全的关键是“工具层”而不是“嘴上说遵守规则”：

- 工具白名单 + 参数黑白名单（比如禁止任意 SQL、禁止任意文件路径）。
- 最小权限：分租户、分资源授权；敏感工具独立审批。
- 提示注入防护：把外部内容（网页、文档）作为“不可信输入”标记，禁止其覆盖系统指令。

### 6.4 评估与监控：没有指标就无法迭代

建议至少监控：

- 任务成功率、平均步数、平均 token 成本、工具失败率。
- 检索命中率（Top-K 中是否包含正确段落）、回答引用率（引用是否被用到）。
- 关键路径耗时（LLM 延迟、工具延迟、重试耗时）。

## 7. 常见面试追问

### 7.1 Agent 如何降低幻觉

- 通过工具与 RAG 补齐事实输入（Grounding），让模型“基于证据回答”。
- 对关键结论做校验（规则校验、二次检索、执行结果断言）。
- 允许回答“不知道”，并把“不确定”转成下一步检索或实验。

### 7.2 工具调用失败怎么办

- 把失败当 Observation 写回，让模型重规划，而不是重复同一个动作。
- 对可重试错误做退避重试，对不可重试错误做降级或换方案。
- 对写操作保证幂等，并记录操作日志，必要时可回滚或补偿。

### 7.3 多 Agent 一定更好吗

- 不一定。多 Agent 提升的是“覆盖面”和“互相校验”，但会引入沟通成本与不收敛风险。
- 只有当任务可拆分、角色边界清晰、协作协议明确时，多 Agent 才会显著收益。
