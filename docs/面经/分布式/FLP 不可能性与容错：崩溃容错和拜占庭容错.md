## 1. 什么是 FLP 不可能性

### 1.1 结论（面试可背）

FLP 不可能性（Fischer、Lynch、Paterson，1985）指出：在**纯异步网络模型**下，只要允许**至少 1 个节点崩溃（Crash Failure）**，就不存在能够保证“总能终止并达成一致”的**确定性共识算法**。

关键词拆解：

- 纯异步：消息延迟没有上界，调度不可预测。
- 崩溃故障：节点可能停止响应（不作恶、不乱发消息）。
- 不可能性：不是“很难”，而是“在该模型假设下无法保证”。

### 1.2 它不否认什么

FLP 不否认工程上能做出可用的共识系统，它否认的是在“纯异步 + 确定性 + 允许崩溃”的组合下，算法能同时保证：

- Safety：不产生矛盾结果（例如两个不同的值都被决定）。
- Liveness：最终一定能决定（不会无限卡住）。

大多数共识协议选择：**永远保证 Safety**，在极端网络下可能牺牲 Liveness（表现为超时、不可用、反复选举）。

## 2. FLP 对工程实践意味着什么

### 2.1 你必须引入额外假设或机制

常见三条路：

1. 部分同步（Partial Synchrony）：在“最终网络会变好”的假设下保证最终可用（许多工程共识协议的经典假设）。
2. 失败检测器（Failure Detector）：用超时推测故障，允许误判，但在误判消失后系统可收敛。
3. 随机化（Randomization）：用随机选择打破对抗性调度（理论上绕开“确定性”限制）。

### 2.2 解释“为什么需要超时、重试、选举”

在异步网络里你无法区分：

- 对方真的宕机了。
- 对方只是网络慢。

所以工程上用超时触发：

- 重试与降级。
- leader 选举与切换。
- 复制追赶与回放。

面试加分点：把 FLP 讲成“**无法从网络沉默中得出确定结论**”，因此超时只是启发式，而不是数学证明。

### 2.3 解释“为什么共识在极端情况下会变慢或不可用”

例如 leader 租约过期、心跳抖动导致频繁选举，系统表现为：

- 写不可用或长时间超时。
- 延迟剧烈抖动（P99 拉长）。

这不是实现差，而是模型约束下的必然代价：要保 Safety，就可能牺牲 Liveness。

## 3. 容错模型：崩溃容错（CFT）与拜占庭容错（BFT）

### 3.1 崩溃容错（Crash Fault Tolerance，CFT）

故障模型：

- 节点最多“停止工作”或“失联”，但不会主动作恶（不伪造消息、不发送矛盾消息）。

典型协议与系统：

- Raft、Paxos（大多数工程落地的共识属于 CFT）。

副本数量直觉（多数派）：

- 允许容忍 `f` 个崩溃故障，通常需要 `2f + 1` 个副本，才能保证多数派仍存在。

### 3.2 拜占庭容错（Byzantine Fault Tolerance，BFT）

故障模型：

- 节点可能任意行为：撒谎、伪造、双发、选择性丢包、发送不同视图给不同节点等。

典型协议与系统：

- PBFT、HotStuff 等（常见于联盟链、跨组织协作、强对抗环境）。

副本数量直觉：

- 若要容忍 `f` 个拜占庭故障，经典结论需要 `3f + 1` 个副本，才能在投票/交叉验证中压住作恶者影响。

### 3.3 CFT 与 BFT 的核心差别

| 维度 | CFT | BFT |
| --- | --- | --- |
| 故障假设 | 只会崩溃/失联 | 任意作恶 |
| 代价 | 协议更简单、性能更高 | 消息轮次更多、计算更重（签名/验证） |
| 副本数 | 通常 `2f + 1` | 通常 `3f + 1` |
| 典型场景 | 数据库、配置中心、服务治理 | 跨组织、强对抗、区块链、关键基础设施 |

## 4. 适用场景怎么选（面试回答思路）

### 4.1 大多数公司内部系统：优先 CFT

原因：

- 节点通常在同一组织控制下，作恶风险较低。
- 性能与复杂度更可控。

常见组合：

- CFT 共识保证元数据一致（如选主、配置）。
- 数据层通过副本 + 事务/日志保证正确性。

### 4.2 跨组织协作或强对抗环境：考虑 BFT

判断标准：

- 参与方互不信任或存在利益冲突。
- 节点可能被攻破并恶意响应。
- 需要在恶意节点存在下仍保证安全性。

代价要明确说出来：

- 更高延迟与更低吞吐。
- 更复杂的密钥管理与证书体系。
- 更复杂的运维与故障定位。

## 5. 常见面试追问

### 5.1 “Raft 能解决拜占庭问题吗”

不能。Raft 默认节点不会作恶，它只能处理崩溃与网络问题。要应对拜占庭，需要额外的签名、仲裁与 BFT 协议，不能简单“加一层重试”解决。

### 5.2 “我们为什么通常不做 BFT”

合理回答：

- 风险模型不匹配：内部系统主要是崩溃故障。
- 成本不匹配：性能与复杂度代价太高。
- 业务可接受：通过权限、审计、隔离、入侵检测来降低作恶概率，比直接上 BFT 更划算。
