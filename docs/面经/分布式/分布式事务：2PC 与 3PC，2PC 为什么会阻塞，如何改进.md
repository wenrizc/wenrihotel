## 1. 2PC 是什么（Two-Phase Commit）

### 1.1 参与者与目标

2PC 解决的问题是：在多个资源管理器（RM，例如多个数据库）参与时，如何让一个分布式事务要么都提交，要么都回滚（原子性）。

角色：

- 协调者（Coordinator，TC）：负责推进事务阶段、收集投票、做最终决定。
- 参与者（Participant，RM）：执行本地事务并投票。

### 1.2 两个阶段

阶段 1：Prepare（投票阶段）

- TC 发送 `prepare` 给所有 RM。
- RM 执行本地事务到“可提交”状态（写 undo/redo、加锁但不提交），并返回：
  - `yes`：我已准备好，可以提交；
  - `no`：我无法提交，需要回滚。

阶段 2：Commit / Rollback（决策阶段）

- 若所有 RM 都 `yes`，TC 发送 `commit`。
- 否则 TC 发送 `rollback`。

面试关键词：`prepare` 后 RM 通常会**持有锁**，直到收到第二阶段指令。

## 2. 为什么 2PC 会阻塞

### 2.1 阻塞点：RM 进入“不知道最终结果”的中间态

在 2PC 中，一旦 RM 回复 `yes` 并进入 prepared 状态，它就处在：

- 本地不能自行提交（必须听 TC 的 commit）。
- 也不能自行回滚（否则违反全局原子性）。

如果此时发生：

- TC 崩溃；
- 或者 TC 与部分 RM 之间网络分区；

那么 prepared 的 RM 就会**一直持锁等待**，导致：

- 相关数据行/表锁长期占用；
- 其他事务被阻塞；
- 整体吞吐下降甚至雪崩。

因此 2PC 被称为阻塞协议（Blocking Protocol）。

### 2.2 还有哪些工程问题

- 单点问题：TC 是故障放大点（需要高可用）。
- 性能问题：两轮网络往返 + 强制日志落盘。
- 恢复复杂：崩溃恢复要依据日志决定重试 commit/rollback。

## 3. 3PC 是什么（Three-Phase Commit）

### 3.1 3PC 如何试图减少阻塞

3PC 在 2PC 的基础上引入一个中间阶段（常见叫 PreCommit）并加入超时机制，目标是：

- 让参与者在某些超时场景下能做出更“安全”的本地决策，减少无限等待。

常见三阶段：

1. CanCommit：询问是否可提交（类似投票意向）。
2. PreCommit：参与者进入可提交状态，并确认。
3. DoCommit：最终提交。

### 3.2 3PC 的前提：更强的网络假设

3PC 需要更接近“同步系统”的假设（例如消息延迟有上界）才能保证安全性与活性。

在真实的异步网络里（延迟无上界），3PC 仍可能在分区与超时误判下出现问题，因此工程上并不如 2PC 普遍。

## 4. 如何改进 2PC（工程上的常见做法）

### 4.1 让协调者高可用：复制 TC 状态

思路：

- 把事务的决策状态（prepare 结果、commit/rollback 决定）写入一个高可用存储或复制日志。
- TC 崩溃后由新 TC 接管并根据持久化状态继续推进。

注意：这只能降低 TC 单点导致的“无限阻塞”，但无法从根本上消除“分区下等待”的代价。

### 4.2 用共识替代 2PC 的核心决策点

更强的做法是把“事务提交决定”放到共识日志里：

- 让 commit/abort 决策本身成为多数派一致的结果。

这类思路常被称为“共识提交（Consensus on Commit）”，本质是在用 Raft/Paxos 的复制日志增强 2PC 的协调者可靠性。

### 4.3 业务层替代：TCC / SAGA / Outbox

当强事务代价过大时，常用弱化一致性换取可用性与性能：

- TCC：Try / Confirm / Cancel，强调可补偿。
- SAGA：长事务拆成一串本地事务 + 补偿事务。
- Transactional Outbox：本地事务写业务表 + outbox 表，再异步投递消息，避免“双写不一致”。

面试建议：说明“哪些场景必须强一致事务，哪些场景可以业务补偿”，不要一把梭。

## 5. 常见面试追问

### 5.1 2PC 能不能保证一致性

在故障可恢复、日志可靠、参与者正确实现的前提下，2PC 能保证原子性，但代价是阻塞与高延迟。

### 5.2 2PC 和分布式锁有什么关系

两者都在“跨节点互斥/原子性”上发力：

- 2PC 解决多资源的事务原子提交。
- 分布式锁解决对共享资源的互斥访问。

它们都可能引入阻塞，并都需要考虑超时、重试、幂等与恢复。
