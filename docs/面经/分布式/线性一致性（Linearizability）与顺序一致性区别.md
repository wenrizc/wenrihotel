## 1. 两句话先给结论

### 1.1 结论

- 线性一致性（Linearizability）：**既要求单线程语义，也要求遵守真实时间（real-time）先后**，因此更强。
- 顺序一致性（Sequential Consistency）：只要求存在一个“全局单序”能解释所有线程的操作，但**不要求与真实时间一致**，因此更弱。

面试一句话：**顺序一致性只关心“有没有一种顺序能解释”，线性一致性还要满足“这个顺序不能违背真实时间”。**

## 2. 顺序一致性（Sequential Consistency）

### 2.1 形式化直觉

顺序一致性要求：所有线程的操作可以被排列成一个全局顺序，并且：

- 每个线程内部的程序顺序（program order）不被打乱。
- 每个读操作读到的值，必须来自该全局顺序中它之前最近一次写入。

注意：它不要求“某个操作在真实时间上发生得更早，就必须排在全局顺序更前”。

### 2.2 体验示例（允许“看起来反直觉”）

如果客户端 A 的写在真实时间上早于客户端 B 的读完成，但系统仍可能让 B 读到旧值，只要存在某个全局顺序能解释（例如把 A 的写排到 B 的读之后）。

## 3. 线性一致性（Linearizability）

### 3.1 形式化直觉

线性一致性要求：每个操作都可以被“线性化”到一个时间点（linearization point），形成一个全局顺序，并且：

- 满足顺序一致性的两条约束（单线程语义 + 可解释的读值）。
- 还必须满足 real-time order：如果操作 X 在真实时间上完成早于操作 Y 开始，那么 X 必须在全局顺序中排在 Y 之前。

### 3.2 体验：写成功后立刻全局可见

在对外承诺线性一致性时：

- 如果写返回成功，那么任何之后开始的读都不应读到旧值。
- 这就是很多人把它当作“强一致”的原因。

## 4. 一个经典对比例子（用来解释区别）

### 4.1 场景设定

对同一个寄存器 `x`，初始值为 `0`：

1. 客户端 A 执行 `write(x=1)`，并且**返回成功**。
2. 随后客户端 B 执行 `read(x)`，返回 `0`。

### 4.2 这在顺序一致性下可能成立

只要我们选择一个能解释的全局顺序：

- 把 `read(x)->0` 排在 `write(x=1)` 之前。

顺序一致性不关心真实时间上 A 是否已经结束，只关心是否存在某个顺序能解释。

### 4.3 这在线性一致性下一定不成立

因为 A 的写已经完成，B 的读在 A 完成之后才开始，real-time 约束要求写必须排在读之前，因此读不可能返回 `0`。

## 5. 工程系统里怎么用这两个概念

### 5.1 为什么 CAP 里的 C 常用线性一致性来定义

在“对外像单副本”的语境里，如果不要求 real-time，那么很多看似“读到旧值”的情况也能被某个顺序解释，导致一致性的承诺变得太弱，不利于讨论分区取舍。

所以 CAP 讨论 C 时，常采用线性一致性或等价的强一致语义作为标杆。

### 5.2 常见系统的对外承诺（面试表达建议）

你可以按“默认读写路径”描述：

- leader 读写 + 多数派提交：更接近线性一致性（仍取决于读路径是否严格走 leader、是否有 lease 等）。
- 读从库 / 异步复制：通常不是线性一致，可能也不是顺序一致（不同客户端看到顺序不同）。

关键点：不要只报系统名，要说明**读写路径与失败场景**。
