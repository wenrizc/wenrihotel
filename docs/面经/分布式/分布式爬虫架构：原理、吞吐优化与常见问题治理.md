## 1. 分布式爬虫是什么，解决什么问题

分布式爬虫（Distributed Web Crawler）是把“URL 发现、调度、抓取、解析、存储”拆成可横向扩展的组件，并通过共享的任务队列、去重系统与状态存储把多台机器协同起来完成采集。

它主要解决三类问题：

- 吞吐与覆盖：单机带宽、连接数、CPU、内存有限，无法在目标时间窗口内抓完。
- 稳定与容灾：单点故障、机器重启、网络抖动会导致任务丢失或重复。
- 治理与合规：对站点限速、代理池、账号池、审计与追踪，需要系统化能力。

## 2. 典型框架与落地形态

“分布式爬虫框架”通常不是指某一个库，而是一套可组合的工程栈。常见形态可以按执行模型分为三类：

- Worker Pool + 统一调度：调度中心负责 URL frontier（待抓队列）与策略，Worker 负责下载与解析，结果写入存储。
- 基于消息队列的流水线：fetch、parse、persist 分成多个 consumer group，通过 `Kafka` / `RabbitMQ` 串联，天然背压与重放。
- 流处理拓扑：把抓取与解析建模成 DAG（例如 fetch bolt、parse bolt、dedup bolt），适合持续流式抓取。

工程上常见的组合（举例，不限定语言）：

- URL 调度：Redis / RocksDB / DB 表 / MQ topic（按优先级与 host 分区）
- 去重：Bloom Filter + KV、或直接落库唯一键兜底
- 抓取：支持连接池、超时、重试、代理、TLS、HTTP/2（视目标站点）
- 存储：对象存储（原始 HTML）、搜索（倒排）、数据仓库（结构化结果）

## 3. 分布式爬虫的核心组件拆解

### 3.1 URL Frontier（任务队列）

Frontier 负责“待抓 URL 的排序与分发”，通常需要同时满足：

- 有界与背压：队列不能无限增长，否则风险转移到内存或磁盘。
- 优先级：站点优先级、页面类型优先级、增量抓取优先级。
- 分区：按 host / domain 分片，避免热点与利于礼貌性限速（politeness）。

### 3.2 Scheduler（调度器）

调度器的职责不是简单“出队”，而是把策略落到工程约束：

- per-host 并发与 QPS 限制（避免把对方打挂或触发封禁）
- 失败退避（指数退避 + 抖动）与熔断（短时间失败过多暂停该 host）
- 任务租约（lease）：防止 Worker 挂掉导致任务永久丢失

### 3.3 Fetcher（下载器）

下载器关注“网络正确性与资源上限”：

- 连接池上限、超时（connect/read/deadline）、重试边界
- DNS 缓存与失败策略
- 代理池与账号池的分配、隔离与健康检查

### 3.4 Parser（解析器）

解析器关注“从内容到结构化数据”的确定性与可重放：

- 解析必须幂等：同一份内容重复解析，不应产生不同结果
- 解析失败要可定位：记录内容版本、解析规则版本、错误样本
- 提取新 URL（link extraction）要可控：避免 URL 爆炸

### 3.5 Dedup（去重系统）

去重分两层：

- URL 去重：避免重复抓取同一 URL（或同一归一化后的 URL）。
- 内容去重：不同 URL 可能返回相同内容（镜像站、参数不同但内容一致）。

分布式场景下通常接受 **at-least-once 抓取 + 幂等落库**，即抓取端允许重复，但结果端用唯一键或版本控制避免数据污染。

### 3.6 Storage（存储与索引）

建议把“原始内容”与“结构化结果”分开存：

- 原始内容：用于复现、回放解析、审计（例如保存 HTML、响应头、抓取时间、代理信息）。
- 结构化结果：用于检索与分析（DB、搜索引擎、数仓）。

## 4. 端到端工作流程（带租约的任务状态机）

建议用显式状态机描述任务生命周期，避免靠“日志推断系统状态”：

- `PENDING`：待调度
- `LEASED`：已分配给某个 Worker（有租约过期时间）
- `SUCCESS`：抓取并持久化完成
- `RETRYABLE_FAIL`：可重试失败（带 next_run_at）
- `DEAD`：重试耗尽，进入死信

关键点：

- Worker 拉取任务时获取租约，处理完成后 ack。
- 租约到期未 ack，任务回到 `PENDING` 或进入重试队列。
- 任务必须有 `attempt` 与 `deadline`，避免无限重试。

```java
// 仅示意：用租约避免 worker 崩溃导致任务丢失；用 deadline 避免无限重试。
record CrawlTask(String url, long taskId, int attempt, long deadlineMs) {}
```

## 5. 如何提高数据采集量（吞吐优化手段与边界）

“采集量”不是单纯把线程数调大。更有效的优化顺序是：先消除明显浪费，再扩大并发，再扩容机器。

### 5.1 先把每次请求变“更便宜”

- 连接复用：开启连接池与 keep-alive，避免每次握手。
- 压缩与解压控制：请求 `Accept-Encoding`，但解析侧要考虑 CPU 成本。
- 减少无效抓取：robots、黑名单、URL 归一化、参数规则、去重。
- 增量抓取：只抓变化页面；用 `ETag` / `If-Modified-Since`（目标站支持时）。

### 5.2 让并发变得“可控且不互相拖死”

- per-host 限并发：比全局限并发更关键。
- 拆分线程池或执行器：fetch 与 persist 分离，避免落库慢拖死下载。
- 有界队列 + 背压：队列满时要降速，而不是继续堆内存。

### 5.3 让系统能“水平扩展”

- 任务分区：按 host / domain / hash 分区到不同 shard，减少热点。
- 数据分流：原始内容与结构化数据写不同存储，避免单点写入瓶颈。
- 批量写：落库与写对象存储尽量 batch，提高吞吐并减少连接数。

### 5.4 采集量的硬边界

- 目标站点容量与反爬策略：最终吞吐上限通常由对方限制决定。
- 代理池容量与质量：代理慢会把并发变成阻塞。
- 自己的网络出口：带宽与 NAT 端口、`TIME_WAIT` 规模都会成为瓶颈。

## 6. 分布式爬虫常见问题与解决方案

### 6.1 重复抓取与漏抓（调度一致性问题）

#### 6.1.1 根因

- 去重与入队不是原子操作（check-then-act）。
- 多个调度节点之间没有一致视图，产生重复分发。
- Worker 异常退出，租约恢复策略不正确导致漏抓或重复。

#### 6.1.2 解决

- 将“去重决策”前移：入队前先做 URL 归一化与去重。
- 用租约 + ack：保证任务最终会被重新分配。
- 结果端幂等：落库唯一键兜底，容忍重复抓取。

### 6.2 热点与倾斜（某些 host 抢占大量资源）

#### 6.2.1 根因

- URL 分布不均：大站点链接密集，小站点稀疏。
- 分区策略不合理：hash 不能体现 host 维度限速，或导致单分区过热。

#### 6.2.2 解决

- host 维度队列：每个 host 一个子队列，调度器按权重轮询。
- 动态权重：根据错误率、RT、429 比例对 host 降权。
- 多级队列：`high/normal/low` 三档，防止低价值 URL 挤占资源。

### 6.3 被封禁与验证码（反爬对抗引发的系统问题）

#### 6.3.1 根因

- 并发与请求模式过于“机器化”：固定间隔、固定 UA、无 Cookie 演化。
- 未识别限流信号：429、`Retry-After`、403 激增。

#### 6.3.2 解决

- 自适应降速：按 host 的 429/403 比例触发降速与熔断。
- 资源池隔离：代理、账号、Cookie 分组，坏组快速下线。
- 策略可回滚：解析规则、请求头策略要支持灰度与回滚。

### 6.4 重试风暴（失败越多压力越大）

#### 6.4.1 根因

- 失败立即重试，且全局同步重试导致尖峰。
- 不区分错误类型，4xx 也被当作可重试。

#### 6.4.2 解决

- 指数退避 + 抖动，且设置最大重试次数与最大总耗时。
- 失败分流：可重试进延迟队列，不可重试进死信队列。
- 熔断：某 host 在窗口期内错误率超阈值暂停调度。

### 6.5 背压缺失导致 OOM（队列无限增长）

#### 6.5.1 根因

- frontier、解析队列、落库队列无界，生产速度大于消费速度。
- 落库慢把任务堆在内存，最终拖垮整个集群。

#### 6.5.2 解决

- 全链路有界：每一段队列都必须有上限。
- 降级策略：只存原始内容，延迟解析；或只存结构化字段，丢弃大文本。
- 按成本丢弃：低优先级任务在资源紧张时丢弃或延后。

### 6.6 一致性与“恰好一次”（Exactly-once 幻觉）

#### 6.6.1 事实

分布式系统中“端到端 exactly-once”通常很昂贵，且对爬虫这种天然可重试任务收益有限。更常见的正确工程目标是：

- 抓取端：at-least-once（可能重复）
- 结果端：幂等（不会因为重复而污染数据）

#### 6.6.2 实现要点

- 唯一键：`url_hash` 或业务主键唯一索引。
- 版本控制：按 `fetch_time` 或内容版本只允许新覆盖旧。
- 原始内容留存：用于事后重放解析修复历史数据。

### 6.7 任务停止与恢复（可治理性）

#### 6.7.1 解决

- 支持三种停止语义：
  - 停止接收新任务（stop accepting）
  - 排空队列后退出（drain）
  - 立即停止（hard stop）
- 断点恢复靠“持久化 frontier + 租约状态机”，不要只靠内存队列。

## 7. URL 归一化与去重策略（实战细节）

### 7.1 URL 归一化（Normalization）

归一化的目标是把“语义相同但字符串不同”的 URL 映射到同一个 canonical 形式：

- scheme/host 大小写、默认端口（80/443）
- path 的 `.`、`..` 规整
- query 参数排序与过滤（删掉 `utm_*` 等跟踪参数）
- fragment（`#...`）通常不参与请求，可直接移除

### 7.2 去重方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- |
| 集合去重（KV 存完整 key） | 精确 | 存储大、写放大 | 中小规模、强准确 |
| Bloom Filter | 空间效率高、吞吐高 | 有误判（false positive） | 大规模 URL 粗去重 |
| 落库唯一键兜底 | 结果一致性强、实现简单 | 抓取端仍可能浪费带宽 | 强幂等结果写入 |

建议组合：

- 抓取前：Bloom Filter 做粗去重减少浪费
- 落库时：唯一索引做硬兜底防污染

## 8. 面试落地：给一个“最小可用”的分布式爬虫设计

### 8.1 组件

- `Kafka`：`crawl_tasks`（待抓）、`crawl_results`（解析结果）、`crawl_dlq`（死信）
- `Redis`：Bloom Filter 位图或 URL 去重 KV（可选）
- `Worker`：拉取任务，抓取后把原始响应与提取的结构化结果写入
- `Storage`：对象存储保存原始 HTML，DB 保存结构化字段（唯一索引幂等）

### 8.2 数据流

1. seed 注入 `crawl_tasks`
2. Worker 消费任务，按 host 限并发抓取
3. 解析提取新 URL，做归一化与去重后再投递 `crawl_tasks`
4. 结果写入存储，失败按策略进延迟重试或 `crawl_dlq`

### 8.3 关键治理点

- host 限速与熔断（避免 429/403 风暴）
- 全链路有界队列（避免 OOM）
- 任务状态可追踪（taskId、attempt、traceId）
- 幂等写入（唯一键 + 版本控制）

## 9. 面试追问清单

1. 为什么分布式爬虫更推荐“抓取允许重复，结果幂等”，而不是全局强去重？

3. 队列满了怎么办？你是阻塞、丢弃、降级还是落盘？依据是什么？

5. 解析规则更新后，如何重放历史原始内容来修复数据？
