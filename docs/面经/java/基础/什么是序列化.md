## 1. 核心概念

序列化（Serialization）是把**内存中的对象状态**转换为一种可传输或可持久化的表示形式（通常是 `byte[]` 或文本）的过程；反序列化（Deserialization）则是把该表示形式恢复为内存对象的过程。

“序列化”通常关注三件事：对象如何被编码、版本如何兼容演进、反序列化是否安全。

常见用途包括：

- **网络传输**：RPC、消息队列消息体、HTTP JSON 响应体。
- **持久化**：落盘快照、缓存（如 Redis value 存对象的编码）。
- **跨进程/跨机器复制**：把对象图复制到另一个 JVM 或另一台机器上。

需要明确的边界：

- 序列化是“编码对象状态”，不是“拷贝对象引用”。对象图中的共享引用、循环引用需要协议显式表达。
- “可用”不代表“适合”。Java 原生序列化在性能、可演进性、安全性上都有明显代价。

## 2. Java 原生序列化

在 Java 中，通常说的“序列化”特指 `java.io` 提供的对象序列化协议：对象实现 `Serializable`（标记接口）后，通过 `ObjectOutputStream` 写出，通过 `ObjectInputStream` 读回。

### 2.1 `Serializable` 的语义边界

`Serializable` 本身不定义方法，它的意义是“允许按 Java 对象序列化协议进行编码”。默认规则可以概括为：

- 会序列化：**非 `static`、非 `transient`** 的实例字段。
- 不会序列化：`static` 字段（类级别状态）、`transient` 字段（显式排除）、以及通过自定义逻辑跳过的字段。
- 继承链：父类如果**未实现** `Serializable`，反序列化时会调用该父类的**无参构造器**来初始化父类部分；父类如果实现了 `Serializable`，其字段也会走序列化协议。

### 2.2 最小可复现示例

```java
import java.io.*;

public class Demo {
  static final class User implements Serializable {
    private static final long serialVersionUID = 1L;

    private String name;
    private transient String password; // 不会被序列化

    User(String name, String password) {
      this.name = name;
      this.password = password;
    }
  }

  public static void main(String[] args) throws Exception {
    byte[] data;
    try (var baos = new ByteArrayOutputStream();
         var oos = new ObjectOutputStream(baos)) {
      oos.writeObject(new User("alice", "p@ss"));
      oos.flush();
      data = baos.toByteArray();
    }

    try (var bais = new ByteArrayInputStream(data);
         var ois = new ObjectInputStream(bais)) {
      User u = (User) ois.readObject();
      System.out.println(u.name);      // alice
      System.out.println(u.password);  // null（transient 未恢复）
    }
  }
}
```

## 3. 协议层：对象图如何被编码

Java 原生序列化不是简单把字段拼成字节，而是写入一个带类型信息的协议流：包括流头、类描述符、字段描述、对象句柄（handle）等。

### 3.1 入口类与关键方法

从源码结构上看，核心入口就是：

- 写出：`ObjectOutputStream#writeObject(Object)`
- 读入：`ObjectInputStream#readObject()`

它们内部会：

- 为每个对象分配 handle，保证共享引用和循环引用在反序列化后仍能保持拓扑结构。
- 写入/读取 `ObjectStreamClass`（类的序列化元信息），用于字段匹配、`serialVersionUID` 校验、兼容性判断。

### 3.2 对象引用与循环引用

Java 原生序列化会维护一张“对象到 handle”的表：

- 首次遇到对象：写 `TC_OBJECT`（新对象）并记录 handle。
- 再次遇到同一对象：写 `TC_REFERENCE`（引用已写过的 handle）。

因此它可以正确表达：

- 同一对象被多个字段引用（共享引用不被复制成两个对象）。
- 对象互相引用形成环（不会无限递归写出）。

这也是它比“手写把字段写成 JSON”更“像对象图”的地方，但同时也带来额外的协议开销与复杂度。

### 3.3 `serialVersionUID` 的意义

`serialVersionUID` 是 Java 原生序列化的“版本号”。反序列化时，如果流里的类版本号与本地类的版本号不一致，通常会抛出 `InvalidClassException`，属于典型线上兼容性故障。

实践建议：

- **显式声明** `private static final long serialVersionUID = ...;`，不要依赖编译器计算的默认值（改动字段、方法签名等都可能导致默认值变化）。
- 把它当作“协议版本”，配合字段演进策略一起使用，而不是当作摆设。

### 3.4 流头与常见 tag（定位线上问题很有用）

Java 原生序列化流以固定头部开始，常见特征是魔数 `0xAC ED` 与版本号 `0x00 05`。

对象与类型信息通过一组常量 tag 编码（在 JDK 中集中定义于 `ObjectStreamConstants`），例如：

- `TC_OBJECT`：一个新对象实例。
- `TC_CLASSDESC`：类描述符（字段列表、`serialVersionUID` 等）。
- `TC_REFERENCE`：指向已出现过的对象或类描述符的 handle。

这也是“为什么 Java 原生序列化能处理循环引用，但体积往往更大”的直接原因：它在流里携带了大量对象图与类型系统信息。

## 4. 兼容性：类演进时会发生什么

### 4.1 常见演进动作与结果

| 演进动作 | 典型结果 | 备注 |
| --- | --- | --- |
| 新增字段 | 新字段取默认值（引用为 `null`，数值为 `0`） | 前提是 `serialVersionUID` 兼容 |
| 删除字段 | 老数据里的该字段被忽略 | 读入后对象里自然不存在 |
| 修改字段类型 | 可能失败或产生不可预期结果 | 多数情况下会报错或数据损坏 |
| 改类名/包名 | 失败 | 类名是类型标识的一部分 |

### 4.2 父类未实现 `Serializable` 的坑

当父类未实现 `Serializable` 时，反序列化不会从字节流恢复父类字段，而是调用父类无参构造器重建父类部分。这会导致：

- 父类字段取构造器初始化值，而不是序列化前的值。
- 父类无参构造器如果缺失，会反序列化失败。

这类问题在“把某个基类改成不再可序列化”或“引入新基类”时尤其常见。

### 4.3 `serialPersistentFields`：显式声明可序列化字段集合

当你需要“序列化字段白名单”，或需要在不改动真实字段的情况下维持序列化协议稳定性时，可以通过声明 `serialPersistentFields` 来控制默认序列化看到的字段集合。

工程含义是：你在把“类的内部表示”与“对外序列化协议”解耦，避免因为一次重构（字段改名、拆分、合并）就把线上存量数据全打崩。

## 5. 自定义序列化：控制协议与不变量

默认序列化经常不满足需求，例如要加密敏感字段、压缩、跳过缓存字段、维持不变量等。Java 原生序列化提供了多个扩展点。

### 5.1 `transient`：显式排除字段

`transient` 适用于：

- 密码、密钥等敏感信息（但更建议根本不要用 Java 原生反序列化处理不可信输入）。
- 可重建字段，例如缓存、派生字段、连接句柄。

反序列化后需要自己恢复时，可以在自定义 `readObject` 中重建。

### 5.2 `writeObject` / `readObject`：定制字段写入与校验

当类定义了私有方法 `writeObject(ObjectOutputStream)` 与 `readObject(ObjectInputStream)`，`ObjectOutputStream` / `ObjectInputStream` 会优先调用它们。

```java
private void writeObject(ObjectOutputStream out) throws IOException {
  out.defaultWriteObject(); // 写默认字段
  // out.writeInt(extra);   // 写扩展字段（注意版本兼容）
}

private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
  in.defaultReadObject();   // 读默认字段
  // 这里可以做不变量校验，否则非法数据会直接进入对象状态
  // if (age < 0) throw new InvalidObjectException("age < 0");
}
```

经验点：

- `defaultWriteObject` / `defaultReadObject` 决定了“默认字段集合”的写入与恢复，省掉大量重复代码。
- 自定义写入扩展字段时，相当于你在自建子协议，需要配套考虑版本演进与兼容读取。

### 5.3 `readResolve` / `writeReplace`：替换对象实例

`writeReplace` 允许在写出前把对象替换为另一个代表对象；`readResolve` 允许在读入后把对象替换为另一个实例。典型用途：

- 单例：反序列化后用 `readResolve` 返回同一个单例实例，避免破坏单例语义。
- 代理对象：写出更稳定的“序列化代理”（Serialization Proxy Pattern），避免直接暴露内部表示与不变量。

### 5.4 `Externalizable`：完全接管序列化

`Externalizable` 提供 `writeExternal` / `readExternal`，你需要手写全部字段的读写逻辑，并且必须提供 `public` 无参构造器。

它的优点是可控，缺点是：

- 易错：字段顺序、兼容性、缺字段默认值都需要你自己维护。
- 仍然是 Java 原生反序列化通道，安全风险并不会凭空消失。

## 6. 性能与工程取舍

Java 原生序列化的工程问题通常集中在：体积大、速度慢、GC 压力大、难演进。

### 6.1 为什么它通常更慢

常见原因包括：

- 协议写入了大量类型与类元信息（类描述符、字段描述等），不是纯数据编码。
- 读写过程中会做反射、访问控制、对象分配与 handle 表维护。
- 对象图复杂时，临时对象与中间结构会增加 GC 压力。

### 6.2 工程建议

- JVM 内部对象复制：优先考虑明确的拷贝策略（拷贝构造、手写复制、MapStruct），不要用序列化当“万能深拷贝”。
- RPC 与消息：优先使用 Protobuf、Thrift、Avro 这类有 schema 的二进制协议，或 JSON（可读性优先）。
- 缓存：缓存层存 `byte[]` 时，明确选用可控的编码（JSON、Protobuf、Kryo 等），避免把 Java 原生序列化当成默认值。

## 7. 安全性：反序列化为什么危险

Java 原生反序列化的风险点在于：`readObject` 过程可以触发复杂对象图构造与类加载，并执行一些类在反序列化路径上的逻辑。若输入数据不可信，可能被构造为“恶意对象图”，触发高危问题。

### 7.1 风险类型

- 远程代码执行（RCE）：经典问题是“gadget chain”，利用类库中已有的可利用链条在反序列化期间执行危险操作。
- 拒绝服务（DoS）：构造超大对象图、深层嵌套、哈希碰撞等导致 CPU、内存耗尽。
- 业务绕过：通过篡改字段值破坏对象不变量，导致鉴权或状态机被跳过。

### 7.2 防护策略

优先级从高到低：

1. **根本性方案：不要对不可信输入使用 Java 原生反序列化**，改用安全可控的协议（JSON、Protobuf 等）。
2. 必须用时：启用反序列化过滤（如 JDK 的 `ObjectInputFilter`），做类型白名单与对象图大小限制。
3. 对关键对象：使用“序列化代理模式”，在 `readObject` 或 `readResolve` 中做严格不变量校验。

一个最小示例（只允许反序列化业务包下的类型，并限制深度与引用数）：

```java
import java.io.ObjectInputFilter;
import java.io.ObjectInputStream;

ObjectInputStream ois = ...;
ObjectInputFilter filter = ObjectInputFilter.Config.createFilter(
    "maxdepth=20;maxrefs=5000;com.example.**;!*");
ois.setObjectInputFilter(filter);
```

## 8. 横向对比：Java 原生序列化、JSON、Protobuf、Kryo

| 维度 | Java 原生序列化 | JSON | Protobuf | Kryo |
| --- | --- | --- | --- | --- |
| 跨语言 | 差 | 好 | 好 | 差（偏 JVM 生态） |
| 可读性 | 差 | 好 | 差 | 差 |
| 性能与体积 | 一般偏差 | 一般 | 好 | 通常较好 |
| 兼容性治理 | 易踩坑 | 取决于字段策略 | schema 驱动更清晰 | 依赖注册与版本策略 |
| 安全性 | 高风险（不可信输入） | 相对更可控 | 相对更可控 | 取决于使用方式 |
