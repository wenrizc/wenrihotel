## 1. 注解是什么

注解（Annotation）是 Java 语言提供的一种“元数据机制”：把结构化信息绑定到类、方法、字段、参数、类型使用处等程序元素上。**注解本身不会直接改变业务逻辑**，它需要被编译器、构建工具或框架读取后，才会产生实际效果。

从实现角度看，注解是一种受 Java 虚拟机（Java Virtual Machine，JVM）与编译器共同约束的语法结构：源码里写的是 `@Xxx(...)`，编译后会把注解信息写入 `.class` 文件的属性（attribute）中，运行期可通过反射读取（取决于保留策略）。

## 2. 注解和“注释、配置”有什么区别

- 注释：仅给人看，不参与编译语义（忽略 Javadoc 工具这类“读注释的程序”）。
- 配置：通常是外部文件或集中化配置中心，强调环境可变与动态调整。
- 注解：代码内的结构化元数据，强调“与代码同行、可被工具解析”，适合表达约束、声明式规则与框架契约。

工程上常见的边界是：**与实现强绑定、需要代码审查的规则用注解**；与环境强绑定、需要动态变更的参数用配置。

## 3. 注解类型如何定义：`@interface`

### 3.1 最小可复现示例

```java
import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
public @interface Audited {
    String value() default ""; // 约定：value 支持简写
    int level() default 1;
}
```

使用时：

```java
@Audited("order") // 等价于 @Audited(value = "order")
public class OrderService {

    @Audited(level = 2)
    public void pay() {}
}
```

### 3.2 注解元素（Element）的类型限制

注解里的“参数”本质上是无参方法（元素），返回类型受到 Java 语言限制，常见合法类型：

- 基本类型：`int`、`boolean` 等。
- `String`。
- `Class`：如 `Class<?>`。
- `enum`。
- 注解类型本身（嵌套注解）。
- 以上类型的一维数组。

**不能出现 `null` 值**：注解元素要么有默认值，要么使用时必须显式赋值。

### 3.3 注解在字节码层面是什么

注解类型在字节码里会被编译成一个接口，并隐式继承 `java.lang.annotation.Annotation`。运行期你通过反射拿到的注解对象，通常是 JDK 生成的动态代理实例，它会按规范实现 `equals`、`hashCode`、`toString` 与 `annotationType()`。

这一点的面试落点是：**注解不是“运行期执行的代码”，而是“可被读取的结构化数据”**。

## 4. 元注解（Meta-Annotation）：控制注解的语义边界

### 4.1 `@Target`：注解能标到哪里

`@Target` 用 `ElementType` 限定注解的使用位置，常见取值：

- `TYPE`：类、接口、枚举、注解类型。
- `METHOD`、`FIELD`、`PARAMETER`、`CONSTRUCTOR`。
- `ANNOTATION_TYPE`：标在注解上（做元注解）。
- `PACKAGE`、`MODULE`。
- `TYPE_PARAMETER`：类型参数，如 `class Box<@A T> {}`。
- `TYPE_USE`：类型使用处，如 `List<@A String>`、`@A String s`。

`TYPE_USE` 是 Java 8 引入的能力，常用于空值分析、序列化约束等“类型系统扩展”场景。

### 4.2 `@Retention`：注解信息保留到什么时候

`@Retention` 决定注解是否进入 `.class`，以及运行期反射能否读到：

| 保留策略 | 是否进 `.class` | 反射是否可见 | 典型用途 |
| --- | --- | --- | --- |
| `SOURCE` | 否 | 否 | 仅给编译器或集成开发环境（Integrated Development Environment，IDE）用，如 `@Override`、`@SuppressWarnings` |
| `CLASS` | 是 | 否（默认） | 供字节码工具使用，运行期通常不读取 |
| `RUNTIME` | 是 | 是 | 运行期框架读取，如 Spring、JPA、Jackson |

选择原则：**能不用 `RUNTIME` 就不要滥用 `RUNTIME`**，否则会放大类扫描与反射读取的成本。

### 4.3 `@Documented`、`@Inherited`、`@Repeatable`

- `@Documented`：生成 Javadoc 时把该注解也写进文档。
- `@Inherited`：只对“类级别注解”生效，子类通过 `Class#getAnnotations()` 可以继承到父类的注解；对方法、字段、接口都不生效。
- `@Repeatable`：允许同一个位置重复标注同一种注解，编译器会用一个“容器注解”把多次出现的注解包起来。

`@Repeatable` 示例：

```java
import java.lang.annotation.Repeatable;

@Repeatable(Tags.class)
public @interface Tag {
    String value();
}

public @interface Tags {
    Tag[] value();
}
```

使用时：

```java
@Tag("a")
@Tag("b")
class Demo {}
```

## 5. 注解在 `.class` 文件里如何存储（JVM 视角）

编译器会把注解编码进 class 文件的属性（attribute）。不同保留策略对应不同属性：

- `RetentionPolicy.RUNTIME`：写入 `RuntimeVisibleAnnotations`（以及参数、类型相关的可见属性）。
- `RetentionPolicy.CLASS`：写入 `RuntimeInvisibleAnnotations`（仍在 class 文件中，但反射默认看不到）。
- `RetentionPolicy.SOURCE`：不写入 class 文件。

与注解相关的常见属性名包括：

- `RuntimeVisibleAnnotations` / `RuntimeInvisibleAnnotations`
- `RuntimeVisibleParameterAnnotations` / `RuntimeInvisibleParameterAnnotations`
- `RuntimeVisibleTypeAnnotations` / `RuntimeInvisibleTypeAnnotations`
- `AnnotationDefault`（注解元素的默认值）

### 5.1 如何验证：`javap -v`

```shell
javac Demo.java
javap -v Demo.class | findstr /I "RuntimeVisibleAnnotations RuntimeInvisibleAnnotations AnnotationDefault"
```

你会在 `javap -v` 输出里看到对应的 attribute 段落，从而直观确认“注解到底有没有进字节码”。

## 6. 运行期如何读取注解：反射与代理对象

### 6.1 反射入口：`AnnotatedElement`

`Class`、`Method`、`Field`、`Constructor`、`Parameter` 等都实现了 `java.lang.reflect.AnnotatedElement`，提供：

- `getAnnotation(Class<T>)`：拿单个注解（可能为 `null`）。
- `getDeclaredAnnotation(Class<T>)`：只看当前元素，不看继承。
- `getAnnotationsByType(Class<T>)`：支持 `@Repeatable` 的“展开”读取。

### 6.2 注解对象的本质

反射返回的注解对象通常不是你手写的实现类，而是 JDK 在内部生成的动态代理。它把“注解元素值”存为一份键值映射，并按 Java 语言规范（Java Language Specification，JLS）规定的语义实现：

- `equals`：同类型且所有元素值相等才相等。
- `hashCode`：按元素名与元素值计算。
- `toString`：类似源码形式的字符串。

理解这一点有助于解释一些现象：注解读取是“解析 + 构造代理对象”的过程，而不是“执行某段注解代码”。

### 6.3 性能与缓存

JDK 会对解析出的注解做缓存，但“扫描类路径、枚举方法、逐个反射读取”仍然可能很贵。框架（例如 Spring）通常会在自己的层面再做缓存，并提供“合并元注解”的更高层 API（Application Programming Interface，应用程序接口），例如合成注解与别名属性。

## 7. 编译期注解处理：Java Specification Request（JSR） 269（Annotation Processing，注解处理）

如果注解的目标是“生成代码或做编译期校验”，更常用 JSR 269 注解处理器，而不是运行期反射。

### 7.1 处理器在 `javac` 里的位置

`javac` 编译通常会经历“多轮（round）处理”：处理器读取本轮的注解与语法树信息，可以生成新的 `.java` 源文件；如果生成了新源文件，编译器会触发下一轮处理，直到不再产生新文件为止。

### 7.2 典型应用

- 代码生成：MapStruct、QueryDSL 等。
- 编译期校验：自定义规则检查、API 约束验证。
- 资源索引生成：为运行期框架减少扫描成本（典型是生成元数据文件）。

注意：Lombok 更接近“编译器插件 + AST 改写”，虽然也与注解相关，但不完全等价于纯 JSR 269 的处理模型。

## 8. 框架如何使用注解（以 Spring 为例）

Spring 把注解当作配置与规则的统一入口：

- 组件模型：`@Component` 及其派生（`@Service`、`@Controller`）通过扫描注册 Bean。
- AOP 能力：`@Transactional`、`@Cacheable` 等会转换成 `Advisor`，在运行期由代理织入。
- 组合注解：一个注解可以“元标注”另一个注解，Spring 会按规则把它们合并解析。

常见坑：

- 忘记写 `@Retention(RUNTIME)`：框架通过反射读不到注解。
- 注解标在实现类方法上，但你在接口方法上读注解（或被 JDK 代理拦截到的是接口方法）：需要明确“你到底在读哪个 `Method`”。
- 误以为 `@Inherited` 能继承方法注解：它只对类注解生效。

## 9. 设计与最佳实践

- 把注解当成“公共 API”：一旦被框架或团队约定依赖，就要谨慎变更元素名与默认值。
- 元素尽量用 `enum` 或 `Class` 表达，避免大量 `String` 造成拼写与重构风险。
- 运行期读取的注解尽量少、尽量集中，并做好缓存；不要在高频路径上反射读取。
- 选择合适的 `@Retention`：仅编译期规则用 `SOURCE`，只给字节码工具用可选 `CLASS`，必须运行期读取才用 `RUNTIME`。
- 避免把“业务数据”塞进注解：注解适合表达规则与标记，不适合承载频繁变化的配置。

## 10. 总结

- 注解是 Java 的元数据机制，必须被工具或框架读取后才产生效果。
- `@Target` 控制“能标到哪儿”，`@Retention` 控制“能保留到哪儿”，这是注解语义的两条主线。
- 注解信息会写入 class 文件 attribute，运行期反射读到的通常是 JDK 生成的代理对象。
- 编译期用 JSR 269 做“校验/代码生成”，运行期框架用反射做“规则驱动”，两者适用场景不同。
