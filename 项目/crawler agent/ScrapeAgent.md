
### **技术方案：AI驱动的人机协作Web爬虫Agent**

#### 1. 项目目标

本项目旨在解决传统Web爬虫开发中耗时、繁琐且高度依赖开发经验的核心痛点。通过构建一个由大型语言模型（LLM）驱动的智能Agent，我们期望达成以下目标：

*   **核心问题**: 自动化从需求理解到代码生成的全过程，将原先数小时甚至数天的开发工作缩短至分钟级别。
*   **业务价值**:
    *   **提升效率**: 极大加速数据采集项目的启动和迭代速度。
    *   **降低门槛**: 使非专业开发者（如数据分析师、产品经理）也能通过自然语言完成简单的数据抓取任务。
    *   **标准化输出**: 确保生成的代码遵循统一的、高质量的编码规范。
*   **期望目标**: 用户通过一个命令行界面（CLI），输入目标URL和抓取需求（如“获取所有产品的名称、价格和评分”），Agent即可通过人机协作，最终生成一个可独立运行的Python爬虫脚本。

#### 2. 需求概述

##### 2.1 功能需求

1.  **任务输入**: 支持用户通过CLI输入目标网页URL和自然语言描述的抓取需求。
2.  **自动化分析**: Agent能自动加载目标页面，并智能分析其DOM结构和网络请求。
3.  **数据源推荐**: Agent能自动发现潜在的数据源（页面HTML或后台API），并根据与用户需求的关联度进行排序和推荐。
4.  **交互式映射**: 用户可以在Agent的引导下，对数据字段和数据源中的具体内容（通过JSONPath或CSS Selector）进行可视化预览和确认。
5.  **人机协作微调**: 支持用户对Agent自动生成的字段映射方案进行自然语言微调（例如，“去掉价格前面的货币符号”）。
6.  **代码生成**: 最终生成一个完整、可读、带注释的Python爬虫脚本（基于`requests`或`Playwright`）。
7.  **任务持久化与恢复**: 用户可以随时中断任务，并在之后从上次中断的地方无缝恢复。

##### 2.2 非功能需求

1.  **可靠性 (Reliability)**: Agent必须能够稳定处理动态加载内容（SPA）、网络超时等复杂情况，不能轻易崩溃或无限等待。
2.  **可用性 (Usability)**: CLI交互界面必须清晰、直观，引导性强，用户能够轻松理解Agent的状态和下一步操作。
3.  **可扩展性 (Extensibility)**: 架构设计应易于扩展，方便未来增加新的工具（如登录、验证码处理）、支持新的LLM模型或集成新的数据输出格式。
4.  **可维护性 (Maintainability)**: 代码结构清晰，模块化程度高，并采用强类型约束，以降低长期维护成本。
5.  **性能 (Performance)**: 在保证智能的同时，Agent的响应时间应在可接受的交互范围内。特别是分析阶段，应避免不必要的长时间等待。
6.  **安全性 (Security)**: Agent在本地环境中运行，用户数据（如Cookie、抓取内容）不应被发送到不必要的外部服务。生成的代码应清晰可读，无恶意注入。

#### 3. 系统架构设计 (总体设计)

##### 3.1 架构图

```
+---------------------------------------------------------------------------------+
|                                     USER (CLI)                                  |
+---------------------------------------^-----------------------------------------+
                                        | (Input/Output via Rich & Questionary)
+---------------------------------------v-----------------------------------------+
|  交互层 (Presentation Layer)                                                    |
+---------------------------------------------------------------------------------+
                                        | (State updates, commands)
+---------------------------------------v-----------------------------------------+
|  核心逻辑层 (Core Logic Layer) - [LangGraph State Machine]                      |
|                                                                                 |
|  +---------------------+   +---------------------+   +-----------------------+  |
|  | Node: analyze_page  |-->| Node: present_choice|-->| Node: map_fields      |->| ...
|  +---------------------+   +---------------------+   +-----------------------+  |
|          |                         ^       |                      ^             |
|          | (Invoke Tool)           |       | (Invoke Tool)        |             |
|          v                         |       v                      |             |
|  +---------------------------------+------------------------------------------+ |
|  | 执行引擎层 (Execution Engine)  <------> 大语言模型层 (LLM Layer)          | |
|  |  - Playwright Wrapper           |      |  - Small Model (Scoring)         | |
|  |  - DOM Distiller                |      |  - Large Model (Generation)      | |
|  |  - API Discovery Filter         |      +----------------------------------+ |
|  +---------------------------------+                                           |
+-----------------^---------------------------------------------------------------+
                  | (Read/Write State & Artifacts)
+-----------------v---------------------------------------------------------------+
|  持久化子系统 (Persistence Subsystem)                                           |
|  +-----------------------------+      +---------------------------------------+ |
|  | State Store (SQLite)        |      | Artifact Store (Local File System)    | |
|  | - AgentState Checkpoints    |      | - ./workspace/{thread_id}/page.html   | |
|  +-----------------------------+      | - ./workspace/{thread_id}/api_1.json  | |
|                                       +---------------------------------------+ |
+---------------------------------------------------------------------------------+
```

##### 3.2 模块划分

*   **交互层 (Presentation Layer)**: 负责所有与用户的直接交互。使用`Rich`库渲染格式化的输出，使用`Questionary`库获取用户的交互式输入。
*   **核心逻辑层 (Core Logic Layer)**: 系统的指挥中心。使用`LangGraph`构建一个状态机（StateGraph），定义了任务从开始到结束的所有步骤（节点）和转换逻辑（边）。它管理`AgentState`对象，并调用其他层来完成具体工作。
*   **执行引擎层 (Execution Engine Layer)**: 负责与外部世界（浏览器）的交互。封装了`Playwright`，提供如“健壮地加载页面”、“监听网络请求”、“执行DOM蒸馏”等原子能力。
*   **大语言模型层 (LLM Layer)**: 提供封装好的、可插拔的LLM调用接口。分为两种角色：用于快速分类/打分的小模型接口，和用于高质量内容生成的大模型接口。
*   **持久化子系统 (Persistence Subsystem)**: 一个跨层服务，由两部分组成：
    *   **状态存储**: 使用LangGraph的`SqliteSaver`，自动将`AgentState`对象持久化到SQLite数据库。
    *   **工件存储**: 一个自定义的文件管理器，负责将大型数据（HTML, JSON）存放在与任务`thread_id`关联的本地文件夹中。

##### 3.3 关键流程：从用户需求到爬虫代码

1.  **启动**: 用户在**交互层**输入URL和需求。**核心逻辑层**创建一个`AgentState`实例，并启动LangGraph工作流，进入`analyze_page`节点。
2.  **分析**: `analyze_page`节点调用**执行引擎**。引擎加载页面（采用双层等待策略），捕获网络流量，并执行API发现（启发式+小模型打分）。同时，执行引擎将原始HTML和候选API响应作为“工件”存入**持久化子系统**。
3.  **决策**: 流程进入`present_choices`节点。**核心逻辑层**从`AgentState`读取候选数据源，通过**交互层**呈现给用户。用户做出选择。
4.  **映射**: 流程进入`map_fields`节点。**核心逻辑层**将用户选择的数据源（从工件存储中读取）和需求，发送给**LLM层**的大模型，请求生成字段映射规则（JSONPath/CSS Selectors）。
5.  **确认与微调**: **核心逻辑层**根据映射规则，调用**执行引擎**提取预览数据，并通过**交互层**展示给用户。如果用户不满意，可以输入微调指令，流程将带着新指令返回`map_fields`节点，形成闭环。
6.  **生成**: 用户确认映射后，流程进入`generate_code`节点。**核心逻辑层**整合所有上下文信息，调用**LLM层**的大模型生成最终的Python脚本，并存入**持久化子系统**。任务结束。

#### 4. 详细设计

*   **交互层**: 实现一组标准化的UI函数，如`display_status(message)`, `ask_for_choice(options)`, `show_table(data)`，供核心逻辑层调用。
*   **核心逻辑层**: `StateGraph`包含`start`, `analyze`, `simplify_dom`, `present_choices`, `map_fields`, `generate_code`等节点。节点之间通过条件边（Conditional Edges）连接，根据`AgentState.status`进行路由，以实现重试和微调循环。
*   **执行引擎层**: 提供`BrowserManager`类，封装Playwright的启动和关闭。提供`robust_load_page()`函数实现双层等待。提供`DOMDistiller`类实现HTML到简化JSON的转换。提供`APIFilter`类实现两阶段API发现。
*   **LLM层**: 提供`LLMClient`基类，并为Gemini、OpenAI等提供具体实现。该客户端封装了API调用、重试逻辑和结构化输出的验证（使用Pydantic）。

### **当前爬虫 Agent 项目的 LangGraph 设计详解**

#### 1. LangGraph 整体架构: **单一状态机 Agent (Single Stateful Agent)**

首先，最核心的架构决策是：我们当前采用的是**单一的、拥有复杂内部状态的Agent架构**，而不是多Agent系统。

*   **为什么是单一Agent？**
    *   **线性但循环的工作流**: 爬虫生成的任务本质上是一个有先后顺序的流程（分析->决策->映射->生成），但其中包含反馈循环（微调）。这种模式用一个状态机来建模是最高效、最清晰的。
    *   **共享上下文**: 整个任务过程高度依赖一个统一的、不断演进的上下文（`AgentState`）。从分析页面得到的DOM，到用户选择的API，再到最终的字段映射，这些信息需要被无缝地、连贯地传递。在单一Agent中，这通过共享的`AgentState`自然实现。而在多Agent系统中，你需要设计复杂的Agent间通信协议来传递这些上下文，增加了不必要的复杂性。
    *   **明确的控制流**: 单一状态机Agent的路径是可预测和可控的。我们能精确地定义从`analyze_page`到`present_choices`的流程。多Agent系统通常更适用于任务可以被分解成多个**并行**或**独立**子任务的场景，而我们的场景是**串行依赖**的。

#### 2. 核心逻辑模式: **状态驱动的规划与执行 (State-Driven Planning & Execution)**, 而非 ReAct

这是一个非常关键的区别。我们的Agent**不采用**纯粹的ReAct（Reasoning-Action）模式。

*   **ReAct模式是什么？**
    ReAct是一种非常微观的循环模式：LLM进行**思考(Thought)** -> LLM决定执行一个**动作(Action)** -> 执行动作并返回**观察(Observation)** -> LLM接收观察并开始新一轮的**思考**。这个循环非常紧密，通常用于需要LLM进行多步、自主探索的开放式任务（例如，让Agent自己上网查资料回答一个复杂问题）。

*   **我们的模式为什么不同？**
    我们的Agent是**状态驱动的宏观规划**。
    1.  **预定义的规划**: 整个工作流（规划）已经被我们预先定义为LangGraph中的节点和边。Agent不会在运行时“即兴”决定下一步是分析还是生成代码。
    2.  **节点即“宏观动作”**: LangGraph的每个节点（如`analyze_page`）可以被看作一个**宏观的、预设的Action**。
    3.  **LLM是“顾问”而非“指挥官”**: LLM在我们的系统中不直接决定下一步做什么。相反，它被特定的节点调用，以完成一项**咨询任务**（例如，在`map_fields`节点中，LLM被调用来“思考”如何生成字段映射）。LLM的输出是数据（映射规则），而不是下一个要执行的动作。
    4.  **状态驱动流转**: 流程的跳转（例如，从映射返回微调）是基于`AgentState`中的`feedback`字段，由我们编写的确定性代码（路由函数）来决定的，而不是由LLM的“思考”来决定的。

**总而言之，我们的Agent更像一个拥有AI增强能力的自动化流水线，而不是一个拥有自主意识的探索者。** 这种设计为我们的特定任务（生成爬虫）带来了更高的可靠性、可预测性和效率。

#### 3. 子 Agent 设计 (当前阶段: 无)

基于上述单一Agent的架构，**当前设计中不包含任何子Agent**。

我们没有`AnalystAgent`或`CoderAgent`。取而代之的是，我们将这些专业职责实现为**专门的节点**和**工具**，并由单一的、统一的LangGraph工作流进行调度。

*   `AnalystAgent`的职责被`analyze_page`, `simplify_dom`, `present_choices`等节点以及它们调用的工具所承担。
*   `CoderAgent`的职责被`generate_code`节点及其调用的代码生成工具所承担。

这种方式在当前阶段更轻量、更易于管理。未来的演进方向可以是，当某个节点（如`analyze_page`）的内部逻辑变得极其复杂时，再考虑将其重构为一个独立的、由主Agent调用的子Agent。

#### 4. MCP 工具的理解与应用

在我们的项目中，“MCP工具”这个术语需要被正确地理解。我们**没有**在技术上实现一个标准的MCP（Model Context Protocol）服务器或客户端。

然而，我们完全采纳了MCP的**核心思想**：为Agent提供一个标准化的、与外部世界交互的接口。在我们的架构中，这个接口就是**Agent的工具箱 (Toolbox)**。

因此，当问及“需要配置哪些MCP工具”时，我们应该理解为“**Agent的工具箱中需要包含哪些核心的工具方法？**”

#### 5. Agent 的核心工具箱 (Toolbox) 与方法详解

这些工具是**执行引擎层**和**LLM层**提供的、可被LangGraph节点调用的具体Python函数。它们是Agent能力的直接体现。

##### **工具1: `robust_load_page_and_capture_requests`**

*   **函数签名**: `def robust_load_page_and_capture_requests(url: str) -> Tuple[Optional[str], List[Dict]]`
*   **核心职责**: 健壮地加载目标页面，并捕获在此期间发生的所有网络请求。
*   **调用者**: `analyze_page` 节点。
*   **实现细节**:
    *   内部启动一个Playwright Page实例。
    *   注册一个`page.on("response", ...)`事件监听器，将所有响应的URL、状态码、响应头和响应体（`response.json()`或`response.text()`）捕获到一个列表中。
    *   调用`page.goto(url, wait_until='networkidle', timeout=60000)`，实现我们讨论的双层等待策略。
    *   返回页面的HTML内容和捕获到的网络请求列表。

##### **工具2: `distill_dom_to_json`**

*   **函数签名**: `def distill_dom_to_json(html_content: str, page: Page) -> Dict`
*   **核心职责**: 执行“面向LLM的语义DOM蒸馏与标注流水线”，将庞大的原始HTML转化为小巧、结构化的JSON。
*   **调用者**: `simplify_dom` 节点。
*   **实现细节**:
    *   遵循我们详细讨论的四阶段流水线：基础清理 (BeautifulSoup) -> 可见性剪枝 (结合Playwright的`is_visible()`) -> 语义标注 (添加`data-agent-id`) -> 序列化为嵌套的JSON对象。

##### **工具3: `filter_and_score_apis`**

*   **函数签名**: `def filter_and_score_apis(requests: List[Dict], user_prompt: str) -> List[Dict]`
*   **核心职责**: 执行两阶段API发现，从原始网络请求中筛选并排序出与用户需求最相关的API。
*   **调用者**: `analyze_page` 节点。
*   **实现细节**:
    *   **阶段一**: 实现一个硬编码的过滤器，根据Content-Type、状态码、URL后缀等规则进行快速粗筛。
    *   **阶段二**: 将粗筛后的API（截断的JSON体）和用户需求构建成一个Prompt，调用**小模型（Gemini Flash）**，并要求其以指定的JSON格式返回每个API的相关性得分和理由。

##### **工具4: `request_field_mappings_from_llm`**

*   **函数签名**: `def request_field_mappings_from_llm(data_source_content: Union[Dict, str], source_type: str, user_prompt: str) -> Dict`
*   **核心职责**: 请求大模型为指定的数据源（API的JSON或简化的HTML DOM）生成字段映射规则。
*   **调用者**: `map_fields` 节点。
*   **实现细节**:
    *   构造一个详细的Prompt，清晰地指示LLM：如果`source_type`是`'api'`，则生成JSONPath；如果是`'html'`，则生成基于`data-agent-id`的CSS Selectors。
    *   调用**大模型（Gemini Pro / GPT-4o）**。
    *   使用Pydantic模型来验证LLM返回的JSON结构，确保其格式的正确性。如果验证失败，可以触发一个带错误信息的重试循环。

##### **工具5: `extract_preview_data`**

*   **函数签名**: `def extract_preview_data(data_source: Union[Dict, str], mappings: Dict[str, str]) -> Dict`
*   **核心职责**: 根据生成的映射规则，从数据源中提取前几条数据作为预览，以便展示给用户确认。
*   **调用者**: `decide_after_mapping` 路由之前的节点（例如 `present_mapping_preview`）。
*   **实现细节**:
