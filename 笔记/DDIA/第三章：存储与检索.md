
## 驱动数据库的数据结构

### 1. 最简单的数据库模型
-   **原理**：一个仅追加（append-only）的日志文件。
-   **操作**：
    -   `db_set`：直接在文件末尾追加键值对。
    -   `db_get`：从文件尾部向前扫描，找到最后一次出现的键。
-   **性能特征**：
    -   写入极快（顺序写入）。
    -   读取极慢（O(n)复杂度，随数据量线性增长）。
-   **结论**：为了高效查找，需要引入**索引（Index）**。

### 2. 索引的基本概念
-   **定义**：从主数据衍生的附加结构，作为路标加速查找。
-   **权衡（Trade-off）**：精心设计的索引能加快读取速度，但会拖慢写入速度（因为每次写入都要更新索引）。因此数据库默认不索引所有内容。

## 存储引擎架构

### 1. 哈希索引（Hash Indexes）
-   **典型代表**：Bitcask（Riak的默认引擎）。
-   **原理**：
    -   内存中维护一个哈希表（Key -> 文件偏移量）。
    -   数据文件是只追加的日志。
    -   读取时：查内存哈希表找到偏移量 -> 磁盘一次寻址读取数据。
-   **日志压缩与合并（Compaction & Merging）**：
    -   为了防止日志无限增长，将日志分为**段（Segment）**。
    -   后台线程对旧段进行压缩：丢弃覆盖的旧值，只保留每个键的最新值。
    -   合并：将多个压缩后的段合并成新文件，合并后删除旧文件。
-   **实现细节**：
    -   删除记录：写入一个特殊的墓碑记录（Tombstone）。
    -   崩溃恢复：定期将内存哈希表快照存入磁盘，加速重启。
    -   并发控制：通常单个写线程，多个读线程。
-   **局限性**：
    -   **内存限制**：所有键必须能放入内存（值可以放磁盘）。
    -   **范围查询效率低**：无法高效扫描 `kitty00000` 到 `kitty99999`，只能逐个查找。

### 2. SSTables 与 LSM-Tree（日志结构合并树）
这是对哈希索引局限性的改进。

#### SSTable (Sorted String Table)
-   **特点**：键值对在文件中是**按键排序**的。
-   **优势**：
    1.  **合并高效**：类似归并排序（Merge Sort），并发读取多个段，顺序写入新段。
    2.  **稀疏索引**：不再需要内存保存所有键，只需保存部分键（如每几KB保存一个）的偏移量。通过二分查找确定范围。

#### 构建与维护流程（LSM-Tree 工作原理）
1.  **写入**：先写入内存中的平衡树结构（如红黑树），称为 **内存表（Memtable）**。
2.  **落盘**：当Memtable达到阈值，将其作为SSTable文件转储到磁盘。
3.  **读取**：先查Memtable -> 查最新的SSTable段 -> 查次新的SSTable段...
4.  **后台**：定期执行压缩和合并。

#### 崩溃恢复
-   Memtable在内存中，断电会丢失。
-   **解决方案**：写入Memtable前，先追加写入一个**预写式日志（WAL）**。WAL仅用于恢复，落盘后即可删除。

#### 性能优化
-   **布隆过滤器（Bloom Filters）**：快速判断一个键是否**不**存在，减少对不存在键的磁盘查找开销。
-   **压缩策略**：
    -   **大小分层（Size-tiered）**：HBase使用。
    -   **分层压缩（Leveled compaction）**：LevelDB/RocksDB使用。

#### 应用案例
-   LevelDB, RocksDB, Cassandra, HBase, Lucene（全文索引）。

### 3. B树（B-Trees）
最广泛使用的索引结构（关系型数据库的标准）。

#### 结构特点
-   **页（Page）**：将磁盘划分为固定大小的块（通常4KB），通过页ID相互引用，形成树状结构。
-   **读写单位**：一次读写一个页面，贴合硬件设计。
-   **分支因子**：一个页面能包含的子页面引用数量（通常几百个），决定了树的高度极低（3-4层即可存储TB级数据）。

#### 操作流程
-   **查找**：从根页面开始，根据键范围指针逐层向下，直到叶子节点。
-   **更新**：找到对应叶子页，修改后写回磁盘。
-   **插入**：若页面空间不够，将页面**分裂**为两个半满页面，并更新父页面引用。

#### 可靠性与并发
-   **预写式日志（WAL / Redo Log）**：因为页面分裂可能涉及修改多个页面，若中途崩溃会导致索引损坏。必须先写WAL才能保证崩溃恢复。
-   **并发控制**：使用**锁存器（Latches）**保护树的数据结构。

#### 优化技术
-   **写时复制（Copy-on-write）**：不覆盖旧页，写入新位置（LMDB使用）。
-   **键压缩**：内部节点只存键的缩略信息，增加分支因子。
-   **兄弟指针**：叶子节点增加左右指针，利于顺序扫描。

| 特性        | LSM-Tree (日志结构)                  | B-Tree (原地更新)                     |
| :-------- | :------------------------------- | :-------------------------------- |
| **写入性能**  | **更高**。顺序写入，无须寻道。                | **较低**。随机写入，且每次需写整页（即使改1字节）+ WAL。 |
| **读取性能**  | **较慢**。可能需检查多个SSTable（布隆过滤器可缓解）。 | **更快**。键唯一存在于某处，寻址路径确定。           |
| **写放大**   | 较低（取决于压缩策略）。                     | 较高（WAL + 页重写）。                    |
| **碎片化**   | 较低。定期重写去除碎片。                     | 较高。页分裂导致磁盘空间未充分利用。                |
| **并发与事务** | 压缩过程可能引起延迟抖动（高百分位响应时间受影响）。       | 键锁定容易实现，事务支持更成熟。                  |
| **适用场景**  | 高吞吐写入。                           | 强一致性事务，高读取性能。                     |

## 其他索引结构

### 1. 二级索引（Secondary Indexes）
-   与主键索引不同，键不是唯一的。
-   **实现**：
    -   值是匹配行的列表。
    -   值是行的主键（再回表查询）。

### 2. 索引中的值存储
-   **堆文件（Heap File）**：索引只存引用，行数据乱序存在别处。避免多个索引重复存储数据。
-   **聚集索引（Clustered Index）**：行数据直接存储在索引的叶子节点中（如MySQL InnoDB的主键）。
-   **覆盖索引（Covering Index）**：索引中包含查询所需的所有列，无需回表。

### 3. 多列索引
-   **连接索引**：将多列组合成一个键（如“姓+名”）。
-   **多维索引**：用于地理空间数据（R树），支持二维范围查询（如经度+纬度）。

### 4. 全文搜索与模糊索引
-   **Lucene**：使用类似SSTable的结构存储词典，内存中使用有限状态自动机（FSA/Trie）加速查找。支持编辑距离搜索。

### 5. 内存数据库
-   **代表**：Redis, Memcached, VoltDB。
-   **优势**：省去了将内存数据结构编码为磁盘格式的开销（序列化/反序列化），而不仅仅是避免磁盘I/O。
-   **持久化**：通过快照、追加日志或特殊硬件（电池RAM）实现。
-   **反缓存（Anti-caching）**：内存不足时将冷数据写入磁盘。

## 事务处理（OLTP）与在线分析（OLAP）

### 1. 概念区分
-   **OLTP (Online Transaction Processing)**：
    -   用户：终端用户。
    -   操作：随机读写，低延迟，按键查找。
    -   数据量：GB到TB。
    -   瓶颈：磁盘寻道时间。
-   **OLAP (Online Analytic Processing)**：
    -   用户：数据分析师。
    -   操作：扫描大量记录，聚合计算（Sum, Count），只读为主。
    -   数据量：TB到PB。
    -   瓶颈：磁盘带宽。

### 2. 数据仓库（Data Warehouse）
-   **定义**：独立的数据库，包含所有OLTP系统的只读副本。
-   **ETL**：抽取（Extract）、转换（Transform）、加载（Load）。
-   **优势**：针对分析查询进行了优化，不影响业务系统。

### 3. 分析的数据模型
-   **星型模式（Star Schema）**：
    -   中心：**事实表**（Fact Table），每一行是一个事件，通常非常宽（100+列）。
    -   周围：**维度表**（Dimension Table），代表事件的人、地、时、物。
-   **雪花模式（Snowflake Schema）**：维度表进一步规范化（拆分）。通常星型模式更受青睐，因为更简单。

## 列式存储

### 1. 核心思想
数据仓库查询通常只访问表中的几列（如 `SELECT SUM(cost)`），而非整行。
-   **行存储**：将一行所有数据存一起。查询时需加载整行，浪费I/O。
-   **列存储**：将每一列的数据单独存储在一个文件中。查询时只加载需要的列。

### 2. 列压缩
列存储非常适合压缩，因为同一列的数据类型相同，重复度高。
-   **位图编码（Bitmap Encoding）**：适合基数（Cardinality）较小的列（如性别、产品类别）。
-   **游程编码（Run-length Encoding）**：适合稀疏位图。

### 3. 内存带宽与向量化处理
-   列存储能让CPU L1缓存容纳更多数据。
-   **SIMD（单指令多数据）**：利用现代CPU指令集，一次处理多个数据点。

### 4. 排序顺序
-   列存储也需要排序，通常由管理员指定排序键（如按日期）。
-   **多重排序**：类似C-Store/Vertica，复制数据副本并按不同键排序，以加速不同类型的查询。

### 5. 写入问题
-   列存储的就地更新很困难（这就需要重写整个列文件）。
-   **解决方案**：使用LSM-Tree架构。新写入在内存中处理，后台合并到磁盘列文件。

### 6. 聚合
-   **物化视图（Materialized View）**：预先计算好的查询结果副本。
-   **数据立方体（Data Cube）**：按不同维度预先聚合的网格。虽然查询极快，但缺乏灵活性。
