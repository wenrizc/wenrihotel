
## 1. 事务的定义与

### 1.1 为什么需要事务？

在数据系统的现实运行环境中，故障是常态而非异常。可能发生的情况包括：

- 数据库软件或硬件故障（如写入半截时宕机）。
    
- 应用程序崩溃。
    
- 网络中断（切断应用与数据库的联系）。
    
- 并发写入导致的覆盖。
    
- 部分更新导致的脏读。
    

为了解决这些问题，系统需要一种机制来简化编程模型。事务（Transaction）就是这种机制。它将多个读写操作组合成一个逻辑单元。

### 1.2 事务的核心承诺

事务提供了一种“安全保证”（Safety Guarantees），其核心逻辑是：要么全部成功（提交 Commit），要么全部失败（中止 Abort/回滚 Rollback）。

- 优势：应用程序无需处理“部分成功”的复杂状态。如果事务中止，应用只需重试即可。
    
- 代价：事务并非天然存在，它通过牺牲一定的性能和可用性来换取编程的简化和数据的一致性。
    

## 2. ACID 的深层含义

ACID 是原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）和持久性（Durability）的缩写。

### 2.1 原子性 (Atomicity)

- 定义：不可分割，**可中止性（Abortability）**。如果事务在执行过程中发生错误，数据库必须丢弃已进行的所有变更，回滚到事务开始前的状态。
    

### 2.2 一致性 (Consistency)

- 定义：数据库在事务前后都保持“良好状态”（符合不变量）。
    
- **补充**：一致性这个词在计算机领域有多种含义。
    
    - 副本一致性（分布式系统）。
        
    - 一致性哈希（分区算法）。
        
    - CAP 定理中的一致性（线性化）。
        
    - ACID 中的一致性（业务逻辑约束）。
        
- 本质：ACID 中的 C 实际上是**应用程序的属性**，而非数据库的属性。数据库可以辅助检查（如外键、唯一约束），但数据的逻辑正确性（如转账借贷平衡）依赖于应用代码。
    

### 2.3 隔离性 (Isolation)

- 定义：同时执行的多个事务互不干扰，相互隔离。
    
- 理想标准：**可序列化（Serializability）**。即并发执行的结果与串行（一个接一个）执行的结果完全相同。
    
- 现实情况：为了性能，大多数数据库默认使用较弱的隔离级别（如快照隔离、读已提交），这可能导致并发竞争条件（Race Conditions）。
    

### 2.4 持久性 (Durability)

- 定义：一旦事务提交，数据就不会丢失，即使发生硬件故障。
    
- 实现方式：
    
    - 单机：写入非易失性存储（硬盘/SSD）+ 预写日志（WAL）。
        
    - 分布式：复制到多个节点。
        
- 局限性：不存在完美的持久性（如所有硬盘同时损毁）。持久性是降低风险的手段，而非绝对保证。
    

## 3. 单对象操作与多对象事务

### 3.1 单对象写入

- 存储引擎通常为单个对象（如键值对、文档）提供原子性和隔离性。
    
- 技术手段：日志（用于崩溃恢复）、锁（用于隔离）。
    
- 原子自增（CAS）：比较并设置，防止丢失更新，但这通常被称为“轻量级事务”。
    

### 3.2 为什么需要多对象事务？

虽然部分 NoSQL 数据库放弃了多对象事务，但在许多场景下它是必需的：

- 关系模型：外键引用必须有效。
    
- 文档模型：更新非规范化的数据（因为缺乏 Join，数据可能由于冗余存储在多处）。
    
- 索引更新：修改数据时，必须同步更新二级索引，否则索引与数据不一致。
    

## 4. 隔离级别

并发 Bug 难以测试和重现，因此理解隔离级别至关重要。

### 4.1 读已提交 (Read Committed)

这是最基本的隔离级别，也是许多数据库的默认设置。它提供两个保证：

1. **无脏读（No Dirty Reads）**：只能读取已提交的数据。
    
    - 意义：避免看到部分更新的数据；避免看到回滚前的数据。
        
2. **无脏写（No Dirty Writes）**：只能覆盖已提交的数据。
    
    - 实现：行级锁（Row-level lock）。写事务持有锁直到提交，阻止其他写事务修改同一对象。
        

- **实现机制**：
    
    - 写锁：防止脏写。
        
    - 读操作：通常**不使用锁**（因为读锁会阻塞写，性能太差）。数据库会保留旧的已提交值，在写事务未提交前，读操作读取旧值。
        

### 4.2 快照隔离 (Snapshot Isolation) / 可重复读

- 解决的问题：读取偏差（Read Skew）或不可重复读。
    
    - 场景：Alice 转账，一个账户扣款完成，另一个未到账。此时若查看总余额，会发现钱少了（状态不一致）。
        
    - 对于备份和长耗时分析查询，这种不一致是不可接受的。
        
- **核心思想**：每个事务从数据库的一个**一致性快照**中读取。事务只能看到事务开始时已经提交的数据。
    
- **实现技术：多版本并发控制 (MVCC)**
    
    - 数据库不直接覆盖值，而是保留对象的多个版本。
        
    - **可见性规则**：
        
        1. 读事务开始时，创建该版本的事务必须已提交。
            
        2. 对象未被标记删除，或删除该对象的事务在读事务开始时尚未提交。
            
    - **关键点**：读不阻塞写，写不阻塞读。这对读多写少的负载极其有利。
        
- **命名混淆**：Oracle 将其称为“可序列化”，MySQL 和 PostgreSQL 将其称为“可重复读”。
    

### 4.3 防止丢失更新 (Lost Updates)

- **场景**：两个事务同时读取-修改-写入（Read-Modify-Write）同一数据（如计数器+1）。后提交的覆盖了先提交的修改。
    
- **解决方案**：
    
    1. **原子写操作**：如 `UPDATE ... SET value = value + 1`。通常是最好的选择。
        
    2. **显式锁定**：应用程序使用 `SELECT ... FOR UPDATE` 强制加锁。
        
    3. **自动检测**：数据库自动检测更新丢失并中止事务（PostgreSQL、Oracle 支持；MySQL InnoDB 的可重复读级别**不检测**）。
        
    4. **比较并设置 (CAS)**：`UPDATE ... WHERE content = 'old_content'`。
        
    5. **分布式冲突解决**：允许创建兄弟版本（Siblings），由应用层合并（如 Riak）或最后写入者胜（LWW，但这会丢失数据）。
        

### 4.4 写入偏差 (Write Skew) 与 幻读 (Phantoms)

- **写入偏差**：是丢失更新的一般化形式。
    
    - 场景：医生值班系统。规则是“至少有一人值班”。两人同时查询，发现都在值班，于是都请求休假。结果两人都休假了，无人值班。
        
    - 特征：两个事务读取相同的对象，但更新不同的对象（或对象的不同状态）。
        
    - 原因：事务依据一个**前提**（Premise）采取行动，但并发写入改变了这个前提。
        
- **幻读**：一个事务的写入改变了另一个事务的搜索查询结果（如行数变化、条件满足变化）。
    
    - 写入偏差通常是由幻读引起的。
        
- **解决方案**：
    
    1. 使用可序列化隔离级别。
        
    2. 显式锁定（`FOR UPDATE`）。
        
    3. **物化冲突 (Materializing Conflicts)**：如果因为查询结果为空而无法加锁，可以创建一个实体表（如时间槽表）来代表该冲突条件，并对其加锁。但这属于这种丑陋的妥协。
        

## 5. 可序列化 (Serializability)

这是最强的隔离级别，保证并发执行结果与串行执行一致。实现主要有三种方案：

### 5.1 真的串行执行 (Actual Serial Execution)

- **原理**：在单线程上按顺序一次执行一个事务。
    
- **可行性前提**：
    
    1. RAM 价格下降，数据可全内存驻留（避免磁盘 I/O 等待）。
        
    2. OLTP 事务通常很短。
        
- **实现**：VoltDB, Redis。
    
- **限制**：
    
    - 吞吐量受限于单核 CPU。
        
    - 必须使用**存储过程**封装事务逻辑，避免网络交互（交互式事务太慢）。
        
    - 跨分区事务性能极差。
        

### 5.2 两阶段锁定 (2PL, Two-Phase Locking)

- **原理**：**悲观并发控制**。
    
    - 读锁（共享锁）：允许多个读，但阻塞写。
        
    - 写锁（排他锁）：阻塞其他所有的读和写。
        
    - **区别**：快照隔离是“读写互不阻塞”，2PL 是“读阻写，写阻读”。
        
- **阶段**：
    
    1. 获取锁（事务执行中）。
        
    2. 释放锁（事务结束时）。
        
- **性能**：较差。吞吐量低，延迟不稳定，死锁频繁。
    
- **解决幻读**：
    
    - 需要**谓词锁 (Predicate Lock)**：锁定所有符合搜索条件的对象（包括未来可能插入的）。
        
    - **索引范围锁 (Index Range Locking / Next-key Locking)**：谓词锁的简化版。锁定索引上的一个范围（如时间段），即使该范围内还没有数据。这是大多数 2PL 数据库的实际做法。
        

### 5.3 可序列化快照隔离 (SSI, Serializable Snapshot Isolation)

- **原理**：**乐观并发控制**。
    
    - 基于快照隔离（MVCC），但在提交时进行检测。如果发现违背了可序列化原则，则中止事务。
        
- **检测机制**：
    
    1. **检测过时的 MVCC 读取**：事务提交时，检查它读取的数据是否被其他已提交事务修改过。
        
    2. **检测影响之前读取的写入**：利用索引范围记录事务的读取，当其他事务写入该范围时通知读取者（但不阻塞）。提交时检查是否有冲突通知。
        
- **优势**：
    
    - 读不阻塞写，写不阻塞读。
        
    - 对于争用不大、读多写少的场景，性能优于 2PL。
        
    - 支持跨分区事务（FoundationDB）。
        
- **现状**：PostgreSQL 9.1+ 的“可序列化”级别即采用 SSI。
