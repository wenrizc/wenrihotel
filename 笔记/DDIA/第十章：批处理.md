
### 2.1 三类数据系统的定义

*   **在线服务 (Services/Online)**：
    *   **特点**：等待用户请求，尽快响应。
    *   **指标**：响应时间 (Latency)、可用性 (Availability)。
*   **批处理系统 (Batch Processing/Offline)**：
    *   **特点**：处理大量有界数据，定期运行，无用户等待。
    *   **指标**：吞吐量 (Throughput) —— 处理特定大小输入所需的时间。
*   **流处理系统 (Stream Processing/Near-real-time)**：
    *   **特点**：介于在线和离线之间，事件发生后不久即处理。
    *   **差异**：输入是无界的（Unbounded），而批处理输入是有界的（Bounded）。

### 2.2 Unix哲学与工具链：批处理的基石

MapReduce的设计思想直接借鉴了Unix工具。

*   **案例分析**：使用 `cat`, `awk`, `sort`, `uniq` 分析日志。
    *   **排序的重要性**：`sort` 命令能处理大于内存的数据集（通过溢写磁盘），这与MapReduce中的核心排序机制一致。
    *   **内存聚合 vs. 磁盘排序**：小数据量可用内存Hash聚合，大数据量必须依赖外部归并排序。
*   **Unix哲学四大原则**：
    1.  **专注**：每个程序做好一件事。
    2.  **组合**：输入输出标准化（文件/流），程序间通过管道（Pipe）连接。
    3.  **原型**：快速设计，甚至先用脚本构建。
    4.  **工具化**：优先使用工具减轻编程负担。
*   **核心特性**：
    *   **统一接口**：文件描述符（File Descriptor）和字节流。无论是文件、套接字还是设备，都抽象为流。
    *   **逻辑与布线分离**：程序只关心stdin/stdout，由Shell决定数据流向（松耦合）。
    *   **透明性**：输入文件不可变（Immutable），便于调试和重试。

### 2.3 MapReduce与分布式文件系统

MapReduce是Unix工具在成千上万台机器上的放大版。

#### 2.3.1 系统架构
*   **HDFS (Hadoop Distributed File System)**：
    *   **架构**：无共享（Shared-nothing）架构，基于商用硬件。
    *   **存储**：数据分块（Block）存储，多副本冗余（通常3副本）以容忍故障。
    *   **NameNode**：中心元数据服务器，管理文件块位置。
    *   **计算向数据移动**：Map任务尽可能在存储数据的节点上运行（Data Locality），减少网络开销。

#### 2.3.2 MapReduce执行流程
1.  **Map阶段**：读取输入，提取键值对（Key-Value）。
2.  **Shuffle (混洗) 阶段**：**核心环节**。
    *   框架负责将具有相同Key的数据路由到同一个Reducer。
    *   **分区与排序**：Map输出按Key排序并分发。这保证了Reducer收到的是有序数据流。
3.  **Reduce阶段**：接收同一Key的所有Value，进行聚合或处理，输出结果到HDFS。

### 2.4 分布式Join算法

在海量数据下，如何关联两个数据集（如用户日志 join 用户表）是批处理的关键。

#### 2.4.1 Reduce端连接 (Sort-Merge Join)
*   **原理**：
    *   Map阶段：两张表的数据都通过Map读取，提取Join Key。
    *   Shuffle阶段：根据Key哈希，将两张表中相同Key的记录发送到同一个Reducer。
    *   Reduce阶段：由于Shuffle保证了排序（Secondary Sort），Reducer可以线性扫描并合并记录。
*   **优点**：对输入数据无假设（无需预先排序或索引），最通用。
*   **缺点**：所有数据都要经过Shuffle，网络和磁盘IO开销极其巨大。

#### 2.4.2 Map端连接 (Map-side Join)
如果对输入数据有特定假设，可以省去Shuffle阶段，极大提升性能。

*   **广播哈希连接 (Broadcast Hash Join)**：
    *   **场景**：大表 join 小表（小表能放入内存）。
    *   **实现**：将小表复制到所有Mapper的内存中，Mapper扫描大表时直接查内存中的小表。
    *   **应用**：Pig (Replicated Join), Hive (MapJoin)。
*   **分区哈希连接 (Partitioned Hash Join)**：
    *   **场景**：两张表都已按Join Key进行了相同的分区（Partitioned）。
    *   **实现**：Mapper 1只处理Table A的Partition 1和Table B的Partition 1。
*   **Map端合并连接 (Map-side Merge Join)**：
    *   **场景**：两张表不仅分区相同，且在分区内已按Key排序。
    *   **实现**：Mapper直接执行归并排序读取。

#### 2.4.3 数据倾斜 (Skew/Hot Spots)
*   **问题**：某个Key（如名人）数据量远超其他Key，导致处理该Key的Reducer成为瓶颈（straggler）。
*   **解决方案**：
    *   **采样**：先运行采样作业找出热键。
    *   **随机分发**：将热键记录随机分发到多个Reducer（Map端处理），另一侧的小表记录复制到这些Reducer。
    *   **Hive偏斜优化**：将热键单独存储和处理。

### 2.5 批处理的输出与哲学

*   **构建搜索索引**：Google MapReduce的初衷。MapReduce非常适合并行构建Lucene/Solr索引。
*   **Key-Value存储**：
    *   **反模式**：在Map/Reduce代码中直接写入数据库（会导致数据库雪崩、连接耗尽）。
    *   **最佳实践**：Bulk Loading。MapReduce直接生成数据库的底层文件（如HBase的HFile），然后批量加载。
*   **不可变性哲学**：
    *   输入不可变，输出完全替换旧版本。
    *   **优势**：支持幂等性（Idempotency），允许任务失败重试；易于回滚错误代码；利于实验。

### 2.6 Hadoop vs. 分布式数据库 (MPP)

| 特性 | Hadoop (MapReduce) | MPP 数据库 (如 Teradata, Vertica) |
| :--- | :--- | :--- |
| **数据模型** | **Schema-on-Read**：数据以原始文件存储，读取时解析。灵活性高（数据湖/寿司原则）。 | **Schema-on-Write**：写入前必须建模。查询优化好，但导入慢。 |
| **处理模型** | 任意代码（Java/C++等），适合非结构化数据（图像、文本）。 | SQL为主，适合结构化分析，不易表达复杂逻辑（如机器学习）。 |
| **容错性** | **任务级容错**：单个Task失败重试，不影响整体。适合超大规模、易被抢占资源的环境（Google Borg）。 | **查询级容错**：节点失败通常导致整个查询中止。假设硬件较可靠。 |
| **存储** | 分布式文件系统 (HDFS)，通用性强。 | 专有存储格式，紧密耦合。 |

### 2.7 MapReduce之后：现代数据流引擎 (Spark/Flink/Tez)

MapReduce的主要问题是**中间状态物化**（Materialization）：每个步骤（Map到Reduce）都要把中间结果写磁盘，这太慢了。

*   **数据流引擎 (Dataflow Engines)**：
    *   **核心改进**：将整个工作流视为一个DAG（有向无环图），中间状态尽可能保留在内存中，不写入HDFS。
    *   **算子 (Operators)**：比Map/Reduce更丰富的原语（Filter, Join, GroupBy），允许优化器全局优化执行计划。
*   **容错机制的变化**：
    *   MR依赖写入磁盘的持久化。
    *   Spark (RDD)：依赖**血统 (Lineage)**。如果数据丢失，根据依赖关系重新计算（Recompute），而非从检查点恢复（除非计算代价太大）。
*   **执行层面的差异**：
    *   JVM重用（减少启动开销）。
    *   基于成本的优化器（CBO）。

### 2.8 图处理 (Graph Processing)

*   **MapReduce的局限**：图算法通常是迭代的（如PageRank，需多次遍历），MR每轮迭代都要读写磁盘，效率极低。
*   **Pregel模型 (BSP - Bulk Synchronous Parallel)**：
    *   **核心思想**：“像顶点一样思考”。顶点之间发送消息。
    *   **超步 (Superstep)**：
        1.  函数处理接收到的消息。
        2.  更新顶点状态。
        3.  向其他顶点发送消息。
    *   **同步**：所有顶点完成一步后，统一进入下一步（Barrier同步）。
    *   **实现**：Apache Giraph, Spark GraphX, Flink Gelly。

### 3.1 为什么Hadoop强调“Schema-on-Read”？
*   **背景**：在企业环境中，数据来源复杂（日志、外部接口、传感器）。强制统一Schema（如MPP数据库要求）需要各部门协调，效率极低。
*   **数据湖 (Data Lake)**：先把数据按原样存下来（Raw Data is better），谁需要用，谁在读取时定义Schema。这解耦了数据生产者和消费者，加速了数据收集过程。

### 3.2 声明式语言的回归
虽然MapReduce允许运行任意代码，但编写复杂Join逻辑极其痛苦。现代框架（Hive, Spark SQL）回归了SQL或类SQL的**声明式API**。
*   **优势**：
    1.  **开发效率**：写SQL比写Java MapReduce快得多。
    2.  **执行效率**：查询优化器（Optimizer）可以根据统计信息自动选择Join算法（如自动将Broadcast Join应用于小表），利用列式存储读取和向量化执行（Vectorized Execution），这往往比手写代码更快。

### 3.3 MapReduce为何要如此频繁地写磁盘？
文中提到Google内部MapReduce任务经常被高优先级进程抢占（Preemption）。
*   **原因**：为了提高集群资源利用率，在线服务利用不完的资源会分配给批处理任务。
*   **后果**：批处理任务随时可能被杀掉。因此，MR设计必须极其“防御性”，每一步都存盘，确保任务能从断点继续，而不是重跑整个作业。但在专用Hadoop集群中，这种假设可能不再成立，因此Spark等内存计算框架更具优势。

### 3.4 批处理的意义
尽管流处理越来越流行，批处理依然不可替代：
1.  **基准与修正**：流处理可能丢数据或逻辑错误，批处理可以作为“Ground Truth”定期重跑修正（Lambda架构）。
2.  **复杂分析**：全量数据的深度挖掘、机器学习模型训练，依然依赖批处理。
3.  **确定性**：输入有界且不可变，保证了结果的可复现性和强一致性。
