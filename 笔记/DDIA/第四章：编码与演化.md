
## 数据编码格式

数据在计算机中有两种表现形式：
1.  **内存中 (In-Memory)**：对象、结构体、列表、树等，针对CPU访问优化（使用指针）。
2.  **传输/存储时 (On-Wire/On-Disk)**：自包含的字节序列（如JSON, Protobuf）。

**术语定义**：
*   **编码 (Encoding) / 序列化 (Serialization) / 编组 (Marshalling)**：内存对象 $\rightarrow$ 字节序列。
*   **解码 (Decoding) / 解析 (Parsing) / 反序列化 (Deserialization)**：字节序列 $\rightarrow$ 内存对象。

### 1. 语言特定的格式 (Language-Specific Formats)
如Java (`java.io.Serializable`), Python (`pickle`), Ruby (`Marshal`).
*   **特点**：绑定特定编程语言，使用方便（只需很少代码）。
*   **缺点**：
    *   **语言锁定**：其他语言难以读取。
    *   **安全性**：解码过程通常涉及实例化任意类，容易引发远程代码执行漏洞（RCE）。
    *   **版本控制差**：往往忽略了向后/向前兼容性。
    *   **效率低**：编码后数据臃肿，编解码性能差。

### 2. 文本格式 (JSON, XML, CSV)
*   **优点**：人类可读，广泛支持。
*   **缺点**：
    *   **数字歧义**：XML/CSV不区分数字和字符串；JSON区分但不区分整数和浮点数（且精度受IEEE 754限制，大于 $2^{53}$ 的整数在JS中会丢失精度）。
    *   **二进制支持差**：通常需要用Base64编码，增加33%的大小。
    *   **模式 (Schema) 可选**：虽然有XML Schema/JSON Schema，但很多应用不使用，导致应用层必须硬编码解析逻辑。
    *   **CSV模糊性**：缺乏标准，处理逗号/换行符需转义。

### 3. 二进制变体 (Binary Variants of JSON/XML)
如MessagePack, BSON, WBXML。
*   **特点**：基于JSON/XML模型，但改为二进制编码。
*   **局限**：虽然比文本紧凑，但因为必须包含**字段名称**（如`"userName"`），空间节省有限。

## 基于模式的二进制编码

### 1. Thrift 与 Protocol Buffers
**原理**：需要定义**模式 (Schema)**，通过IDL（接口定义语言）描述数据结构，并生成代码。

#### 编码机制：
*   **字段标签 (Field Tag)**：使用数字（1, 2, 3...）代替字段名称。
*   **紧凑性**：二进制数据中只包含“字段标签 + 数据类型 + 值”。
*   **示例**：Thrift CompactProtocol 和 Protobuf 使用可变长度整数（ZigZag编码）来压缩数字。

#### 模式演化规则 (Schema Evolution)：
*   **向前兼容性 (旧代码读新数据)**：
    *   旧代码遇到不认识的字段标签（新字段），根据数据类型标记**直接跳过**该字段。
*   **向后兼容性 (新代码读旧数据)**：
    *   新代码读取旧数据时，读不到新定义的字段。
    *   **限制**：新增字段必须是**可选的 (Optional)** 或有**默认值**，不能是**必须的 (Required)**。
*   **字段删除**：
    *   只能删除可选字段。
    *   **禁止复用标签号**：因为可能还有包含旧标签号的数据在使用中。

#### 数据类型变更：
*   可以改变数据类型（如int32变int64），但可能发生截断。
*   Protobuf没有专用数组类型，而是用`repeated`。这使得将单值字段改为多值字段（repeated）成为可能（旧代码只读取列表的最后一个元素）。

### 2. Apache Avro
**背景**：源于Hadoop项目，针对动态类型和大规模数据设计。

#### 编码机制：
*   **无字段标签**：二进制数据中**不包含**字段名，也**不包含**字段标签号。仅仅是值的连结。
*   **依赖模式**：解析必须严格按照模式定义的顺序和类型读取。

#### 读写模式分离 (Writer's vs Reader's Schema)：
*   **Writer's Schema**：写入数据时使用的模式。
*   **Reader's Schema**：应用程序读取数据时期望的模式。
*   **模式解析 (Resolution)**：
    *   Writer和Reader模式**不必完全相同**，只需**兼容**。
    *   Avro库通过对比两者，根据**字段名称**进行匹配转换。
    *   Writer有但Reader没有的字段 $\rightarrow$ 忽略。
    *   Reader有但Writer没有的字段 $\rightarrow$ 使用Reader定义的默认值填充。

#### 模式演化规则：
*   添加/删除字段必须提供**默认值**。
*   **字段类型**：使用`Union {null, type}`来表示可空（比Required/Optional更明确）。

#### 如何让Reader知道Writer的模式？
1.  **大文件 (Hadoop)**：模式写在文件头（Object Container File）。
2.  **数据库**：记录中带版本号，外部维护版本号到模式的映射（Schema Registry）。
3.  **网络通信**：握手阶段协商模式。

#### 动态生成模式的优势：
*   相比Thrift/Protobuf，Avro不需要手动分配标签号。
*   非常适合**数据库转储**场景：如果数据库表结构变了，只需生成新的Avro模式，不需要关心字段标签的映射。

## 数据流的类型 (Modes of Data Flow)

### 1. 数据库中的数据流
*   **场景**：一个进程写入，将来某个进程（可能是同一个）读取。
*   **本质**：存储 = 发送消息给未来的自己。
*   **兼容性需求**：
    *   **向后兼容**：必须的，否则无法读取以前存档的数据。
    *   **向前兼容**：在滚动升级中，旧代码可能读取新代码写入的数据。
*   **数据超出代码 (Data outlives code)**：
    *   代码更新了，但数据库里可能躺着5年前的数据。
    *   **注意**：旧代码读取新数据并更新时，**必须保持未知字段不变**（不要在写回时丢失了新字段）。
*   **归档**：数据转储通常使用最新模式，推荐使用分析友好的列式格式（如Parquet）。

### 2. 服务中的数据流 (REST 与 RPC)
*   **架构**：客户端/服务端（Web, Mobile, Microservices/SOA）。
*   **Web服务**：
    *   **REST**：基于HTTP的设计哲学。资源、URL、HTTP方法。强调简单、文本格式（JSON）。利于演化、调试和生态集成。
    *   **SOAP**：基于XML的协议。复杂，依赖WSDL和工具生成代码。互操作性常有问题。
*   **RPC (远程过程调用)**：
    *   **理念**：试图让远程调用看起来像本地函数调用（位置透明）。
    *   **RPC的根本缺陷**：
        1.  **不可预测性**：网络可能超时、丢失，而本地调用要么成功要么异常。
        2.  **结果状态**：超时后不知道请求是否已执行（需要幂等性机制）。
        3.  **性能**：延迟高且波动大。
        4.  **传值**：只能传序列化数据，不能传引用/指针。
    *   **现代RPC (gRPC, Finagle, Thrift)**：
        *   不再试图完全隐藏网络细节（使用Future/Promise, Stream）。
        *   性能优于REST（二进制编码）。
        *   主要用于**组织内部**服务间通信。
*   **演化**：
    *   通常假设服务器先升级。
    *   REST API版本控制：URL版本号 (v1) 或 Accept Header。

### 3. 消息传递中的数据流 (Asynchronous Message Passing)
*   **介于RPC和数据库之间**：低延迟（像RPC），但通过中间件存储（像数据库）。
*   **消息代理 (Message Broker)**：如Kafka, RabbitMQ, ActiveMQ。
    *   **优点**：
        1.  **解耦**：发送者不关心接收者是谁、是否在线。
        2.  **缓冲**：削峰填谷，提高系统可靠性。
        3.  **重试**：防止消息丢失。
        4.  **多播**：一条消息多方消费。
*   **数据模型**：代理通常不关心编码，只是字节序列。可以使用任何格式（推荐支持演化的二进制格式）。
*   **Actor模型 (分布式)**：
    *   如Akka, Erlang, Orleans。
    *   集成了消息传递和编程模型。
    *   **挑战**：滚动升级时，不同节点的Actor代码版本不同，消息编码必须兼容。
